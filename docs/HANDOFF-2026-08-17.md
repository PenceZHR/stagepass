#### 需求原文（2026-08-17 用户原话）

> 「现在每个 stage 点开圆圈有一个界面，进去又有了一个界面，是不对的，交互太乱了，
> 统一成一个页面。」

现在点进去要穿三层：

| 层 | 是什么 | 里面有什么 |
|---|---|---|
| 1 | 阶段环 | 八个圆圈，点一个 |
| 2 | `#sheet` 弹层（`panel.html` 的 `<dialog class="sheet">`） | 问题 / 标准两个页签、下一步、闸门动作（跑这个阶段 / 请 Codex 问我 / brief 定稿 / 接受风险）、**答题表单**、以及一个「查看阶段产物」按钮 |
| 3 | `#stage-view` 产物驾驶舱（`stage-artifact-view.js`） | 整屏接管：轮次与文件 / 星图 / 只读文件，自带顶栏（打开系统终端）和「← 阶段详情」返回 |

**要合成一页。** 合并时不能弄丢的东西（每一条都是真机撞出来才有的）：

- 答题表单只画在**它自己那个阶段**（`openQuestionOf` 的 phase 收窄）—— 一道 Build 的
  裁决不许出现在别的阶段上；
- 表单上的题号写在 DOM 上（`form.dataset.question`），不是闭包变量 —— 判据是
  「人现在看着的是哪一道」；
- 进入阶段是**纯查看**：不自动拉起或聚焦 Terminal.app，不启动 turn，不推闸门；
- 退出时恢复进入前的 Workspace 收起状态（`stageWorkspaceWasCollapsed`）；
- 轮次时间轴换行排布，任何轮数下都不出现横向滚动条（22 轮那次的教训）；
- canvas 的 CSS 尺寸由样式表钉成 100%（`updateStyle=false` 那个坑）。

**判据**：一个阶段的全部东西在同一屏上说完，不需要「再进去一层」。至于是并列三栏、
可折叠区块还是别的形状，是设计问题，动手前先定。

### 换掉了什么

**问人不再派信使。** 裁决 / 录需求 / 接受风险三条路的题都是 StagePass 自己算的，
模型从来只是个把表单端到人面前的信使。为了这一次转达要：起会话、注入 MCP 配置、
等它调工具、还要防它「一个工具都没调就结束了 turn」。

2026-08-17 实测：那条线程从 08-15 建立起**一次 MCP 调用都没有过**，而 MCP 只在线程
创建那一刻绑得上、事后补不了，`codex resume --remote` 上的 `-c` 对它无效 ——
信使这条路本身就是不稳的。

现在题落进库里，面板画到浏览器上，人在那儿答（`POST /api/answer`）。

**一个语义跟着变了，是对的**：「会话死了」不再等于「这道题废了」。题就摆在页面上，
跟会话活不活着没关系；没答上就是 `no_answer_in_time`。
`session_died_before_answering` 和 `ask_turn_ended_without_answer` 两类整类消失。

**一轮的产出改走格子文件**（`domain/round-slots.ts` + `system/slot-files.ts`）。
结构由 StagePass 铺好（15 个格子、上限填 10），模型只把 `null` 换成值；
`id` 和 `artifacts` 都预填，模型连它们都不用写。任何一条对不上就整份拒绝，
理由原样留给下一轮 —— 不修复、不猜、不截断。

**MCP 整条拆掉**，不留回退：`src/plugin/` 整个目录、反向请求处理器、
`mcp_servers.*` 注入、`TerminalTarget.config` 与 `-c` 覆盖，以及 `ask-human.ts` 里
整套中继机器。

### 真机验过的

- 裁决：`/api/ask` → 题出现在 Build 弹层 → 界面上逐格选完提交 → 库里
  `applied {advanced, reject}`，Change 从 `Build/settled` 走到 `Build/running`
  并续跑了一轮。**服务日志里 `stagepass_ask` 出现 0 次，MCP 进程 0 个。**
- 跑一轮（用户 2026-08-17 11:59 实机）：`JOB-CHG-002-PRD-1786967650580` `done`，
  `artifact_ids` = `["docs/stagepass/CHG-002/PRD-r2.md"]`（StagePass 预填，文件真在
  磁盘上），19 条判定 15 yes / 4 未判，反方 `overall` 从格子文件读出。
  格子文件铺 2 份、读完清 0 份 —— 走的确实是格子那条路。

### 途中挖出来并修掉的真错

1. **格子 id 会撞车**：红蓝两份文件各一套 `G-01`…，并进同一份发现名单时按 id 去重，
   后来那条被当成重复吃掉。改成 `R-01` / `B-01`。变异验证过。
2. **`Number("")` 是 `0`**：浏览器交空格子会被静静地答成第一个选项。
3. **`questions.answer` 收的是 elicitation 信封**（`{action, content}`），塞裸答案表炸
   `answer_action_unknown`。纯映射的单测碰不到，真机点出来的。
4. **格子 id 不补零**会撞上 `compose` 的 `order_not_sorted`（表单按字段名排序），
   整批问题发不出去。
5. **还没跑过 turn 的新线程被判失败**：`readRecentTurns` 撞上 `not materialized yet`
   会让整个 job failed。一条连第一条用户消息都没收到的线程可证明有零轮 turn。
6. **删 Change 会炸 FK**：`ChangeStore.delete` 里是一串**手写表名**，
   `aside_visits`（2026-08-11 加的）没人记得补进去。改成问 schema，
   下次加表自动跟上。删 CHG-001 时撞出来的。
