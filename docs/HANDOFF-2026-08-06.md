## 一、这一刀治的是什么

用户 2026-08-06：「输出质量有问题，反复对抗不收敛」「PRD 阶段会涉及很多其他阶段的
问题，比如说架构、技术栈、测试 —— 这肯定不是他做的呀」「力度有问题，追的过于细」。

取证（当时的 `~/.stagepass/panel.db`，CHG-001，21 轮）：

| 路径 | 有阶段边界 | 有上限 | 产出 | 挡门 |
|---|---|---|---|---|
| **blockers**（`PHASE_PLAY.blue.task`） | ❌ | ❌ | **139 条 finding** | 全挡 |
| **rubric 逐条判定**（`PRODUCER[phase]`） | ✅ | ✅ | 192 条（64 个 `no`） | **一条不挡** |

`standard` 类 gap：**0 条**。接线是好的，0 是设计造成的 —— 298 条 criterion 全
`blocking=0`（出厂一律不阻断，2026-07-31 拍的）。

**一句话：准的那条路只说不算，野的那条路说了算。**

而 `PHASE_PLAY` 里**十一个阶段的反方任务逐字相同**（「找出遗漏、冲突与不可验证之
处」）—— 「每个阶段有自己的尺度」在代码里根本不存在，而「不可验证之处」这五个字
就是无限精度递归的发动机。

## 三、做出来的形状

### 3.1 模板管红方，收口管反方 —— **两件事，两个判据**

这是这一批里最要紧的一处更正。原来把「收口」绑在「有没有模板」上，铺开到 Review/QA
时 16 条测试红了，逼出真正的问题：**Review 的反方是第二个审查者，不是文档评审员** ——
它读得到代码、自己去看，报的是真缺陷。砍掉它，Review 就只剩红方一个人看代码。

| 判据 | 谁 | 后果 |
|---|---|---|
| `templateFor(phase) !== null` | 九个**产出文档**的阶段 | 红方必须照节写，缺节挡门 |
| `PHASE_PLAY[phase].blue.investigates` | 五个**反方够得着代码**的阶段 | 保留自由 blockers |

- **有模板**：PRD / Spec / TechSpec / Plan / TestPlan / Review / QA / Merge / Retro
- **无模板**：Build / Fix —— 它们交的是 commit，套模板 = 六节永远缺、永远挡门
- **投调查**：Build / Fix / Review / QA / Merge
- **收口**：PRD / Spec / TechSpec / Plan / TestPlan / Retro —— 每轮上限 = criterion 条数，**收敛 = 全 yes**

`investigates` 那一格**紧挨着 `blue.reach`**，因为它就是 reach 的直接后果 —— 不另建名单。

### 3.2 落点

| 在哪 | 是什么 |
|---|---|
| `domain/phase-template.ts` | 九份模板，4~6 节。认节：**标题逐字相等**（不是包含），标题底下空着也算缺 |
| `domain/round.ts` `templateGaps` | 缺节开 `TEMPLATE-<节>`（finding/P1）。**不经模型的嘴** —— 缺没缺是数出来的，补上了也是数出来的。人 waive 掉、驳回掉的一个字都不碰 |
| `rubric_criteria.section` | 可空列，走 `migrate` 那条「只加可空列」的路 |
| `rubric-defaults.ts` | 九份 rubric 按节铺开（PRD 11 / Spec 8 / TechSpec 8 / Plan 5 / TestPlan 7 / Review 6 / QA 5 / Merge 4 / Retro 4） |
| `RubricStore.upgradeDefaults` | **起面板时后台自动升**（用户 2026-08-06：「页面不要带升级到最新版」）。判据是 `rubrics.reason` 上那个标记 + 「还是第 1 版」—— 换掉「只认 v1」是因为那条把自己锁死了：升一次就变 v2，同一份永远升不上去 |
| `summariseAssessments` | 裁决表多一句「**卡在 acceptance、assumption**」 |

### 3.3 出厂 `blocking` 的窄口例外

判据是**结构性的**：**阻断 ⟺ 挂了节**。2026-07-31 那条拍板在十一个阶段一个字都没被
翻，两份护栏（域层 + 装库读回）都改成**双向断言**钉这个边界，不是放宽。

理由：原来一律 `false` 防的是「漏答视同阻断 → 新项目一上来被拦」。模板下漏答有了
另一个出口 —— 缺节在红方那一侧就被 `templateGaps` 判掉了，轮不到反方漏答。

## 四、路上撞到的三件事（都留了护栏）

1. **`section` 会在面板保存时静默丢掉。** `panel.js` 的 drafts 只搬 `key/text/blocking`。

2. **加路由让 `handle()` 从 607 涨到 618，棘轮当场拒了。** 按它指的方向还债：

3. **升级按钮「不存在」。** 真机实测：它在 DOM 里，但排在「第 N 轮判定」后面、
   掉到折叠线以外 —— 而「看不见」和「不存在」对使用者是同一件事。位置本身也错：
   它是项目级动作，不该埋在某个阶段的判定底下。已挪到最上面。

## 五点二、PRD 六轮的实测账（**机制立住了**）

| 轮 | 结局 |
|---|---|
| r1 / r2 | 反方契约漏 `artifactIds` —— 我的 bug，`5ecc76a` 修 |
| r3 | producer 10 yes / **1 no**（`deferred` 技术栈越界） |
| r4 | 没人按，turn 超时 30 分钟，整轮作废 |
| r5 | producer 10 yes / **1 no（同一条）** + critic 2 条结构性 no |
| **r6** | **producer 13 yes / 0 no，critic 4 yes / 0 no**，那条 standard closed |

**四个结构判据全程成立**：`finding` 恒为 0、模板缺节恒为 0、每轮判定条数有上限、
越界被逮住而且逮的是对的那件事（红方把 Cocos 3.8.8 写进结果和验收 → 判 no）。

对照真库上一份：**21 轮、139 条 finding、没有一个阶段收敛过、全靠人 waive 收场。**

### 五个设计阶段全部跑通（2026-08-06 晚，真机）

| 阶段 | 轮 | 判定 | `no` |
|---|---|---|---|
| PRD | r6 | 17 | 0 |
| Spec | r2 | 12 | 0 |
| TechSpec | r1 → r2 | 12 → 12 | **1 → 0** |
| Plan | r1 | 9 | 0 |
| TestPlan | r1 | 11 | 0 |

**六轮有效对抗，五种模板（7 / 5 / 6 / 5 / 5 节）：`finding` 累计 0，模板缺节累计 0。**

唯一那条 `no`（TechSpec 的 `deferred`：「留给下游的每一项都写明留给哪个阶段」——
红方只写了「相应下游阶段」）**被红方一轮修掉**。那是「有界且可修」最直接的证据：
一条具体的、指得出名字的、红方够得着的意见，不是同一句抱怨在降尺度。

> ⚠ **「连续两轮全 yes」仍然是零个完整样本。** 用户每次都在第一轮全 yes 之后就
> 批准放行 —— 那是他的裁决权（闸门本来就把这个决定留给人），但从取证角度，
> **「模板真的封住了可挑剔的表面」这件事还没有被证明过一次**。
> 想拿到它，只要在任意一个阶段连着跑两轮不批准。

> ⚠ 这份账是这套机制**唯一的证据**，而上一份（21 轮 / 139 条）已经被删过一次
> 且不可恢复（BACKLOG §8.5）。下次清库之前先导出来。

### 两个「红方赢不了」的标准，是真机逼出来的（`fe9576b` 已修）

单元测试永远抓不到它们 —— 它们不是「代码错了」，是**要求了一件结构上做不到的事**。

1. **模板漏了「已经定死的约束」那一格。** r3、r5 连着两轮判 `deferred` 为 no，
   而红方两轮都改了：先写在结果里（no），再挪进「留给下游决定的」（还是 no ——
   一个不可退让的约束根本不是「留给谁决定」）。**它没地方可写。**
   → PRD 加第七节，标准措辞分开「新定」和「转述人已经定死的」。r6 当场 yes。
2. **我收走了反方的 id 通道，却没回头看哪条标准在要它。** 砍掉 blockers 之后，
   共用的 `CRITIC` 里「沿用同一个 id」「每条问题指向具体位置」在 PRD **结构上永远
   判 no** —— 裁判的理由写得明明白白：「反方的返回 JSON 里没有携带既有问题的 id」。
   → `CRITIC` 按能力分流。判据是这棵树已有那条的反面：
   **放开一样能力要看有没有标准在禁它；收走一样能力，要看有没有标准在要它。**

## 五点五、真机跑出来的三个投递层缺陷（**都没修**）

> PRD 六轮 + Spec 一轮撞出来的。**机制本身四个判据全程成立**（`finding` 恒为 0、
> 模板缺节恒为 0、每轮判定有上限、越界被逮住），挡路的全在投递层。

### 5.5.1 裁决完成之后，那个 Codex 会话不会关

人按「请 Codex 问我」→ 答完 → Change 进了下一阶段，**而那个 `codex resume` 进程
还活着**（实测 22 分钟，父进程就是面板）。

下一阶段起轮时 StagePass 认不出哪个会话是自己的，整轮作废，错误写得很准：

```
codex_unavailable: new Codex sessions appeared but none carried this prompt;
                   another Codex is probably running
```

### 5.5.2 出口按「注册表里有没有」判，而进程不一定在注册表里

`panel.js`：`closeTermButton.hidden = !entry.live`，注释自己写着
「**出口：有活进程时才出现。没有它，上面每一个 disabled 都是一个没有出路的死结。**」

而 `entry.live` 只认 `PanelSessions` 那个注册表 —— `CodexTuiTransport` 为一轮直接
spawn 的进程不进注册表。于是实测到的状态是：**进程真的在跑，面板说没有，出口被藏，
「跑这个阶段」「请 Codex 问我」一起藏，人手上一个能按的都没有。**

判据取错了地方：该问的是「这个 (Change, 阶段) 上有没有活着的进程」，两个来源，
而只有一个被问到了。

> ⚠ 查这类问题**不能只看 `.disabled`**：一个 `display:none` 的按钮，`disabled`
> 照样读得到。要看 `getBoundingClientRect()` 是不是 0×0。这一轮我就是先看了
> `.disabled`、报了「按钮正确地灰着」，而它其实根本没被画出来。

### 5.5.3 页面轮询死了不自愈

重启面板的那几秒，页面的轮询 fetch 抛异常、循环就死了 —— 服务器回来之后页面**永远
冻在旧状态**：按钮不变灰、点了没反应、终端不动。人第一反应是「系统坏了」。

### 共同的形状

**三条都不是「状态错了」，是「状态对的，但人看不出发生了什么」。** 失败原因一直写在
`jobs.error` 里，屏幕上一个字都没有。修任何一条之前先想清楚：**这件事该在哪一屏
告诉人。**

## 五点七、**让 Build 也收敛：三刀已落（`7c0b5c2`），真机验过一轮**

> 用户原话：「上面 3 个我都需要，3 个刀都要同时做。」

### 真机第一轮（Build r1，2026-08-06 晚）

```
判定 +18（13 producer + 5 critic）    no 7
finding 0     模板缺节 0（六节全中）     产出 Build-r1.md 1124 字
```

**对照三刀之前：Build r2 开 35 条 finding、r6 开 21 条。** 那条无上限的通道关掉了。

七条 `no` **全部指向同一个事实：红方基本没干活** —— 只交了一份报告，没按 Plan 做
诊断/基线/目标收敛/范围追溯，也没跑 TestPlan 的用例。六条 producer 标准从六个角度
独立撞上同一件事，**这正是机制该有的样子**：不是六个不同的挑剔，是同一个事实被
六个格子分别照出来，而且每一条都指得出名字、红方修得动。

**第一刀当场验到了**：`tests` 那条判 no，依据是「报告明确承认 TestPlan 用例均未
运行」—— 「Build 不许自审」第一次在报告层面被抓住。

第七条是 critic 的，也判得对：反方判 no 时没指明是报告的哪一节 —— 那正是同日换上去
的新标准（`CRITIC_WITH_ASSESSMENTS`）。

### 还差机械的那一半

**轮末 diff 闸门没做**：「Build 这一轮碰了测试路径就整轮作废」。现在只有报告里那条
标准在管，而 `phase.ts` 自己写着 Build 是整树提交、**StagePass 分不出哪一行是红方
写的** —— 靠提示词说「不许动测试」，模型违反了没人发现。

要动 `RepoOps`（轮末取这一轮的改动路径列表），是独立的一块。


### 为什么 Build 和设计阶段不同

设计阶段能收敛靠两样：**模板**把散文切成有限个格子，**收口**让反方只走逐条判定。
Build 两样都不成立 —— 它交的是 commit（没有可切的表面），它的反方读得到代码
（发现是真缺陷，无界是本质的）。所以要么给它造一个表面，要么拿掉它那个无限表面。
**用户要求两件一起做，再加上治病那一刀。**

### 三刀

**① 拿掉它自己写的检查**（治 BACKLOG §8.3 诊断出来的病）

Build 那 35+21 条大头是 `verify.mjs` 的绕过点 —— **它自己写的验证器**，关掉一个就
长出下一个，这类没有收敛点。两件事：

- TestPlan 写测试：进 `PRODUCES_COMMIT` + `artifact-home` 给代码落点
- **Build 轮末 diff 闸门**：这一轮碰了测试路径就整轮作废。**只能是机械判据** ——
  Build 是整树提交，StagePass 分不出哪一行是红方写的，靠提示词说「不许动测试」
  模型违反了没人发现

**② 给 Build 也造一份模板**

红方除了 commit 还要交一份「施工报告」，那就有了可离散化的表面。
**单独做没用** —— 反方仍然读得到代码，不收口的话模板只约束了报告、没约束发现的数量。

**③ 把真缺陷挪到 Review**

Build 的反方也收口（`blue.investigates = false`），只判编码规范 rubric；
代码缺陷留给 Review —— 它的红方本来就是审代码的。

### 三刀合起来是连贯的

①治红方那一侧的所有权，②给 Build 一个表面，③收口反方。**②+③ 合起来正好让 Build
变成和设计阶段同一个形状**，而①把那个无限表面拿掉。

### 开工前必须先拿到的一个答案

**§8.7·1：TestPlan 交的测试，要不要求当场能跑、而且是红的？**

- 要求 → TestPlan 得能执行命令、得查干净树，**地基级**。它能挡住 TestPlan 交一堆
  假测试 —— 否则病只是从 Build 搬到了 TestPlan
- 不要求 → TestPlan 产出的是没验证过的测试代码，Build 第一次跑才知道它对不对，
  而那时改它的权限已经不在 Build 手上

**这条不拍，①只能做一半。**

### 已知代价（用户已接受）

- ③ 让 Build 的反方不再报代码缺陷 —— 而红方刚写完代码，此时发现最便宜；
  推到 Review 才发现，修它要走 Fix，多一整个阶段
- ① 要动 `PRODUCES_COMMIT`，而 `phase.ts:212` 写着那条名单**同时**意味着
  「整树提交」和「要求干净树」，**两件事同一个名单不许分开** —— 这一刀要重新想它

### 顺带

这一刀落了之后，`docs/RUBRICS-AND-TEMPLATES.md` 要重新生成
（`node --import tsx scripts/dump-rubrics.ts`），Build/Fix 那两行会从「没有模板」变掉。

## 六、**删除一个 Change 的语义（用户 2026-08-06 提，还没做）**

1. **「删 Change」到底要删到哪一层？** 库 / 工作树 / git 历史，三层的可逆性差着数量级。
2. **git 历史那一层做不做得到？** 只有 `filter-repo` 按路径拔那一条路，而它会改写

3. **id 复用是不是本身就该改掉？** 产物目录撞车的根在这儿。一个不复用的 id

4. **纯产物和整树提交要不要分开？** 如果 Build 的产物也走窄提交、代码走另一条，
   「删掉 StagePass 写的东西」才第一次成为一个可执行的操作。
