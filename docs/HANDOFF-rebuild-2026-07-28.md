## 一、先读这个：为什么重建

不是因为代码烂。是因为**没有人（包括模型）能判断哪部分是真的**。

删除老树里一个组件文件之前，必须先查：它有没有活的父组件、某个 prop 传给了谁、钉它的测试是不是 `describe.skip`。**查了四轮才敢下手，一个文件。** 那样的文件有几百个。

这条约束是不可能在老树上增量满足的 —— **每一次删除都要依赖那个已经被证明不可靠的判断**。所以新树的属性必须是可判定的：里面每一行都是有人特意放进去的。

|---|---|
| 走通过的 Change（PRD → Done） | **0** |
| 历史上完成过的闸门命令 | **1**（走的是名叫"紧急"的 web 表面） |
| `gate_decision` 卡被人看见过的次数 | **0** |
| `human_decisions` 里真正由人产生的行 | **0** |

**没有可回归的东西。** 反对重写的常规理由（作废十万行测试）默认系统能跑 —— 它不能跑。

## 四、今天定死的判断（不要重新讨论，除非有新证据）

### 4.1 人机交界走 Codex TUI，不走 App

四条路各测了一遍，只有一条闭合。**全部目视或日志确认。**

| 路线 | 结果 |
|---|---|
| host-attested MCP App（老需求文档指定的主表面） | ❌ 从未运行过 |
| `codex mcp-server` + `codex://threads/<id>` 回看 | ❌ **Desktop 打开是空的**（rollout 78KB 一条不缺，窗口就是不显示） |
| mcp-server + StagePass 自渲染流 | ⚠️ 能跑，**用户否决**：渲染是 Codex 的事 |
| **`codex resume <id> "<prompt>"` + MCP elicitation** | ✅ |

决定性差别：**`codex resume` 自动发送，零按键；App 的 `threads/new?prompt=` 只预填不发送 —— StagePass 无法自主发起。**

TUI 里敲 `/app` 能把会话接力给 Desktop，三个客户端共用 `~/.codex` 底座。**所以两个表面都保留，只是 StagePass 只驱动 TUI。**

### 4.2 提问用 MCP elicitation，「卡片」这个概念作废

```
CLIENT_CAPABILITIES: {"elicitation":{"form":{},"url":{}}}
```

`ui://` HTML widget 押注单一客户端的渲染实现，那正是它死掉的原因。elicitation 是**协议层能力** —— 谁拥有 turn，选择器就在谁那里渲染。

实测通过的三种形状：闸门裁决（1 题 N 选项）、批量澄清（**3 题含布尔，一次问完**）、取消（`{"action":"cancel"}`，不带 content）。

### 4.3 插件不走 HTTP，直接读写同一个 SQLite

没有端口、没有鉴权、没有 actor 身份 —— 老树在这三样上花掉大部分复杂度还是搞错了（16 条插件回执全标成 `codex_mcp_app`，而那个 app 从未启动）。

schema 只允许插件做两件事：读一个已提出的问题、追加一条答案。`changes` 在账本触发器后面，**直接改会 ABORT**（有断言）。

### 4.4 沉默保留，关闭必须明说

Gap 的核心规则。老实现每轮整体覆盖 blockers，注释写着"仍成立的问题是这一轮自己的责任去重报"—— **那是把要求推给模型，而这恰恰是模型最做不到的事。**

现在：发现是事件，Gap 是状态。**安全方向同时也是偷懒方向**，忘记什么都打不开。

`closed` 必须带理由（没理由的关闭和"忘了"长得一样）；`waived` 是人的决定，只有人能撤销；重新发现会重开 closed 但不会撤销 waived。

### 4.5 裁判是唯一的用户界面

红蓝是裁判**派生的子 Agent**，不是另开的 Terminal。两条理由，第二条是技术性的：**子 Agent 有独立线程和上下文，蓝方看不到红方的推理**；同一线程的顺序 turn 做不到，蓝方会读到红方所有自辩，质疑退化成附和。

实测可控：`SpawnAgentArgs { agent_path, agent_nickname, agent_role, prompt }`、`WaitAgent { timeout_ms }`，每个子 Agent 可单独指定模型和推理强度，还能 `no-apps`。

PRD §5.7 明写：**不许为红蓝各开一个 TUI。**

### 4.6 Codex TUI 搬进 StagePass Web 的终端面板（2026-07-28 定）

**Codex TUI 运行在 StagePass Web 里的一块 pty 面板中，不再是 Terminal.app 窗口。**

#### 这不违反「StagePass 不渲染」，但判据必须换

被否决过的那条路（§4.1 表格第三行）是：StagePass 解析 `codex mcp-server` 的事件流，**自己理解语义再画界面**。

这次不是。pty 里跑的是同一个 `codex` 二进制，画面仍由它用转义序列自己画，xterm.js 只把转义序列还原成像素 —— 它不知道什么是「thinking 块」、什么是「选择器」。**换的是窗口宿主，不是渲染者。**

**注意 `Terminal.app` 也不是「Codex 原生客户端」** —— 它是苹果写的通用终端模拟器，Codex 只是在里面跑。原话里的"原生客户端"指的是 **TUI 这个程序本身**，不是包着它的那块玻璃。所以今天的 osascript 方案与 pty 面板**在架构上是同一个位置**：通用终端宿主 + Codex 在里面自己画。区别只是玻璃谁写的。

#### 但这带来一个真问题：判据从可机械检查变成了要人判断

今天的判据「`src/` 里没有任何渲染代码」grep 一下就知道过没过。换成「不许解释 Codex 的语义」，就需要有人判断某段代码算不算解释。而 §一 说重建的**首要理由**正是「没人能判断哪部分是真的」—— 判据一旦要判断，它就会滑：先是「turn 结束加个高亮吧」（要 parse），再是「选择器滚上去看不见了，顶部加个提示吧」（要 parse），最后回到那条被否决的路上。

**滑坡的第一推力是一种观感**：读代码的人会本能地觉得"这不就是回到自渲染了吗"。这个观感有一半是对的 —— 看的地方确实回到了 StagePass。所以判据必须是机械的，不能靠自觉。做法见 §九 改动 3。

#### 收益不只是好看

今天 `defaultLaunch`（`tui-transport.ts:217`）是 `detached: true` + `.unref()`，**StagePass 连子进程句柄都扔了**，不知道 TUI 还在不在。所以 §五.3 那个坑（不能等进程退出）只能靠 30 分钟超时兜底。**pty 握在 StagePass 手里，这个风险从「靠超时猜」变成「进程死了立刻知道」。** 另外顺手去掉 osascript 这个 macOS 绑定。

#### 与 4.5 的关系（容易搞错，写死）

**L4 的对抗阶段在面板里仍然只有一块终端 —— 裁判那块。** 红蓝是子 Agent，不是终端。任何"对抗阶段开三块面板"的设计直接违反 PRD §5.7。

#### 路 B 内部的顺序（用户 2026-07-28 决定）

**不为面板单独安排一次 L3 演练。面板建好之后，一次真选择验完 pty 版 L2。**

L3 已经在 Terminal.app 版上通过（§二），所以这里要验的是**执行通道换成 pty 之后 L2 仍然成立**，以及 elicitation 选择器在 pty 里可用。

### 4.7 阶段线程：一个 (Change, 阶段) 一个 thread

**绑定粒度从「一个 Change 一个」改成「一个 (Change, 阶段) 一个」。** 与 4.6 是一起的，不能只取一个：粒度改细的前提是有地方把 11 块终端组织起来。

#### 理由是 fence，不是「乱」

「一个 Change 一个终端会很乱」是真的，但那是审美理由。真正的理由是 PRD §4 概念 3：*决策绑定它所依据的快照；快照变了，旧决策失效而不是静默生效。*

一个 Change 一个线程，意味着 Spec 阶段的裁决**有一部分依据活在 Codex 的对话历史里** —— 模型记得 PRD 阶段聊过什么，而那段记忆不在 StagePass 的任何快照中。**fence 管不到它。** 这是结构性缺口，不是 bug。

一阶段一线程之后，跨阶段信息**只能走文档**（PRD → Spec → TechSpec …），而文档正是能快照、能哈希、能 fence 的东西。**所以这不是把界面弄整齐，是让 fence 真的覆盖全部输入。**

第二条实际理由：上下文长度。12 阶段 × 每阶段若干 turn，加上 L4 的红/蓝/裁判轮次，全塞一个线程，而 `codex resume` 每次恢复完整历史。

#### 现有代码写的是相反的决定，必须一起改

`src/store/binding-store.ts` 第 5–13 行的注释写着 *"One Change, one persistent Codex thread"*，并给了两条理由：

| 原理由 | 现在成不成立 |
|---|---|
| 人的活会散在十几个 task 里 | **不成立了。** 12 个线程如果是面板里按阶段排的 tab，那不叫散，那叫有组织。**这正是 4.6 改变的东西** —— 它把「一阶段一线程」从代价变成收益 |
| 每个阶段开一段不知道前面的新对话 | **成立，是真代价。** 换来 fence 完整 + 上下文不爆。账要记：**每个阶段的开场 prompt 必须自己带上游文档**，组题工作变重（方向与 PRD §5.2「StagePass 全权组题」一致，且让"模型知道什么"从隐式变显式） |

**这段注释不改掉就是 §一 描述的那种毒** —— 下一个读代码的模型会看到一段理直气壮论证相反决定的文字，且没有任何标记说它已作废。

#### 具体规则

1. **12 个阶段**（以 `src/domain/phase.ts` 的 `PHASES` 为准），`Done` 是终态不发生 turn，所以**实际有线程的是 11 个**。
   - `phase.ts` 第 16–18 行记着老树曾在这件事上自相矛盾（`CONTENT_PHASES` 说 13、`PipelinePhase` 说 9）。**不要引入第三个数字。**
2. **重入复用同一线程。** `Fix` 不在 `advancesTo` 里（`phase.ts:60`），一个 Change 可以进 Fix 很多次；设计阶段被拒是「原地再来一轮」（`phase.ts:71-77`）。所以 `(change, 阶段)` 在时间上不唯一 —— **已决定：重入 `codex resume` 同一个阶段线程，不新开。**
   - 理由：Fix 第三轮最需要的上下文，恰恰是「前两轮改了什么、为什么还没过」，那正在同一线程里。
   - 代价：被打回多次的阶段线程会变长。认了 —— 它长的是**同一件事**的历史，不是十二件事的。
   - 固定 11 块使面板可穷举，与 PRD §4 概念 1「阶段与转移可穷举」同构；每次新开会让面板变成一个会长的列表，那是老树「不知道有多少东西活着」的形状。
3. **跨阶段信息只能走文档。** 这是那笔交换的另一半，必须和粒度写在一起，否则下一个人会以为上下文还能靠对话历史传。
4. **不需要 11 个进程同时活着。** rollout 文件是持久的，任何一块随时能用 `codex resume` 复活、历史不丢。常驻 1–2 个，其余是**可复活的空壳**：点开就活，关掉不丢。
5. **同一个阶段线程，任何时刻只许有一个活着的进程。** 两个 `codex resume <同一个 id>` 同时往一个 rollout 追加，§五.2 那个坑就废了 —— turn 边界交错，认错就拿到别人的答案。一阶段一线程降低了这个风险（并发的是不同文件），但面板必须保证它，因为面板让「同时开着好几块」变成常态。

### 4.8 权限走 invocation，一阶段一套

#### 现状（从 `~/.codex/config.toml` 与 `codex --help` 实读）

- `[projects."<绝对路径>"] trust_level = "trusted"` 机制**已存在**，`/Users/zhanghr/Desktop/stagepass` **已经在里面**。
- `/Users/zhanghr` 与 `/Users/zhanghr/Desktop` **本身也是 trusted**，桌面下的项目都已继承。**不要把「为项目开信任」写成待办。**
- **但 `trust_level` 只管一道门：「你信不信这个文件夹」，它不管审批策略。**

#### 真正的两个开关（`codex-cli 0.144.4` 实读）

| 开关 | 可选值 |
|---|---|
| `-s, --sandbox` | `read-only` / `workspace-write` / `danger-full-access` |
| `-a, --ask-for-approval` | `untrusted` / `on-request` / `never` |

`never` 原文：*Never ask for user approval. Execution failures are immediately returned to the model.* —— 零提示；被沙箱挡住的命令直接把错误回给模型。

**已实测：`codex resume` 这两个参数都接受。**

**版本陷阱**：这个版本**没有** `--full-auto`，也**没有** `on-failure` 档位。旧文档和旧记忆里有它们，照抄会得到一个启动即失败的命令行。

#### 决定一：不写进 `~/.codex/config.toml`

1. **StagePass 改用户的全局 config，是 M5「读接口不许写」的反面。** 性质等同老树 `listBaselineDocs` 在 GET 里 scaffold 十个文件。
2. **会漏。** 全局配置会影响用户在别的终端、别的项目里手动跑的 codex。
3. **成本是一行。** `src/codex/tui-transport.ts:135` 已在拼 flags 数组（`-s` 就在那里）。

（若将来需要文件形态，`-p, --profile <NAME>` 会层叠 `$CODEX_HOME/<name>.config.toml`，比改主 config 干净。默认走 flags。）

#### 决定二：一阶段一套权限

`-s` / `-a` 本就是 per-invocation，`CodexTuiTransportOptions.sandbox` 已是参数 —— **这一层是免费的**，且与 4.7 同构：

| 阶段 | 给什么 |
|---|---|
| PRD / Spec / TechSpec / Plan / TestPlan | `-s read-only -a on-request` |
| Build / Fix | `-s workspace-write -a on-request` |
| Review / QA | 沙箱按是否需要跑测试决定；`-a` 同上 |

## 五、坑（会再咬人的）

1. **`src/db/schema.ts` 里不许写反引号。** 整个 schema 是一个模板字符串，注释里一个反引号就终止它，然后在几行之后报一个关于无关单词的语法错。**今天踩了四次。** 检测是即时的（typecheck 直接挂），只是错误信息指向错地方。

2. **`codex resume` 追加到同一个 rollout。** 一个文件里有这个线程的全部历史，从头扫会返回**上一个问题的答案** —— 表现为一个快得离谱、内容还不对的 turn。transport 记录提问前的记录数，只往后读。

3. **TUI 跑完 turn 仍然开着。** 等进程退出会永远等下去。完成检测靠文件里的 `task_complete`。代价是卡死从这一侧看不见，所以 TUI transport 有超时并带名字失败 —— mcp transport 故意没有。

4. **prompt 绝不经过 shell。** 通过 osascript 传参会让中文全变乱码，模型收到一堆替换字符。写文件，脚本里 `$(cat ...)` 读回来。

5. **默认推理强度是 `xhigh`。** 一句 "Reply with exactly: OK" 烧 2 万 token；两个设计 turn 十分钟跑不完。验证脚本传 `model_reasoning_effort="low"`。

6. **`cwd` 给大仓库，模型会先读几分钟代码。** 合理行为，但验证脚本该用空临时目录。

7. **默认参数会吃掉 `undefined`。** 测试里 `call(undefined)` 触发默认值，断言打在一个完全合法的输入上。

8. **node-pty 的 `spawn-helper` 装完没有执行位。** 1.1.0 的 prebuild 里它是 `-rw-r--r--`，表现是一句**不指明文件**的 `posix_spawnp failed`。修：`chmod +x node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper`。**要固化进安装步骤**，不知道这条能耗掉半天。

9. **`codex` 启动会弹阻塞式更新提示。**

   ```
   Update available! 0.144.4 -> 0.146.0
   1. Update now   2. Skip   3. Skip until next version
   Press enter to continue
   ```

   **二进制里没有关闭更新检查的配置键** —— 试过 `check_for_updates` / `update_check` / `auto_update` / `disable_update` / `skip_update` / `hide_update` / `upgrade_notice` / `CODEX_DISABLE*` 八个候选名，`strings` 全部 0 命中。**不要去找一个不存在的命令行开关。** 唯一规避是 TUI 那个持久化的 "Skip until next version"，按一次可顶到下个版本。

   用户决定：**人在面板前，按一下 Enter 无所谓。** 这个决定成立是因为面板 —— 在 Terminal.app 那条路上提示藏在可能被最小化的窗口里，StagePass 会静默等满超时；在面板里它就在眼前。**残留风险只剩「StagePass 无人值守跑 turn」一种场景。**

10. **【前置探针】✅ 2026-07-29 已验，绿。elicitation 选择器在 pty 里可用。**

    `pnpm probe:elicit` —— 机械判据（按一次 Down 再 Enter，落在 enum 第二项才算过），两次复现：选择器画得出、方向键选得动、回车提交，客户端回 `{"action":"accept","content":{"decision":"reject"}}`。**面板的地基是实的，路 B 可以建。**

    **但验出了一件会掐死整个产品的事：`-a never` 会让 Codex 自动 decline 掉 elicitation。** 同一个探针换成 `-a never`，选择器根本不画，秒回 `{"action":"decline"}` —— 而那个回复格式完全合法，和"人按了 Esc"（§4.2 第三种形状）长得一模一样，**失败是静默的**。§4.8 决定二原来那张"每个阶段都 `-a never`"的表因此是错的，已改（PRD §6.6）。

    过程里还踩了三个**探针自己的**坑，都不是 Codex 的问题，记下来免得重犯：
    - **MCP 子进程的 `cwd` 不是仓库。** 用 `process.cwd()` 解析路径会让插件起不来，症状只有一句 `connection closed: initialize response`。从 `import.meta.url` 解析。
    - **TUI 的文字不能用普通正则匹配。** 它用光标移动而不是空格排版，`Allow the X MCP server` 在字节流里是 `AllowtheXMCPserver`；而且 CSI 序列有中间字节（`ESC [ 0 SP q`），`[0-9;?]*[a-zA-Z]` 这种模式漏掉它。**先剥转义、再去掉全部空白，然后匹配。**
    - **别让模型当触发器。** 最早的探针要模型去调工具，六轮里四轮它根本没调，每轮十几分钟什么也没答出来。改成探针自带一个 MCP 服务端、在工具调用里直接发 elicitation，一轮几分钟且结果稳定。

    另：**`-a never` 也不覆盖 Codex 自己的 MCP 工具授权提示**（"Allow the X MCP server to run tool ...?"），那是另一道门，每个新工具第一次都会问。

11. **（历史，已解决）elicitation 选择器在 pty 里能不能用，曾经没验。**

    它是 L3 的命脉，**也是面板方案的地基 —— 这条不行，面板就白建了。** 不需要 StagePass、不需要面板：起一个最小的、声明 `elicitation` 能力的 MCP 服务端，在任意 pty 终端（例如 `brew install ttyd && ttyd -W codex`）里跑一次 `elicitation/create`，看选择器出不出来、方向键能不能选、回车能不能确认。与 §4.2 已做过的实测是同一个动作，只是换了终端宿主。**成本以分钟计。**
