# 第一部分 · 框架

## 一、2026-08-05 定的框架：bootstrap

用户当天定：**StagePass 是他以后所有项目的基座，以后的项目都从这里出来。**

### 1.1 由此作废的判断

- 采用率、star 数、「算不算 top 开源项目」—— **无关**。用户数 1 是设计，不是缺陷
- 「被平台吸收」这个风险 —— **反过来了**。Codex 自己长出闸门是好事，少维护一块
- 开源基建（CONTRIBUTING / SECURITY / 发布）—— **零收益，别做**

### 1.2 由此升级的判断

| | 原来 | 现在 |
|---|---|---|
| 每 Change 一个通宵 | 可以忍 | **致命** —— 收税的地基不是地基 |
| 没有 CI | 没外部贡献者，无所谓 | **必需** —— 地基静默坏掉，代价按未来项目数乘 |
| `handle()` 1464 行 | 技术债 | **地基裂缝** |
| `panel.js` 不过类型检查 | 一处盲区 | 同上，已经咬过两次 |
| 阶段序列写死 | YAGNI | **地基工程**（见 §4.5） |

> **核心判断：bootstrap 的质量标准比产品更高，不是更低。**
> 产品的缺陷是一次性的，地基的缺陷会乘以未来所有项目的数量。

### 1.3 一个新的硬要求：它必须自举

方法论的载体必须用这套方法论建成。两个理由：**可信度**（不用自己方法建的工具，
说服不了三年后的你）、**更实际的**（先在自己身上发现毛病，而不是在一个真项目上）。

**真正的自举里程碑**（编译器自举的那个测试）：

> **用 StagePass 跑一个 Change，产出 StagePass 自己的下一个改动。**

两个现在就挡着它的障碍：

1. **工作树是脏的** —— Build/Fix 要求干净树（同 §3.1·1）
2. **面板从同一棵树上跑着** —— Codex 在这个目录里改代码，而面板进程正在用这些代码。
   改到 `panel-server.ts` 就是给自己动手术。**worktree 能解，但这是这个里程碑独有的
   问题，之前没人想过。**

### 1.4 「从零造一个新项目」这条路从来没跑过

`Project` 有 `id / name / path`，注释写着「Codex 就跑在这个目录里」。
至今跑过的唯一一个 Change 是对着 `demo` —— **一个已经存在的仓库**。

**已经拆掉的雷**：派轮前会预检目录信任（`panel-server.ts:824`，不信任就报
`workspace_not_trusted`，不会静默等满 30 分钟）。

**没验过的是零状态本身**：空目录、`git init`、Build 要写出一整个项目而不是一个 delta、
以及报告类产物污染在新项目里会更严重（所有文件都是新的）。

> **工厂的第一个产品是「造一个新工厂」，而这条产线从没通过电。**

### 1.5 Bootstrap 的五个失败模式

**① 永远在改工厂，从不生产 ← 最常见的死法**

「改进基座」永远比「生产东西」更有理由，因为改进会乘以未来所有项目。
**这个逻辑是对的，问题是它永远成立。** 做工具的人最容易死在这里，而且死的时候
感觉良好，因为每一步都有充分理由。

**要一条机械判据挡它** —— 比如「每改一次基座，必须用它生产一个真东西」。跟别的信条
一样写成会红的东西，不靠自觉。**这是五条里唯一一条会让你在感觉良好的状态下把时间
全花掉的。**

**② 自举会放大错误，而你没有对照组**

方法论有缺陷，每个项目都继承。而你在里面，造不出反事实 —— 每个项目都会像在验证
这套方法，因为方法塑造了项目。
**缓解**：偶尔**故意**不用它做一个东西，当对照组。

**③ Codex 耦合的爆炸半径变大了一个量级**

2026-08-03 已经证明 Codex 会单方面改行为、推翻整套设计。原来的代价是「一块设计作废」，
现在是「波及所有项目」。
**缓解**：§4.4 那份行为契约 + 探针，从「值得做」变成「保险」。

**④ 不是所有项目都适合这条产线**

探索性实验、一次性脚本、给别人仓库提的 PR —— 强行走 12 阶段会让文档比代码还长。
**这是 §4.5「阶段序列必须可变」的真实理由：防止基座变成税。**

**⑤ 产出的项目绝不能依赖 StagePass 运行**

现在是安全的（产物是 markdown + git commit）。
**但模块图谱是第一个可能打破它的东西。**

> **判据：图谱必须是「能从代码重新生成的描述」，不是「代码之外必须维护的事实」。**
> 前者可以随时丢掉，后者丢了项目就残了。

### ⚠ 2026-08-05 晚 · 真机取证，**原诊断被推翻**

真要无人值守，要动的是**批量裁决 / 预授权**那类设计（还没设计），不是这个配置键。

**解药留着**（`default_tools_approval_mode="auto"` 无害且方向正确），但它的功劳

**3. ~~Plan 阶段可能真的需要超过 30 分钟~~ —— 2026-08-05 已修，但根因不是这个**

真相是 **`--turn-timeout` 只喂给了 transport 一个人**：job 自己的截止和租约 TTL
在 `panel-server.ts` 里写死 30 分钟，谁都不读那个参数。所以「把它调大」在改代码之前
**一点用都没有**。

**同一堵墙有两个名字**：三个都是 30 分钟时 transport 先喊，错误是
`codex_unavailable ... 1800000ms`；把 transport 推上去之后轮到 job 截止先喊，
错误变成 `deadline_reached`。看错误信息的人会以为是两个不同的毛病。

**租约也必须跟着** —— 它短于另外两个的话，收尸人会在一条**还在跑**的轮身上收尸：
库里说它死了、屏幕上 Codex 还在动。这是这个坑的第三个面，也是最难看出来的。

已改（未提交）：三个都取自 `options.turnTimeoutMs`。真机验过 `deadline_at` = 起跑
+180.0 分钟，而改之前是 +30.0。Build 第 3 轮跑了 **64 分钟**并成功落地 —— 那一轮在
改之前会死在第 30 分钟。

**13. ★ retry 之后「状态说在跑，其实没派出去」**（2026-08-05 实测）

```
questions.apply(retry)  →  Change 状态 = running     ✓ 发生了
runPhaseTurn            →  workspace_dirty，拒        ✗ 没有 job 被创建
```

**两步是分开的**：先改状态，再派发。派发被拒时状态**不回滚**。于是
`Build/running` 挂着、库里没有 running 的 job、没有活进程 —— 而面板显示它在工作。

而拒绝的理由写进 `stageNote`，被「进程已经结束了」覆盖（同 §3.2·5）——
**人根本看不见它拒了**。

### 4.1 没有应用层 —— 一个函数 1464 行

```

> **判据是 CHG-001 跑到 Review 报出来的东西是哪一类** —— 报具体缺陷就直接修、不动
> 地基；报结构性问题才把这一部分拿出来。
>
> **真要动手时，从 §5.9 进** —— §5.5 那条反馈链路建立在两样代码里还不存在的东西上。
> 先补地基，别先建上层。

## 五、设计

### 5.0 一句话

两张图，一条反馈链路。**微观图**（函数依赖）管「代码写得对不对」，**宏观图**（概念）
管「这个系统是不是这个系统」。架构不预言，从跑出来的代码里**观测**。

### 5.1 出发点，以及最强的那条证据

用户的原始诉求，原话：「纯让 AI one-shot 特别容易耦合」。要的是**防耦合**和
**review 方便**。后来追加了一条更难的：**怎么提升架构本身的合理性**。

**这套东西的弱版本已经在跑，而且有效。**

`src/architecture.test.ts` 里那张手写的 `LAYER` 表，加上「只能向下依赖」「没有无人
调用的导出」「一个概念一个名字」—— 本质上就是**一份模块级的图谱和它的护栏**。

```
45 个生产模块 · 137 条依赖边 · 183 个导出函数 · 0 个环 · 护栏全绿
```

对照同一份文件里记着的老树病历：一个 1232 行的 MCP App 零生产调用活了几个月；
`request_plan_changes` 有标签、有契约、有渲染，**没有任何表面能执行它**。

**同一批人、同一个模型、同一种工作方式，唯一的差别是有没有这套约束。**

所以「模块化能不能提升代码质量」手里已经有答案。这次要做的是把它
**从模块级推到函数级、从手写推到上游产出**。

### 5.2 它提升什么、不提升什么

**会大幅提升的：**

- **跨模块耦合** —— 结构性消除，不靠模型自觉（见 §5.4.1）
- **review 条目的具体程度** —— 从「这段写得不好」变成「这行在 x=0 时错」
- **改动的可预测性** —— 爆炸半径事前可知，现在是改完才知道

**不会提升的：**

- 单个模块内部的代码水平 —— 那还是模型的水平决定的
- 语义正确性 —— 每个模块都满足契约，拼起来照样能错
- 抽象层次混乱（一个模块既管业务规则又拼 SQL）—— 两张图都看不出来，只能靠 rubric 和人

> **一句话：它提升的是代码质量的下限和可见性，不是上限。**
> 而下限和可见性恰好就是痛点，所以它打中的是真问题。

### 5.3 四条拍板（2026-08-04 逐条问答确认）

1. **全流程**，不是只有 Build。TechSpec / TestPlan 起就产出图谱，Build / Fix / Review 消费。
2. **图谱是账本里的一等公民** —— 有表、有契约、面板能看见。不是产物文档里的一章。
3. **粒度：一个导出函数 = 一个文件 = 一个模块。派轮的单位是「模块组」。**

   两个不同的粒度，别混：
   - **模块 / 文件 / 图谱节点**是同一个东西 —— 一个导出函数。按现状 45 个文件会变成 183 个
   - **派轮和对抗的单位是一组模块**。理由：一模块一轮 = 183 次按按钮，会压垮
     「每对抗一轮我都要知情」那条判据
4. **图谱变更走对抗**：红方只能提变更请求 → 蓝方审 → 人在面板上按。图谱有版本。

### 5.4 两张图

|  | 宏观图 | 微观图 |
|---|---|---|
| **节点** | 概念（Change、Round、Gap、Rubric…） | 函数 |
| **边** | 概念关系 | 调用 / 导入 |
| **产出于** | Spec | TechSpec |
| **规模** | 20~30，**一屏看完** | 几百，**只能查不能看** |
| **主要读者** | 人 | AI（配料单） |
| **能判什么** | 概念有没有归宿、模块该不该存在 | 有没有环、爆炸半径、层违规 |
| **合理性靠什么保证** | **只能靠对抗和人** | **能机械判定** |

最后一行是硬的：**概念划得对不对没有客观答案，环有没有则有。**

由此定分工：**宏观图是被红蓝对抗的对象，微观图是被护栏检查的对象。**
这正好落在 StagePass 本来就擅长的事上 —— 它一直缺的是「让对抗有具体的东西可抓」。

#### 5.4.1 微观图：可见性是机关，不是副产品

派轮给模块组 G 时，喂进去的东西**由图确定性地算出来**：

```
G 里每个模块的完整契约（职责 + 接口 + 测试契约）
+ G 直接依赖的模块的【接口签名】—— 只给签名，不给实现
+ 谁依赖 G（所以它知道自己不能乱改签名）
+ 全局约束（分层规则、禁止环）
```

> **「只给签名不给实现」是防耦合的真正机关。**
> 看不见实现，就写不出依赖实现细节的代码。这比任何 rubric 都硬 ——
> 它不是概率上更不容易，是物理上做不到。

这也是**为什么粒度要细到「一个导出函数一个文件」**：文件是可见性的边界。
`domain/round.ts` 里有 13 个导出函数，派轮给其中一个时，模型要么看见整个文件
（那它就能顺手调另外 12 个），要么就得把文件切开。

**细粒度不是洁癖，是让这个机关生效的必要条件。**

#### 5.4.2 检索是图遍历，不是向量召回

一般讲 RAG 是「切块 → embedding → 按相似度召回 top-k」。**这里不该这么做。**

代码的依赖不是「相似的东西」，是**确定的东西** —— 模块 A 用 B 和 C，图上写着。
所以检索退化成图遍历，而这带来一个决定性的差别：

**向量召回不全，你不知道；图遍历不全，会红。**

配料单因此是可测的：给定图谱和一个模块组，喂进去的内容唯一确定，能写护栏、能回放。

#### 5.4.3 宏观图必须是另一个维度，不能是微观图的缩略版

**最容易做错的地方。** 如果宏观图是把函数聚合成模块、模块聚合成目录，那它没有新信息，
就是微观图打了个包 —— 对账永远是绿的，整套白做。

真正有用的宏观图，节点是**概念**：Change、Phase、Round、Turn、Gap、Rubric、Criterion、
Evidence、Gate、Binding、Blocker、Question……

边是**概念关系**：Round 属于 Phase；Gap 由 Round 产生；Criterion 判定 Gap；
Gate 消费 Gap 的状态。

**注意这张图里一个文件名都没有。** 这是它保持独立、也是它能发现问题的原因。

#### 5.4.4 全部价值在对账

三类对账，每类抓一种微观图抓不住的架构病。

**① 一个概念散落在几个模块 → 概念无归宿**

现成的实例就是 §3.3·9：Blocker 契约只有 `id/severity/title`，Review 要求的「文件和
位置」只能待在散文里。宏观图上 Blocker 显然该有「位置」这个属性，微观图上没有任何
模块存它。**这条对账会在 Build 之前直接报出来**，而现在是撞上了才发现。

**② 一个模块承载了几个概念 → 职责不单一**

`web/panel-server.ts` 2587 行，对账会显示它同时承载 Round、Gate、Rubric、Binding、
Question、Brief 六七个概念。**这是「该拆了」的机械判据，比「文件太长」准得多** ——
一个 2000 行只服务一个概念的文件没问题，一个 300 行服务五个概念的文件有问题。

**③ 宏观有关系、微观没依赖（或反过来）**

- **宏观有、微观无** = 关系没实现，或靠约定俗成维持。最危险，因为它看着好好的
- **微观有、宏观无** = 一条计划外的依赖，多半是抄近路

第 ③ 类抓的正是「AI 顺手调了不该调的」，但是在**概念层面** —— 比实现层面更根本。

#### 5.4.5 顺带：Spec ↔ TechSpec 第一次有了机械对账

宏观图属于 Spec（概念是需求层面的），微观图属于 TechSpec。于是两个阶段的衔接
从「靠模型读文档」变成「两张图比对」：

> 「你的技术方案漏了 Spec 里的三个概念。」

这句话现在没人说得出来。它也补上了 §5.2 那个空缺 ——
**每个模块必须能说出它服务于哪个概念，说不出来的就是没有存在理由的模块。**

### 5.5 反馈链路

用户 2026-08-04 定的形状，原话：

> 「先设计架构（不要那么细），先迭代一轮先把功能跑出来（需要先用系统跑出来确保
> 不会错的太离谱），然后根据 build 或者 review 的反馈来不断修正架构，也就是做成反馈。」

以及主次：**「模块的问题需要先改进去，架构可以慢调。」**

#### 5.5.1 为什么不能一开始就定细

细架构定错的代价**大于**不定架构。因为契约是权威，模型不会质疑它 ——
它会**为了满足一个错的契约写出扭曲的代码**：塞适配层、加兜底、绕着走。
粗架构留了余地，定错的代价小得多。

**这条是用户自己提的，它解掉了这套思路里唯一可能让质量变差的机制。**

#### 5.5.2 快环 / 慢环，以及那条机械分界线

| | 内容 | 频率 | 可逆性 |
|---|---|---|---|
| **快环** | 模块级问题 | 立刻修 | 可逆、局部（重写一个文件） |
| **慢环** | 架构调整 | 批量、低频 | 不可逆、全局 |

先做可逆的、把不可逆的往后推 —— 信息不足时的正确策略。而且**每修一个模块，架构
信息就多一点**，所以慢调不是妥协，是在攒证据。

但有一类模块问题的根源就是架构。需要一条不靠判断力的分界线：

> **修一个模块时，如果它需要新增一条图上没有的依赖边 —— 那就不是模块问题，
> 是架构问题。立刻停手，攒进架构那一批。**
>
> **只改模块内部、不动任何边的，全是模块问题，随便修。**

这条正好接上 §5.3 的第 4 条：想加边 → 提变更请求 → 攒着 → 批量判。

#### 5.5.3 反馈的信号源必须是代码本身，不是 Review 的意见

**这是整条链路最要紧的一条。**

粗架构 → 粗反馈 → 粗修正会锁死在粗的层面。破法是：**从跑出来的真实代码解析出真实
依赖图，和架构图比对 —— 差异本身就是最细的反馈。**

> 模型的意见是主观的、会漏、会讨好；真实依赖图是客观的、不会漏。
> 「你的架构说 A 不该依赖 D，但代码里 A 调了 D 三次」—— 这句话不需要任何判断力。

这也说明**对账不能一直搁置**（§5.10）：它不只是护栏，**它是反馈链路的信号源**。
没有它，这个闭环没有输入。

#### 5.5.4 第一轮的完成判据

「确保不会错得太离谱」没法执行 —— 谁定义离谱。换成机械的：

> **第一轮的目标不是「功能对」，是「把所有概念都摸到一遍」** ——
> 宏观图上每个概念，都要有代码真的碰过它。

碰过了才有资格说这个概念的边界在哪；没碰过的概念，边界纯属想象。

#### 5.5.5 收敛判据

实测：四个阶段每轮开 2~8 条，**没有一个真正收敛**，全靠人 waive 才过闸门。
架构反馈会一模一样。所以提前定停止条件：

> **连续两轮 Build 没有产生新的「计划外依赖」**（真实依赖图 vs 架构图，对账无新增
> 差异）→ 架构算定了。

机械的，而且它真的意味着边界不再被踩了 —— 比「模型说没问题了」可信。

#### 5.5.6 慢环需要节拍，不只是优先级

架构债和技术债的区别：技术债有人还，架构债没人还 —— 收益在未来，代价在现在。
慢环只有优先级（「以后再说」）而没有节拍，会自然衰减成不调。

**建议：每批模块 Build 完必须过一轮架构复审。** 选阶段触发而不是数量触发，因为它和
已有的阶段边界重合，不用新增一种节奏，而且那个时点人正好在看这批的结果。

### 5.6 为什么模块化能减少震荡（可验证的预测）

震荡的三条成因，模块化解掉两条：

**① 文档是连续的，改动会扩散。** 改一处文字就产生新的可挑剔表面。
**模块是离散的** —— 改一个模块只碰一个文件，不生成新表面。

**② 每轮的蓝方是新的，它挑出的是「不同的」问题而不是「剩下的」问题。**
新一轮蓝方读同一份 26000 字文档，注意到的是别的地方。模块级不会这样：
**一个 40 行的模块，可挑的表面小到能被穷尽。**

**③ 不解决的那条：「这个模块写得够不够好」仍然主观**，而且模块多了，主观判断的
次数变多了。救赎是单次判断便宜得多也准得多。

> **可验证的预测（跑起来第一件要看的）：**
> 模块级的开条数应该在两三轮内掉到 0~1。
> **如果还在 2~8 震荡，说明 §5.6 的推理错了**，这一部分的收益估计要整体下调。

⚠ **注意范围**：这个预测只到模块级。**模块图谱不会让 Spec 少震荡一轮** ——
Spec 是散文，连续性问题跟代码怎么组织无关。设计阶段的震荡只有 §5.4.3 的宏观图
能减，而且它短期会**增加**条目（新表面），收益要到第二、三轮才显现。

### 5.7 实测数字（2026-08-04，从 `src/` 真解析）

```
45 模块 · 137 依赖边 · 183 导出函数 · 0 个环 · 平均爆炸半径 5.0
```

- **爆炸半径分布极不均**：`domain/phase.ts` 波及 30 个（全树 2/3），多数模块只 0~2 个
- `web/panel-server.ts` **依赖闭包 41** —— 够得着全树 91%
- 上游产物全量 123 KB（PRD r4 + Spec r5 + Plan r2 + TestPlan r4）→ 单模块配料单约 1.7 KB

**关于最后一条要说准。** 用户明确说过「token 我不在乎」，所以 72 倍这个数字**不是卖点**。
它的意义只有一个事实：

> **现在一轮里，跟当前模块无关的内容占 98.6%。**

模型要自己在 123 KB 里找出该看的 1.7 KB，而找错的代价不是慢 ——
**是它会去调不该调的东西，因为它看见了。**

可视化（真数据的地层剖面图，点模块看配料单）：
`https://claude.ai/code/artifact/ffe8050d-6274-4944-99ed-94cd769c4f1d`

### 5.8 风险清单

按严重程度排，前三条会让整套白做。

1. **两张图互相污染。** 宏观图一旦是从代码归纳出来的，就退化成微观图的摘要，
   对账永远绿。**必须先有宏观图，或者由不同轮次独立产出。** 很容易被违反。
2. **反馈链路死在「没人真的改架构」。** 跑完一轮报了问题然后没人动 —— 因为改架构要
   重写已经能跑的代码，而代码能跑。**解药是强制消费点**：这一轮的架构反馈没被处置，
   下一轮不许开。
3. **「先跑出来」的沉没成本会污染架构判断。** 功能一旦跑通，「这个边界划得不对」会
   变成「但它能跑啊」。**解药是提前立心理契约**：第一轮的产物明确标成一次性的
   （不是「MVP」——MVP 的潜台词是留着改）。**事后立不住。**
4. **架构反馈摊给人的频率不能等于对抗轮次。** 注意力上限已经量出来了（18 次按钮、
   一个通宵）。一次改一条边界比一次看完五条更糟，因为它们互相影响。
   **知情是每轮的，决策是批量的。**
5. **概念数量必须控制在一屏。** 超过 30 个人就看不动。反过来说，**放不进一屏本身
   就是信号**：系统太大了，该拆成两个。
6. **概念划分本身是主观的**，所以宏观图不能像护栏那样判红。
   **对账可以机械做，画图不能。**
7. **给 AI 的树只能是单模块配料单，绝不能是全图。** 喂全图等于把 98.6% 的无关内容
   塞回去。这个反射很强（「让它更懂全局」听起来总是对的），容易做反。

### 5.9 这条链路缺的地基

> **§5.5 整条反馈链路，建立在两样现在不存在的东西上。** **动手时这一节是入口。**

#### 5.9.1 ~~长回边不存在~~ —— **2026-08-05 晚已做**

新动作 `sendBack(to)`：settled 可用，目标必须在**严格上游**（按这个 Change 的图）；
P0 一样的产品规则在域层守着（目标不合法 = `SendBackTargetError`，PRD/Fix 压根不
合法）。裁决表里是「打回上游（哪一份文档错了，上面那格选）」+ 目标格 `T`（标签
静态、名单动态，各归各格）+ 第二趟理由 `Tx` → 账本 `reason`。
「打回去修」（代码错，送 Fix）和「打回上游」（文档错，回设计阶段）是两个选项。

三种边的现状：自环 —— `jumpsFrom` 里第一次可见（`kind: "self"`）；短回边 ——
和长回边**统一成一个栈**；长回边 —— 有了。

**还没做的一半（下一趟的活）**：打回理由现在只进账本 —— **目标阶段的下一轮
提示词还读不到它**。§5.5 的反馈链路要闭合，得把「Build 为什么把你打回来」送到
Spec 红方眼前（走名单文件那条路，2026-08-02 四张脸的教训：原文 + 收件人）。

#### 5.9.2 ~~`returnPhase` 存不下嵌套回跳~~ —— **2026-08-05 晚已做**

`returnStack`（栈，`domain/change-state.ts`）：打回和送修共用同一个机制，approve
弹栈回去而不是沿主线走。不变量钉死：自底向顶严格递减、每层在当前阶段严格下游、
Fix 栈非空且顶是 Review/QA、closed 栈空。库里 `return_stack` JSON 列 ——
**这棵树第一次正经写表重建迁移**（旧 CHECK 绑死 return_phase，SQLite 改不了约束；
老库 `'Review'` → `'["Review"]'` 无损，触发器当场重建，migrate 注释预告过的那一天）。

跳转表**没有建表**：`domain/journey.ts` 的 `jumpsFrom(ledger)` 投影出
`从哪 · 去哪 · 方向(forward/backward/self) · 理由 · 哪一轮`，`/api/panel` 的
`journey` 字段带出去 —— **G 档画历史箭头只许读这一份**（两份不一样的结构就是
从第二份开始的）。真机验过：CHG-001 的 74 行账本投出 19 跳，TestPlan 自环 3 次、
Build 自环 3 次 —— §5.9.4 说的「环在撒谎」第一次机器可读。

#### 5.9.3 UI：环从「路径」变成「地图」

用户 2026-08-04 原话：

> 「环的形状还是要的，只是不能暗示用户下个阶段一定是这个，可以用箭头指示，
> 不管是向前还是跳转到别的阶段。」

解耦是：**位置说「有哪些阶段」（稳定，肌肉记忆），箭头说「从这里能去哪」（可变）。**

**① 箭头表达「可去」，不是「要去」。** 只画一条指向下一步，就是把预言从环的顺序换成
一条箭头。要复数，每条带理由：

```
批准      → Spec        （闸门放行）
再来一轮   → 自己          （还有 3 条没清）
打回      → TechSpec     （Build 报了架构问题）
```

跟「一切都是由我来决定」对上：**UI 摆选项，不摆结论。**

**② 历史的箭头和可选的箭头必须是两种画法。** 走过的用实线、**永久留着**
（这是 Change 的病历，一眼看出「被 Build 打回来过两次」）；能去的用虚线，随状态变。

**③ 活箭头要有硬上限。** 任一时刻实际可去的只有：批准 → 下一阶段、再来一轮 → 自己、
打回 → 某个上游、（Review/QA 才有）→ Fix。
**最多 4 条，建议写进护栏**，否则以后加功能时会悄悄涨到 8 条。
**自环别忘了画** —— 它是频率最高的那条边，现在完全隐形。

**④ 让形状本身带语义。** **沿着环走 = 正常推进；穿过中心画成弦 = 回头。**
回边罕见且重要，值得这个视觉强调，而且天然不会和向前的边缠在一起。

#### 5.9.4 环现在撒的谎（有实测）

```
PRD       每轮开条  5 · 4 · 4 · 5   →  跑了 4 轮才批准
Spec                6 · 6 · 5       →  3 轮
TechSpec            8 · 2 · 4 · 4   →  4 轮
```

**真实形状不是 12 个节点的环，是 12 个各自带自环的节点。** 每个节点上花的轮数（3~4）
比它在环上的位置（1/12）更能说明「你在哪」。

**最小改动**：节点画成带刻度的圆（跑了几轮就几段），而不是一个点。
环表达总进度，节点表达局部反复 —— 也不违反 `panel.js` 开头那条「环那一屏什么都不加」，
因为这不是加东西，是把节点本身画准。

### 5.10 明确搁置，没有答案

- **图谱和真实代码怎么对账。** 用户当天说「先不涉及，只讨论思路」。
  但 §5.5.3 说明它不能一直搁置 —— **它是反馈链路的信号源**。
  真做的时候要上真解析器（本次量数据用的正则只够量结构，不够当护栏）。
- **图谱的表结构、契约字段。** 没定。
- **图谱在面板上怎么呈现。** 没定 —— 注意 §5.9.3 定的是**阶段环**的形状，
  跟图谱怎么画是两件事，别混。

# 第四部分 · 结论

## 六、这次更正的判断（别再重推）

| 原判 | 更正 | 依据 |
|---|---|---|
| 不能离线跑完一整轮 | **能，已经有了** | `ScriptedCodexTransport` + 4 个测试文件在用 |
| 阶段序列可变是 YAGNI | **是地基工程** | bootstrap 框架 |
| CI 零收益 | **必需** | 同上 |
| 开源基建值得补 | **零收益，别做** | 同上 |
| 模块化能减少震荡 | **只减模块级的**，不减 Spec 的 | §5.6 末尾 |

## 七、建议的顺序

1. **查许可门根因**（半天，只读）← 它决定整个验证策略往哪边靠
2. 修成本：许可门 + §2.2 尸体日志 + §2.3 进度条
3. **把 CHG-001 推到 Review** —— 一个闭环从没合上过的东西还不能叫 bootstrap
4. 补 CI（§4.6）
5. **用 StagePass 造一个最小的新项目**（哪怕是个 hello world CLI），跑通零状态那条路
   —— **工厂的价值取决于能不能生产新东西，不是能不能改老东西**
6. 再看第三部分（判据是第 3 步 Review 的产出）

**在第 3 步之前不要做**：模块图谱、`handle()` 重构、事件流、开源基建。
**注意力是唯一真正稀缺的资源，而它已经被量化过了**（18 次按钮、一个通宵）。

**还要立一条**（§1.5·①）：**每改一次基座，必须用它生产一个真东西。**
否则会永远在磨刀。
