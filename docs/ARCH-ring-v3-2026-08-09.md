# ARCH：环 v3 的技术架构

> 状态:2026-08-09,依 `PLAN-2026-08-09-ring-v3.md` §一的八条拍板。
> 粒度到文件与函数。批次边界见 PLAN §二,本文按模块说清每处为什么这么动。

## 一、这次动哪几个模块

`domain`(环的定义与状态机,承重的全部)、`work`(轮的执行与 commit 语义)、
`db`(CHECK 约束与迁移)、`store`(座位/worklist 的并行修复)、`web`(环 UI、
自由终端)、`codex`(turn-runner 只跟着 CONSUMES 的投递变,不动契约)。

## 二、文件与函数清单

### domain/phase.ts(批 1)

- `PHASES`:增 `"BuildPlan"`(排在退休的 `Plan` 后)、`"Test"`(排在 `Build` 后)。
  全集 15 名,主线 8 名。
- `RETIRED_PHASES`:`{TechSpec, Plan, Review, Fix, Merge, Retro, Done}`。
- `DEFAULT_GRAPH`:filter 只剩 `!isRetired` —— `phase !== "Fix"` 特判死掉,
  Fix 现在就是普通的退休阶段。
- `TERMINAL_PHASE = "QA"`。`FIRST_PHASE` 不动。
- `phaseGraphOf`:错误码 `fix_not_on_the_line` 删(`retired_phase` 覆盖);
  `must_end_with_done` 改名 `must_end_with_terminal`(名字要说真话)。
- `advancesTo`:`Fix` 特判删 —— 不在图上就抛 `unknown_phase`,没有调用方再拿
  Fix 来问(change-state 的 Fix 机械同批拆除)。
- `CONSUMES` 定稿(PLAN §一那张表);退休行保留给历史:`TechSpec:[Arch]`、
  `Plan:[Arch]`、`Review:[Build]`、`Fix:[]`、`Merge:[QA]`、`Retro:[Merge]`、
  `Done:[Retro]`。那段「四行没验证过」的注释换成这次的推导。
- `SENDS_TO_FIX` / `sendsToFix`:**删除导出**。调用方:change-state.ts(同批拆)、
  question.ts(打回选项,改读 `upstreamOf`)。
- `RED_REVIEWS_OTHERS = {QA}`:Review 行死;Test 的红方写测试是自己的作品,自审
  不算,不进名单。
- `PRODUCES_COMMIT = {Build, Test}`:Fix 退休、TestPlan 收窄成纯文档。
  「整树提交 = 要求干净树」那条等式在批 4 拆成两半:整树的只剩 Build,
  Test 走声明落点的窄提交(见 §七·代价)。

### domain/change-state.ts(批 1)

- `CHANGE_ACTIONS`:**删 `"rerun"`**。它存在的全部理由是「Review/QA 的 reject
  被送修(→Fix)占用了,原地再来一轮没有自己的动作」;Fix 退休后 reject 在
  所有阶段恢复「就在这儿再来一轮」的本义,rerun 变成 reject 的第二个名字 ——
  两条路一个意思,是这棵树一直在删的东西。
- `ACCEPTS.settled`:去掉 rerun。
- `isLegal`:rerun 分支删;sendBack 分支不动。
- `transition`:
  - `reject` 收敛成一行 `{ ...state, status: "pending" }` —— sendsToFix 分支删。
    QA 的「代码错了」走 `sendBack`(三向归因,人选目标,清单 = `upstreamOf(QA)`
    = Build / Test / … 传递上去)。
  - `rerun` case 删。
- `assertStateValid`:Fix 专属分支(栈非空、栈顶必须 Review/QA)删 —— Fix 变成
  普通退休阶段,通用那句「`${entry} is not on the line`」接管。closed 校验随
  `TERMINAL_PHASE` 自动指向 QA。
- `IllegalTransitionError`:报错文案里的 Fix / rerun 措辞清掉。
- `approvalTargets` / `recommendedApproval`:逻辑不动(它们只依赖 `advancesTo`
  和栈);Fix 特例的注释改写。

### domain/journey.ts(批 1 跟随、批 7 画钻石)

投影读 `graph.order`,八阶段自动跟上。批 1 只保证测试与注释同步;
并排画 BuildPlan∥TestPlan、Build∥Test 与「打回箭头 = Fix 交互」是批 7。

### domain/phase-play.ts、phase-template.ts、rubric-defaults.ts(批 1 最小 + 批 2 定稿)

三个都是按 `Phase` 全键的 Record —— **加阶段名的同一批必须给出条目,类型上
分不开**。批 1:`BuildPlan` 整体继承 `Plan` 的现有条目;`Test` 给最小可跑的
模板(测试代码 + 落点声明两节);退休阶段条目原样留着给历史。批 2 定稿:
TestPlan 模板去掉代码节收窄成纯文档;QA 剧本重写(案卷输入、读/跑/变、
三向归因);全部措辞逐条过,`dump-rubrics` 再生成。

### work/round-turn-runner.ts(批 3)

- 上游文档投递:已读 `upstreamOf`,CONSUMES 一换自动跟上 —— 验证点是
  Build 的任务书里**不得**出现 TestPlan 的产物(互盲)。
- commit 语义:`producesCommit` 名单变化即刻生效 —— TestPlan 落回
  `commitPaths`(纯文档),Build/Test 暂同走 `commitAll`(串行下安全),
  批 4 再把 Test 换成声明落点的窄提交并给 Build 加挡门。

### db/schema.ts(批 3)

CHECK 约束里的阶段名单扩容。**迁移先、SCHEMA_SQL 后,封在 prepareSchema 里**
(建表顺序陷阱)。照 Arch 阶段入库时的迁移先例走 —— SQLite 的 CHECK 不可
ALTER,该重建的表按那次的模式重建。活库现状:CHG-001 在 `Arch/settled`、
`returnStack:["Build"]` —— v3 全序里两者都在,原样合法,不需要搬家。
**迁移前置检查**:若有活 Change 停在本批退休的阶段上,迁移拒绝执行、报人
(这次已核:没有)。

### store/parallel-store.ts、worklist-store.ts(批 4)

批 3 撤回时审计的 5 条 P0 逐条修(worklist 按 (Change, 阶段) 分队列、孤儿
座位、blocked 座位出口、sendBack 不收编 settled 座位、closed 不开座位)。
分叉/合流调度:Arch 过门开 BuildPlan+TestPlan 两座位;Build、Test 都过门
才开 QA。

### web/panel-server.ts、panel-view.ts(批 6、7)

Arch 编辑过门(brief 机制复用:产物无人编辑不许 settle);环的钻石画法;
打回箭头(Fix 交互);closed 后的自由终端挂载(只读原则:看状态不起进程)。

## 三、数据怎么存、状态怎么迁移

- 阶段名单只加不改:历史行的名字永不改写,退休名单负责语义。
- `rerun` 从动作枚举里删:**历史命令行若存过 `rerun`,读路径不得抛**
  ——批 3 核 command-store 的读侧是否校验动作枚举,是则给历史值放行
  (读旧值合法,写新值非法 —— 和退休阶段同一个形状)。
- `closed` 的含义从「Done 批准」变成「QA 批准」:纯派生,无存量迁移
  (活库没有 closed 的 Change)。

## 四、接口与契约

- 案卷(批 5):固定 schema,StagePass 从库装订 —— Arch 契约节、BuildPlan、
  TestPlan、Build/Test 的 commit id(库取,手抄禁令)与报告、怎么跑。
  模型不写案卷;附导读可以,导读断言一律不算数。
- QA 的 sendBack 选项即 `upstreamOf("QA")`,升级到 Arch = 共模归因,过人。
- 两轨互盲是投递契约:Build 的题面不含 TestPlan/Test 的任何产物,反之亦然
  ——批 3 加测试钉死(打真实症状:查任务书文本,不查哪个函数)。

## 五、新增了哪些依赖边

零。全部改动都在既有依赖边内(domain 内部、work→domain、db 独立、
web→store→domain)。这也是「并行走座位不走 DAG」的红利:图的地基没有新边。

## 六、边界划在哪

- **全序 vs 并行**:主线保持全序(sendBack/栈序/子序列判定的地基),并行
  只存在于座位层。图上不长岔路。
- **闸门 vs 消费**:QA 的绿是 merge 动作的守卫(pre-push 印章),不进
  CONSUMES。
- **阶段 vs 交互**:Fix 是交互(打回箭头 + 重开座位),Merge/Retro/Done 是
  动作/状态/派生,都不占站位。入场券判据:有产物可对抗。

## 七、想过但没选的划法,和选了的代价

- **DAG 图**:没选 —— 「上游」和长回边整个建在全序上,DAG 让 upstreamOf
  说不清先后。代价:环 UI 要自己把全序**画**成钻石(投影问题,不是结构问题)。
- **rename Plan→BuildPlan**:没选 —— 历史行读不出来,CHECK 违约。代价:
  PHASES 里躺着七个退休名,读代码的人要靠退休名单分辨死活(注释承担)。
- **保留 rerun 作为 reject 的别名**:没选 —— 两条路一个意思。代价:历史
  命令行的 rerun 值要读侧放行(§三)。
- **Test 并进 TestPlan(维持现状)**:没选 —— 文档和 commit 混在一个阶段,
  正是工作区冲突的根源;拆开后每轨「先文档后代码」对称,案 B 变干净。
  代价:批 1~3 之间 Test 阶段是「在图上但跑不了真轮」的过渡态
  (模板最小、runner 未接落点声明),落地前不得对活 Change 派 Test 轮 ——
  过渡期由「活库只有 CHG-001 且停在 Arch」兜底。

## 八、最可能出错的一处

`change-state.ts` 拆 Fix/rerun 时的**测试连带面**:栈序校验、approvalTargets
的上界、§8.9 重走语义的测试全都拿 Fix/Review/Plan 当例子写。改例子要打真实
症状(状态机的可观察行为),不是替换字符串 —— 「同一规则两份拷贝」和
「测试打你改的函数」两条老坑都埋在这儿。次险:schema CHECK 迁移(批 3),
有 Arch 先例但要复验先例真的重建了表而不是只对新库生效。
