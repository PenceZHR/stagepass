> 接 `HANDOFF-2026-08-18c-migration.md`。那份记的是「迁进 Codex 插件」；
> 这一份记的是**那条路为什么走不通、以及退到哪里**。

## 一、一句话状态

**产品现在是一个本地 http server，在浏览器里开。MCP 插件那一层整个删了。**

```bash
npm start                        # 当前仓库
npm start -- ~/Desktop/某项目     # 别的仓库
# 然后开 http://127.0.0.1:4399/
```

开在哪都行：Codex 的 in-app browser（它自带、官方说明就是「给本地开发页面用」）、
Claude Code 的 Browser pane、普通浏览器。**只有第一次开需要经过模型**，之后它就是
一个真网页 —— 宿主重画不影响它、F5 能恢复、有 DevTools、没有 CSP 沙箱。

`pnpm check` 1177 全绿。树上只有一个产品出口：`scripts/stagepass.ts`。

## 二、两次转向，和逼出它们的证据

### 2.1 插件不能承重（08-18 深夜 → 08-19 凌晨）

一夜六种失败，**根子全在 widget 那层实验性的壳**：

| 撞到的 | 真相 |
|---|---|
| 「怎么改都是同一个报错」 | 六个独立原因共用一句话，每修一个还剩五个 |
| 装完的插件起不来 | `ws` 是 CJS，打进 ESM 就抛 —— **三次构建从来没启动成功过** |
| 修好的代码被换掉 | marketplace 源指着一条**已结束会话的 /tmp scratchpad**，缓存刷新把当晚全部修复盖成早上的实验探针 |
| 握手超时 | 模板装在版本目录**旁边**，缓存刷新只物化插件包自己 |
| 「我没关掉怎么点不动」 | 卡片不是窗口，宿主重渲染就断 |
| 每次都要开新窗口 | MCP server 按会话起，一台机器上三个进程各锁着不同版本的代码 |

**用户的结论**：「MCP 的路子彻底堵死了」。

### 2.2 StagePass 不该自己跑轮（08-19 凌晨，最后一次转向）

退到浏览器之后，还剩最后一堵墙：**在 Codex 里打不开 StagePass 跑的那条会话**
（"This is open in another app"）。

我先判成「订阅造成的」，做了「派完就退订」—— **那个判断是错的**。真相：

> **谁执行 turn，谁就占着那条线程。** 退订解决的是「订阅」，解决不了「执行」。
> 跑那一轮的是工作台起的 `codex app-server` 子进程，所以 App 打不开它。

我拿一次「没有 turn 在跑时退订能 attach」的实验下了结论，还照它改了代码、让用户去验。
**同一个错误当晚犯了两遍**（第二遍是 `thread/inject_items`：协议层接受了，但题面
没进 rollout）。

**用户的定案（甲）**：StagePass 只给题面，人在自己的会话里跑 —— 那一轮从第一秒起
就是他的：看得见、点得开、审批弹给他、进程死了也不关它事。

## 三、树现在长什么样

```
scripts/stagepass.ts   进程边界：绑项目、收尸、拆请求、喂静态文件
src/web/serve.ts       请求边界：method+path+body → JSON。**只做分发**
src/web/bind-project.ts 绑在起它的那个仓库上；默认看第一条 Change
src/web/api.ts         只读的数据口（GET）
src/web/actions.ts     会改库的路（POST）
src/web/runtime.ts     执行通道（还在，见 §五）
src/web/panel.js/html  界面，浏览器直接吃
```

`src/plugin/` 整个没了 —— 剩下的模块全搬进 `src/web/`（目录名成了谎话）。
删掉的还有：`ws` 依赖、daemon、websocket、`codex/trust`、`web/session-recovery`、
`app/draft-questions`。

**不照着「零入边」删** —— 08-18 那次教训（零入边只是因为唯一的调用者被删了）。
这次用树自己的工具取证：把入口换成 `scripts/stagepass.ts` 算依赖闭包，89 个产品
模块里够不着的只有 7 个，逐个判过才删。

## 四、三条现在立着的规矩

- **项目必须先是 git 仓库。** Codex 按仓库认 project（`isGitRepository`）——
  不是仓库的目录在它那儿根本不是项目，StagePass 开出来的会话**无处显示**
  （用户为此跑满 47 分钟去找一条线程，扑空）。拦在建项目那一步，不是派轮那一步。
- **工作台绑一个项目。** 起在哪就绑哪，没有项目选择器、没有 `?project=`。
  于是「认不出来就编一个」那条路**在结构上不存在**（面包屑写着库里没有的 `CHG-1`
  就是它造成的）。
- **起来先收尸。** 上一个工作台被杀时手上那轮会留在账本里当 `running`，于是这个
  阶段永远派不动（`phase_already_running`），人看到的是「按钮坏了」。判据是租约。

## 五、下一步：把「取题面」接完（甲那条路只差两段）

已经落地的地基：

```
prepareRound         （round-runner）开名单、落 gap 文件、写题面文件 → 交出信封，**不派**
prepareRubricRound   （rubric-round）组装同一份请求 → 调它
```

备和跑**共用同一份请求组装** —— 两份必然分叉，而分叉的表现是「人手跑的那一轮和
StagePass 记的账对不上」，那种错要到结算才发作。

### 5.1 还差的两段

1. **工作台的口子**：`POST /api/handoff` → 把信封给人（按钮 + 可复制）。纯接线。
2. **结算**：人跑完点一下，StagePass 认回那条线程、读红蓝、落账。
   要把 `runRound` 里「派完之后」那半截也切出来，比前两刀都大。

### 5.2 认回线程的判据（**这一节 2026-08-19 晚被真机推翻并改正了**）

> 原文写的是「每条带 cwd 和 `title`，而 `title` 就是第一条用户消息，按
> **(项目目录, 标题)** 就能认回」，并且标着「已实测，别再重验」。
> **两处都是错的**，而且第二处会让结算收错线程。真机纠正如下。

```
thread/list 的一条记录没有 title 这个字段。键是：
  id, parentThreadId, preview, cwd, name, turns, source, updatedAt, …
preview  =  第一条用户消息的**全文**，不截断（实测最长一条 360656 字符）
name     =  模型生成的摘要标题；StagePass 开的线程上它是 null，指望不上
```

所以判据是 **(项目目录, `preview` 里含题面路径)** —— 题面路径每轮一个随机临时
目录，全局唯一，而它就在人原样粘贴的那段信封里。仍然**不用人手抄 id**。

**还差一半：子 Agent 要滤掉。** 裁判会把信封**原样转达**给它派生的正反两方（题面
就是这么要求它的），于是那两条子线程的 `preview` 和裁判那条**逐字节相同** ——
按正文根本分不开。真机上一个 marker 认回 3 条，而第二个 marker 排在最前面的是
红方那条子线程。收错的后果：拿子 Agent 当裁判去数它的孩子，一个都没有，整轮报
`round_agents_not_found`，而人看到的是「我明明跑完了」。

判据是**血缘**：人自己开的那条 `parentThreadId` 是 null，子 Agent 一定有。
（不拿 `sourceKinds` 滤 —— 那是一张会变的枚举表，「有没有父亲」才是这件事本身。）

`thread/search` 更直接，但要 `experimentalApi` 能力，走不通。

### 5.3 执行通道（`runtime` / `seats` / `await-turn`）留着没删

甲那条路成立之后它就该退休。**先别急着删** —— 「取题面 + 结算」跑通之前，它是唯一
能把一轮跑完的路。等 §5.1 两段都通了，再照 §三 那个取证办法删。

## 六、会咬人的实测结论（这一夜新增）

- **谁执行 turn，谁就占着线程。** 订阅和执行是两件事；退订换不来「人能打开它」。
- **零轮次线程连 `threads` 表都不进**，`thread/resume` 必拒（`no rollout found`）。
  所以次序只能是「开线程 → 立刻发第一轮 → 跑完 → 才有人点得开」。
- **`thread not loaded` ≠ 线程不存在。** 让出订阅权之后线程会被卸载，读之前要先
  借回来（resume → read → **unsubscribe**，放掉写在 `finally` 里）。
- **App 认项目在启动时。** 新 `git init` 的目录要它重新认一次（重启或打开一次那个
  文件夹）；**之后新 session 是实时出现的，不用再重启。**
- **Codex 的 hooks 是实验特性**：`~/.codex/hooks.json`（不带子目录），要
  `[features] codex_hooks = true`，只处理 `PreToolUse` / `PermissionRequest`，
  而且条目上还有 `trustStatus`。`hooks/list` 是诊断口 —— 别再靠跑一轮看日志猜。
- **widget 的 `callTool` 圈死在自己 server 里**：`codex_app__*`（Desktop 的任务 API）
  跨不过去，插件进程也够不着那条私有管道。三条门全关。

## 七、我这一夜犯的两类错（下一个人别再犯）

1. **拿不完整的实验下定论，然后照它改代码、再让用户去验。** 犯了两遍（退订、
   `inject_items`）。用户的原话：「你能不能都搞好了再让我验证？」
   —— 交之前自己把每条路走完。构建绿灯、测试全绿，都不等于人点下去有反应。
2. **同一句报错底下有六个不同的原因时，每修一个就说「再试一次」。** 从用户的位置
   看，那就是「怎么改都不对」。

这一夜留下的两道护栏正是这两类错的产物：**构建启动冒烟**（起真进程、送真消息、
答不上就红着退出）和**「界面说得出名字的按钮都真的存在」**（它当场抓出了「面板叫人
按一个不存在的按钮」）。
