## 一、今天修了什么（四项，每一项都有真机证据）

### 1. 三个截止时间统一 —— 今天丢掉的 6 轮全因为这个

`--turn-timeout` **只喂给了 transport 一个人**。job 自己的截止和租约 TTL 在
`panel-server.ts` 里写死 30 分钟，谁都不读那个参数。

于是 `--turn-timeout 180` **一点用都没有**：21:25 起跑的那轮 21:55 整死于
`deadline_reached`，transport 那边还剩 150 分钟没用上。

**更坏的是它换了个名字**：三个都是 30 分钟时，transport 先喊，错误是
`codex_unavailable ... 1800000ms`；把 transport 推上去之后，轮到 job 截止先喊，
错误变成 `deadline_reached`。**同一堵墙，两个名字**，而看错误信息的人会以为是两个
不同的毛病 —— 我自己就先后诊断错了两次。

**真机证据**（同一张表里前后对照）：

```
job 021495（改后）  起跑 02:47:01  截止 05:47:01  相差 180.0 分钟  租约 05:47:01
job 128995（改前）  起跑 01:25:28  截止 01:55:28  相差  30.0 分钟
```

租约也必须跟着 —— 它短于另外两个的话，收尸人会在一条**还在跑**的轮身上收尸，
库里说它死了、屏幕上 Codex 还在动。**这是这个坑的第三个面，比前两个更难看出来。**

改完之后 Build 第 3 轮跑了 **64 分钟**并成功落地 —— 那一轮在改之前会死在第 30 分钟。

### 2. `panel.js` 的 `label` ReferenceError —— 「TUI 每次都卡住」

用户报的症状：「每次 codex 问完或者什么阶段我的 TUI 都会卡住，但明明没卡住是在跑的」。

根因是 `attach()` 里这一行：

```js
if (!reattaching && label === null) {   // ← label 从来没有被声明过
  await wait(800);
  await attach(phase, true);            // ← 这行永远执行不到
}
```

`label` 是 aside 那套东西的变量，`7d8e53b` 撤掉整套 aside 时删了它、**漏了这一处引用**。
每次流一断这行就抛 `ReferenceError`，重连永远不发生。

**它躲过 `pnpm check` 的原因**：`tsconfig.src.json` 的 include 只有 `src/**/*.ts` 和
`scripts/**/*.ts` —— **`panel.js` 根本不在类型检查范围内**。一个裸标识符引用只有在浏览器
里跑到那一行才会炸，而没有任何一层在它炸之前看过它。

浏览器里当场证的（`typeof label` 不抛，所以它骗不了人）：

```
typeof label      →  "undefined"
label === null    →  ReferenceError: label is not defined   ← 决定性
"label" in window →  false
```

**没顺手改的两件事，留给下一个人**：

1. **重连仍然只有一次**。修好之后一条终端一生能自动重连一次；第二次会话被关掉
   （同一个阶段里 `sessions.close()` 有 12 个调用点）还是会停住。症状从「每次卡」
   变成「每隔一次卡」。那个「只连一次」是有理由的（免得在反复断的服务上转圈），
   要改就是改一条设计决定。**建议**：重连成功并且真收到过字节之后，把额度还回去。
2. **`panel.js` 完全不在类型检查里** —— 这才是它能活下来的原因。真正能防住同类问题的
   是把它纳入检查（`allowJs` + `checkJs`，或者改成 `.ts`）。

### 3. blocker 加 `where` / `why` —— 用户提出的「语义损失」

**用户 2026-08-04 的原话：「红方直接 commit 的，写成报告肯定会有语义损失」，
以及后来的「绝对不能出现语义损失」。**


**类型是必填的，这是故意的** —— 我们修的这个 bug 就是「一个映射把字段静默丢了」。

## 二、新撞出来的三个缺陷，一个都没修

### A. ★ retry 之后「状态说在跑，其实没派出去」← 最该先修

**这是这个产品从头到尾在防的那一类，而它现在就活在主路径上。**

```
questions.apply(retry)  →  Change 状态 = running     ✓ 发生了
runPhaseTurn            →  workspace_dirty，拒        ✗ 没有 job 被创建
```

**两步是分开的**，第一步改状态、第二步才派发。于是 `Build/running` 挂着、库里没有
running 的 job、没有活进程 —— 而面板会显示它在工作。

**而拒绝的理由看不见**：它写进 `stageNote`（终端底下那行），至少两处会覆盖它，
其中一处是「进程已经结束了」——那正是答完之后必然发生的事（上一份 §四·B2 记过）。

**触发它的是 E，从一条没人预测到的路**：我们一整天都以为 E 会在
「Review 写报告不 commit → Fix 要干净树」那里发作。**实际是一轮失败之后，红方改到
一半的代码留在树上，把 retry 自己挡住了。**

→ 修法方向在 **BACKLOG §3.1·13**。

### B. 红方 blocker 形状错，炸掉整轮 —— 而那份数据本来就要被丢掉

`round.ts` 的顺序是：

```js
const red = parseTurnResult(transcript.red);   // ← 先解析，形状不对就抛
...
const found = redReviewsOthers(phase) ? [...red.blockers, ...blue] : blue;
```

**解析在判断「要不要用」之前。** 而 Build 阶段 `redReviewsOthers` 是 false ——
红方写的是自己的代码，自评不算数，它那些 blocker 本来就要被扔掉。

**真机代价**（第 4 轮，58 分钟）：红方交了 `blockers: ["BUILD-WEB-1/…: npm run build 失败了", …]`
—— 一个**数组套字符串**，而契约要的是对象。整轮作废，**连带蓝方同一轮 11 条有效发现
一起没了**。

**不是契约变长把它带偏的**：八次子 Agent 运行里 **7 次形状完全正确**（四次蓝方全对，
红方三对一错），而且崩掉的那一轮里蓝方交的是完整五字段。是一次性滑档。

→ 修法方向在 **BACKLOG §3.1·14**。

### 上一份 §五·1 把超时全归给许可门 —— 至少一半是「跑得慢」被错杀

我下午先用错判据得出「Plan r1 不是许可门」，晚上又发现那个判据本身是错的。
两次都记下来，因为**判据错了比结论错了值钱**。

**许可门在 rollout 里的正确判据（三条都反直觉）：**

1. **MCP 调用的 `name` 是 `exec`，不是 `stagepass_*`。** Codex 0.146.0 把它包在

2. **`"status":"completed"` 不代表它返回了** —— 那说的是「这条调用发出去了」。
   真判据是**按 `call_id` 配对，看有没有对应的 `custom_tool_call_output`**。
3. **按晚了的门留下的是一条完全正常的 completed 调用。** 破绽在它**前面那段空白**，
   不在它自己身上。所以「没有悬着的调用」≠「没有撞过许可门」。

**实测**：TestPlan r3 那 81 分钟的轮里，两段静默 31.0 分 + 33.7 分**都停在 exec→MCP
调用上、都最终拿到了 output** —— 65 分钟花在等人按。

**别拿静默时长当卡住判据** —— 那一轮中间有 101 / 58 / 54 分钟的静默，全是正常的。

**实时探测**（今晚实测能在 2 分钟内叫出来）：最后一条是工具调用、没有对应 output、
且 `input` 里有 `mcp__` / `stagepass_`。

## 五、动手之前必须知道的（补上一份那几条）

1. **macOS 的 `pgrep` 没有 `-a`**（那是 Linux 的）。用 `-a` 时它只吐 PID，不报 argv。
   我因此报过一次假的「还有 6 分钟就超时」。用 `-fl`。
2. **`panel.js` 不在类型检查范围内**（见 §一·2）。改它之前知道这件事。
3. **`SCHEMA_SQL` 是模板字面量，注释里不能出现反引号** —— 会当场截断，报
   「Property assignment expected」这种驴唇不对马嘴的错。
4. **一轮跑着的时候树脏是正常的**，干净树只在**派发那一刻**被要求。写监控别把
   「在 Build 且树脏」当告警条件。
5. `.stagepass/verification/` 下那几个一次性库还在（`worklist2` 那个的项目指向用户
   真实的 `demo`，08-03 的残留就是它跑出来的）。按上一份〇那条以后不再建，可以清。
