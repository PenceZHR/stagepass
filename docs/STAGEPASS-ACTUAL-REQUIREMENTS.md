> 本文不规定接口设计、数据结构、目录组织、技术选型、迁移步骤或开发任务。

## 1. 核心需求

Stage Pass 要成为一套由人类主导、由 Codex 执行、由系统控制流程和验证事实的软件工程工作台。

它不是一个通用聊天工具，也不是一个多 Agent 引擎聚合器。它的核心价值是：

- 把模糊想法逐步转化为可以交付的软件变更；
- 主动发现用户和 Codex 没有意识到的需求、设计和实现风险；
- 用阶段、证据、审查和人工放行约束 Codex；
- 让缺少完整软件工程经验的用户，也能按照可靠流程完成开发；
- 保留每次决策、执行、验证和交付的真实记录。

一句话概括：

> Stage Pass 用一套可观察、可审查、可恢复的软件工程流程，帮助人类安全地指挥 Codex 完成真实项目。

## 2. 产品定位

### 2.1 Stage Pass 是什么

Stage Pass 是位于用户、Codex 和代码仓库之间的流程控制系统。

它负责：

- 引导用户表达需求；
- 组织从需求到交付的完整流程；
- 在关键阶段主动暴露风险；
- 为 Codex 准备当前任务所需的上下文；
- 调用并约束 Codex 完成分析、设计、编码、审查和修复；
- 根据事实判断当前结果是否具备进入下一阶段的条件；
- 把最终决定交给人类。

### 2.2 Stage Pass 不是什么

Stage Pass 不是：

- Codex 或其他模型的聊天外壳；
- Claude 与 Codex 的统一适配层；
- 多 Provider、多模型供应商路由平台；
- 依靠增加 Agent 数量形成卖点的编排平台；
- 让 AI 自己生成、自己审查、自己批准的全自动流水线。

Stage Pass 的卖点是它的软件工程方法和流程哲学，不是支持多少 Agent 引擎。

## 3. 目标用户与使用场景

### 3.1 目标用户

主要用户是使用 AI 编码，但缺少完整软件工程方法、质量控制经验或项目管理能力的个人开发者。

用户可以提出产品想法并做出业务判断，但不应被要求：

- 熟悉完整的软件交付流程；
- 知道每个阶段应该问什么；
- 自己识别所有隐含风险；
- 为每次 Codex 执行手写专业提示词；
- 仅凭模型的自然语言总结判断工作是否完成。

### 3.2 核心使用场景

用户选择一个真实代码项目，创建一次 Change，并在 Stage Pass 的引导下完成：

```text
PRD → Spec → Tech Spec → Plan → Test Plan
    → Build → Review → Fix → QA → Merge → Retro → Done
```

用户在整个过程中持续看到：

- 当前处于什么阶段；
- 当前已经形成了哪些成果；
- 还存在哪些风险和阻塞；
- Codex 正在做什么、做过什么；
- 为什么现在可以或不可以进入下一步；
- 当前需要用户做出什么决定。

## 4. 核心产品原则

以下五项均为**【持续要求】**，适用于现有代码和所有后续重构。

### 4.1 人类拥有最终决定权

- 用户是需求来源和最终裁决者；
- Codex 可以提出建议、生成成果和执行工作；
- Codex 不能批准自己的成果；
- 关键阶段必须由人类明确批准或拒绝；
- 用户接受已知风险时，必须能够看到风险并留下理由；
- 系统不能因为 Codex 声称"已经完成"就自动放行。

### 4.2 系统必须主动暴露风险

Stage Pass 不能等待用户自己发现问题。

系统需要通过需求追问、对抗审查、评分规则、代码审查和质量验证，主动找出：

- 需求目标不清；
- 用户对象或成功标准缺失；
- 范围冲突；
- 规格遗漏；
- 技术方案与需求不一致；
- 实施偏离批准计划；
- 测试覆盖不足；
- 代码缺陷；
- 尚未解决却被后续结果掩盖的问题。

用户不需要先成为专家，系统要把需要用户判断的问题清楚地摆出来。

### 4.3 AI 产出与流程裁决分离

- Codex 负责分析、建议和产出候选结果；
- Stage Pass 负责记录、验证、比较和结算；
- 阶段是否完成不能只依赖模型自评；
- 无法验证、结果缺失或输出不合格时，不能默认成功；
- 后一次执行不能无条件覆盖前一次仍然有效的问题。

### 4.4 证据优先于叙述

- 代码是否改变，以真实仓库状态为准；
- 测试是否通过，以真实执行结果为准；
- 风险是否解决，以问题记录和复核结果为准；
- 阶段是否可以放行，以系统掌握的事实和规则为准；
- Codex 的总结可以帮助理解，但不能替代证据。

### 4.5 过程必须可追溯、可恢复

- 用户应能回看每个阶段的输入、成果、问题和决定；
- Codex 执行失败时，系统必须明确显示失败，而不是伪装成完成；
- 页面关闭或程序异常后，用户应能继续此前的 Change；
- 系统必须区分正在执行、成功、失败、中断和结果过期；
- 恢复后不能丢失已经确认的需求、风险、审批和执行事实。

## 5. 产品形态

### 5.1 产品由四个协作组件组成

- **Stage Pass Server**：唯一业务权威，承载阶段、gate、命令、审计、恢复和 rollout 判断；
- **Stage Pass Web**：项目与 Change 的运营控制面，展示状态、证据和健康度，提供 start/retry/interrupt/recover/settings 等操作；
- **Codex Hybrid Bridge**：以 app-server 负责 shell control，以 Codex Desktop follower 在持久 task 中执行受管 turn；
- **StagePass MCP App**：在 Codex task 内展示人类交互卡并提交经过 Server 校验的决定。

这四个组件是当前产品形态。MCP App 是人工决策主表面的一部分，不是可选的未来客户端。

### 5.2 Server 是唯一流程与命令权威【待实施 · 持续要求】

- 阶段判断、放行规则、风险结算、动作合约、Codex 上下文、幂等与恢复只存在于 Server；
- Web、Hybrid Bridge 与 MCP App 都只能调用 Server 提供的稳定能力，不复制业务判断；
- Server 不依赖 Web 在线也能持续执行和恢复 Change；
- 客户端投影与 Server 冲突时，以 Server 当前事实为准。

### 5.3 Web 是控制面，不是主要人工决策面【待实施】

Web 保留项目/Change 管理、流程状态、运行控制、模型与推理设置、bridge/MCP 健康、证据和只读决策审计。需要用户理解内容后作出的批准、拒绝、风险接受、采纳、返工等业务决定，主路径在 Codex task 内的 StagePass MCP App 完成。

迁移允许部分 rollout：尚未启用的阶段继续保留原 Web 决策路径；已启用阶段的默认 Web 决策入口只读并引导用户打开 Codex。只有 bridge/MCP 不健康且用户显式展开时，才允许经过审计的 Web 紧急表面。

### 5.4 持久 Codex task 模型【待实施】

- 一个 Change 始终映射到一个持久、可复用的 Codex task；
- 每个 Project 另外拥有一个可复用的 Project PRD task 和一个可复用的 Project Context task；
- Project PRD/Context 使用 durable project run 作为 owner，不得通过 synthetic Change id 伪装成 Change；
- 各阶段 role 是同一 canonical task 上的顺序 turn，不得为 writer/critic/build/fix 等角色创建第二个用户可见 task。

### 5.5 当前不开发 TUI【不做（当前）】

TUI 不是当前交付内容；当前架构仍不得把流程权威绑在 Web 中。

## 6. Agent 范围与 Codex 能力

### 6.1 只支持 Codex【已达成 · 持续要求】

目标态：

- Codex 是 Stage Pass 唯一的 Agent Runtime；
- 用户在本机安装并登录 Codex 后，Stage Pass 可以直接使用；
- 产品中不提供 Claude 支持；
- 产品中不提供 Agent Provider 选择；
- 不为已删除的 Claude 能力保留兼容入口。

Codex-only Provider 收敛已经完成，不再是本轮迁移优先事项。本轮重点是把现有 Codex 执行迁移到可见、持久、可恢复的 Desktop task 与 MCP 人工决策链路。

### 6.2 Codex 原生能力 rollout【待实施】

四个迁移配置只能由 Server 的统一配置模块读取，且只有字面量 `on` 表示启用；未配置时全部关闭：

- `STAGEPASS_CODEX_DESKTOP_BRIDGE`：统一控制 Change、Project PRD、Project Context 三类 managed scope；
- `STAGEPASS_MCP_INTERACTIONS`：控制 MCP interaction 能力；
- `STAGEPASS_CODEX_DECISION_SURFACE`：人工决策面的全局 master；
- `STAGEPASS_CODEX_DECISION_PHASES`：严格阶段 allowlist。

阶段 allowlist 固定为 `PRD,Intake,Spec,TechSpec,Plan,TestPlan,Build,Fix,Review,QA,Merge`。缺失表示空集；解析时允许 trim 与去重，但空 token、未知 token 或空白值必须清空 allowlist、报告 `codex_decision_rollout_invalid` 并 fail closed。

所有 Gateway actor 分类、Web Server projection、Broker presentation、wakeup 与 recovery 必须调用同一个 Server helper。只有 master 开启、阶段在 allowlist 中、interaction kind 与阶段映射有效时，Codex 决策面才启用；不得出现 caller 自行读环境变量或复制布尔判断。

### 6.3 用户可以控制 Codex 的关键运行选项【待实施】

Stage Pass 需要允许用户在合理范围内控制：

- 使用的 Codex 模型；
- 推理强度；
- 当前项目或 Change 的默认设置；
- 单次执行需要覆盖默认值时的设置。

用户不需要直接操作复杂命令，也不需要理解底层调用细节。

**现状**：底层存在推理强度字段但为硬编码，调用参数未暴露模型选择，无任何用户可操作入口。列为重构第三优先事项。

### 6.4 Stage Pass 负责准备上下文【已达成 · 持续要求】

- 用户主要提供需求、回答、反馈、理由和决策；
- 用户不需要为每个阶段重复粘贴项目背景；
- Stage Pass 根据当前 Change、阶段成果、未解决风险和仓库事实准备 Codex 所需上下文；
- 不同阶段只能获得完成当前职责所需的信息；
- 会话无法继续时，系统应能根据已保存的项目事实重新建立有效上下文；
- 浏览器页面不能成为唯一的上下文来源。

### 6.5 用户可以看到有用的 Codex 输出【已达成 · 持续要求】

用户需要看到：

- Codex 的最终答复和阶段成果；
- 当前执行状态；
- 已运行的重要操作；
- 对代码造成的实际变化；
- 失败原因；
- 可公开的推理摘要或说明；
- 与当前阶段有关的结构化结论。

Stage Pass 不获取、不承诺展示模型的完整私有思维链。可见的推理摘要只能用于帮助用户理解，不能单独作为阶段放行证据。

## 7. 核心流程需求

### 7.1 PRD【已达成，持续演进中】

- 接收用户最初的自然语言想法；
- 主动追问目标用户、问题、范围和成功标准；
- 允许用户回答、接受建议或暂缓非关键问题；
- 形成可供后续阶段使用的需求基线；
- 未解决的关键需求问题必须阻止进入下一阶段。

### 7.2 Spec【已达成】

- 根据批准的 PRD 形成产品规格；
- 使用正方产出与反方质疑暴露遗漏和冲突；
- 把问题作为持续存在的 Gap 跟踪；
- 旧问题必须被明确复核，不能因为重新生成文档而消失；
- 严重问题必须阻断；
- 可接受风险只能由人类带理由接受；
- 用户决定继续对抗、退回修改或批准。

Spec 阶段的"对抗产出 + Gap 跟踪 + rubric 评分 + 人工介入"是其余三个前期阶段（7.3–7.5）未来对齐的样板。

### 7.3 Tech Spec

基本要求【已达成】：

- 把批准的产品规格转化为技术设计；
- 明确系统行为、约束、影响范围和主要风险；
- 保持每项关键技术决定与需求可对应；
- 用户确认后，才成为后续计划和实施的依据。

**【预留】** Tech Spec 最终需要与 Spec（7.2）同等的对抗审查、人工介入和 rubric 评分机制。当前暂缓实施，但重构中的任何设计不得阻碍它加入。

### 7.4 Plan

基本要求【已达成】：

- 把批准的技术设计拆成可执行步骤；
- 说明预期影响范围、验证方式和已知风险；
- 发现与既有需求或设计冲突时，不能静默继续；
- 用户批准后才允许开始施工。

**【预留】** Plan 最终需要与 Spec（7.2）同等的对抗审查、人工介入和 rubric 评分机制。当前暂缓实施，但重构中的任何设计不得阻碍它加入。

### 7.5 Test Plan

基本要求【已达成】：

- 在编码前明确需要验证什么；
- 让需求、风险和测试之间能够对应；
- 同时包含适用的自动验证和人工检查；
- 测试计划被确认后才能进入 Build。

**【预留】** Test Plan 最终需要与 Spec（7.2）同等的对抗审查、人工介入和 rubric 评分机制。当前暂缓实施，但重构中的任何设计不得阻碍它加入。

### 7.6 Build【已达成 · 持续要求】

- Codex 只能依据已批准的计划和测试计划施工；
- 施工必须与用户正在使用的主工作区隔离；
- 用户可以看到实际修改内容和与计划的偏差；
- 越界修改、危险文件或不符合范围的改动必须阻断；
- 只有用户确认后，修改才能被接纳到正式工作成果中。

### 7.7 Review【已达成 · 持续要求】

- 对已经接纳的代码进行独立审查；
- 问题按严重程度呈现；
- 未解决的严重问题持续阻断；
- 新一次审查失败不能抹掉以前仍然有效的问题；
- 审查结论过期时必须重新审查；
- Review 满足条件后才能进入 QA。

### 7.8 Fix【已达成 · 持续要求】

- 根据 Review 或 QA 的阻塞问题进行针对性修复；
- 修复仍需遵守隔离施工和人工接纳；
- 修复范围应与已确认问题一致；
- 修复后必须重新经过受影响的 Review 或 QA；
- 不允许通过 Fix 直接绕过后续验证。

### 7.9 QA【已达成 · 持续要求】

- 按 Test Plan 验证当前代码；
- 保存每项验证的真实结果和证据；
- 验证失败时回到 Fix；
- 代码发生变化导致结果过期时，旧 QA 不能继续用于放行；
- QA 未满足条件时不能进入 Merge。

**【预留】** Live QA（浏览器实测）阶段：已有初步设计文档，当前决定**暂缓**——先完成 Codex Hybrid Bridge、统一 Server 权威和人工决策面迁移后再重新评估。已有设计文档保留作参考，不进入实施。

### 7.10 Merge【已达成 · 持续要求】

- 汇总需求、设计、计划、实现、审查、测试和代码事实；
- 清楚展示所有阻塞和已接受风险；
- 任一关键前置条件失效时，Merge 不可执行；
- 最终 Merge 必须由人类批准。

### 7.11 Retro【已达成】

- 记录本次 Change 中有效的方法、出现的问题和后续事项；
- 用户能够把未完成事项转入后续工作；
- 复盘结果应能帮助下一次 Change 改进。

### 7.12 Done【已达成】

- 为每个 Change 形成独立交付说明；
- 说明完成了什么、如何使用、主要改动和已知限制；
- 已知限制包含未关闭问题和被人类明确接受的风险；
- 交付说明不能只复制 Codex 对自身工作的总结。

## 8. 通用功能需求

以下均为**【已达成 · 持续要求】**，重构过程中不得回退。

### 8.1 项目与 Change

- 用户可以管理多个本地项目；
- 每个项目可以包含多个独立 Change；
- 每个 Change 拥有自己的需求、流程、执行、证据、决策和交付记录；
- 不同 Change 的上下文和结果不能相互污染。

### 8.2 当前状态与下一步

任意时刻，用户都能够清楚看到：

- 当前阶段；
- 已完成阶段；
- 正在执行的工作；
- 当前阻塞；
- 可执行操作；
- 操作不可用的原因；
- 需要用户决定的事项。

系统不能要求 Web、Hybrid Bridge 或 MCP App 自己猜测这些结论——这些结论必须由 Server 以结构化形式提供（与 5.2 一致）。

### 8.3 人工决策

- 所有批准、拒绝、风险接受和修改要求都要记录；
- 需要接受风险时必须显示风险内容和影响；
- 严重到不可接受的问题不能通过普通确认绕过；
- 结果或依据过期后，原批准不能继续无条件生效。

### 8.4 执行与进度

- 长时间工作不能因为用户关闭网页而自动丢失；
- 用户可以看到排队、执行、成功、失败或中断状态；
- 重复点击不能意外创建互相冲突的工作；
- 同一 Change 中互斥的工作不能同时破坏流程；
- 失败后要给出可理解的原因和可行的下一步。

### 8.5 风险与证据

- 风险按严重程度和状态集中展示；
- 用户能追踪每个风险来自哪里、是否已处理、如何处理；
- 审查、测试、代码变化和人工决定都能形成可回看的证据；
- 已过期的证据必须明确标识，不能继续伪装成当前结果。

## 9. Web 控制面体验需求【持续要求】

Web 不以自由聊天或主要业务决策为主界面，而以 Change 的工程控制面为主界面。

网页需要让用户快速理解：

- 我现在在哪里；
- 系统为什么停在这里；
- Codex 已经做了什么；
- 现在最大的风险是什么；
- 我需要检查什么；
- 我接下来可以做什么。

Web 还需要：

- 用一致方式展示阶段、风险、证据和人工决策；
- 在执行过程中持续反馈进度；
- 提供 start、retry、interrupt、recover、settings、bridge repair 和“在 Codex 中打开”等运营控制；
- 对已启用的 Codex 决策阶段展示 interaction 状态和只读审计，不保留默认直接决策入口；
- 对尚未启用的阶段保留迁移期 Web 路径，确保 partial rollout 不阻断 Change；
- 在 Server、Hybrid Bridge、Codex Desktop 或 MCP 不可用时清楚说明原因；
- 避免向普通用户暴露不必要的底层实现细节；
- 不要求语音交互或强对话体验。

## 10. 质量与安全需求

以下均为**【已达成 · 持续要求】**。

### 10.1 本地优先

- 当前面向本地单用户场景；
- 用户的项目代码和执行过程默认留在本机；
- 不要求提供远程 SaaS 或多租户能力。

### 10.2 安全执行

- Codex 不能不受约束地修改用户正式工作区；
- 超出批准范围或存在明显危险的操作必须停止并请求用户处理；
- Stage Pass 不应向界面泄露凭据、敏感环境信息或不必要的私有内容；
- 用户必须能在实际修改进入正式成果前进行检查。

### 10.3 可靠性

- 任何失败都不能被记录成成功；
- 程序重启后，已确认的业务事实不能丢失；
- 过期结果不能用于新的放行；
- 页面显示必须与系统掌握的当前事实一致；
- 关键流程必须能够解释为什么允许或拒绝某项操作。

### 10.4 Codex Desktop Phase 0 发布闸门【持续要求】

Codex Hybrid Bridge 依赖的 private IPC、持久 shell、Desktop follower、同 task 连续 turn、Host/MCP source-thread 绑定和崩溃恢复，必须在目标 Codex Desktop 版本上通过真实客户端验证。单元测试、callback 模拟或仅 SQLite 证据不能替代发布验证；Phase 0 private-IPC viability 是 Codex 原生控制面的硬发布闸门。

### 10.5 Git 表面与内部证据分离【待实施】

- Stage Pass 不提供面向用户的 Git UI 或通用 Git 操作；
- 用户在 Codex/外部工具中完成日常 Git 操作；
- Stage Pass 继续在内部读取和保存 base commit、HEAD、patch/diff identity、changed-files hash、adoption、review/QA freshness 和 merge readiness 等证据；
- 移除 Git UI 不得削弱隔离施工、越界阻断、结果新鲜度或可追溯性。

## 11. 范围排除与暂缓

### 11.1 明确不做

- 多 Provider 或通用模型路由；
- 远程 SaaS；
- 多租户和权限系统；
- 语音交互；
- Chat-first 主界面；
- 完整私有思维链展示；
- 面向用户的 Stage Pass Git UI 与通用 Git 操作；
- 对 Stage Pass 核心流程的重新发明。

### 11.2 已决定、待实施（重构范围）

- Codex Hybrid Bridge 与三类 persistent managed scope（见 5.1、5.4）；
- StagePass MCP App 人工交互与统一 Server 命令权威（见 5.1–5.3）；
- 严格、可部分发布的 Codex decision rollout（见 6.2）；
- Codex 模型与推理强度用户可选（见 6.3）；
- 移除 Stage Pass Git UI/operations，同时保留内部 Git evidence（见 10.5）。

### 11.3 预留（暂缓，未来做）

- TUI 客户端（依赖 5.2 完成）；
- Tech Spec / Plan / Test Plan 的对抗+介入+rubric（见 7.3–7.5）；
- Live QA 阶段（见 7.9，重构后重新评估）。

## 13. 已确认的产品决定

按 2026-07-24 决策更新：

- 当前产品组件是 Server、Web、Codex Hybrid Bridge 和 StagePass MCP App；
- Server 是完整产品内核和唯一命令权威，Web 是运营控制面；
- 人类业务决定的主表面是 Codex task 内的 MCP App，partial rollout 期间 disabled phase 保留 Web 路径；
- 一个 Change 对应一个持久 Codex task；每个 Project 另有 Project PRD 与 Project Context 两个可复用 task；
- 未来可以增加 TUI，但当前不实现；
- 只支持 Codex；Provider 收敛已经完成，不再是迁移优先事项；
- Live QA 暂缓，重构后重新评估；已有设计文档保留作参考；
- Tech Spec / Plan / Test Plan 的对抗+介入+rubric 是预留目标，当前暂缓但设计必须为其留出空间；
- MCP 是 human-interaction cards 的必需组件；
- 移除 Stage Pass Git UI/operations，但保留内部 Git evidence；
- Codex Desktop Phase 0 private-IPC viability 是硬发布闸门；
- 不做多 Agent Provider 适配；
- 本地优先、单用户；
- 核心卖点是 Stage Pass 的软件工程流程与人类裁决机制。
