### 1.3 换成了什么：两个文件路径由裁判原样转达（`d5ed0ec`）

```
StagePass 写   rubric-CHG-1-PRD-r3.md          按 1..N 编号，零 criterion key
               rubric-answers-CHG-1-PRD-r3.md  空壳
```

### 1. ★ 每一轮都要人按一次 MCP 许可，不按就烧满 30 分钟

> 待修位置：**§四·第一档·2**。这里是它的完整现场记录。

**这是现在最要紧的一条，而且 2026-08-04 凌晨抓到了现场。**

`-a on-request` 之下，Codex 在第一次调某个 MCP 工具时会弹自己的许可提示。
**而「一次」是按会话算的，不是按线程** —— 每一轮对抗都是一个新的 `codex resume`
进程 ＝ 新会话，所以**每一轮都会弹一次**。

抓到的原文（Spec 第 5 轮，03:40）：

```
Action Required | demo
Calling stagepass.stagepass_next({})
Field 1/1
Allow the stagepass MCP server to run tool "stagepass_next"?
› 1. Allow                    Run the tool and continue.
  2. Allow for this session   …
  3. Always allow             …
```

**不是只对某个工具。** 同一夜 03:44 又抓到一次，那次是裁决那条路上的
`stagepass_ask`（`Called stagepass.stagepass_ask({})` 之前先弹了同样的许可框）。
判据是「这个会话第一次调这个 MCP 服务器」，和是哪个工具无关。

**没人按 = 整轮静默烧满 30 分钟。** 那一夜连着两轮这么死的：

```
Spec 第 3 轮  卡在 stagepass_next({})       30 分钟超时 → Spec/blocked
Spec 第 4 轮  卡在 stagepass_answer({...})  30 分钟超时 → Spec/blocked
```

两次 rollout 的最后一条都是 `custom_tool_call`，之后一个字节不长；上下文才 43.8%，
不是撑爆。用户当时在忙别的（他的原话：「两个阶段我都在忙别的没点」）。第 5 轮他在，
按了 `1. Allow`，日志立刻出现 `Called stagepass.stagepass_next({}) └ 第 1 条，共 13 条`，
之后一路顺跑、一口气关掉 11 条。

**这条挡着「无人值守跑完一个阶段」这件事本身** —— 而那正是这个产品存在的理由。
对抗轮十几分钟起步，人不可能全程守着。

三条出路，**都要用户拍板**：

| | 代价 |
|---|---|
| 弹出来时按 **3. Always allow** | 一劳永逸，但往用户的 Codex 配置里写一条持久规则 |
| StagePass 检测到这道门就当场告诉人 | 治标：至少不再静默烧 30 分钟，而是说「去按一下」 |
| 换审批模式 | **死路** —— `-a never` 会让 elicitation 被自动 decline，类型上已不可表达 |

2026-08-03 中午提过一次「按 3」，凌晨又提了三次。**用户每次按的都是 `1` 或 `2`**，
所以这条至今没被根治 —— 而且 08-04 05:45 查过：按完之后 `~/.codex/config.toml`
里**没有任何工具放行相关的键**（只多了几条别的会话写的 `[projects."…"] trust_level`），
`~/.codex` 下最近 30 分钟一个文件都没被改过。

**所以「3. Always allow」到底写在哪，仍然是未知数。** 下次按了之后立刻
`find ~/.codex -newermt "-5 minutes"` 扫一遍 —— 那是这条坑唯一的根治线索。

**一个有用的副产品**：`bolop8rkr` 那个「卡住检测」监控器管用 ——
判据是**行为**（rollout 超过 3 分钟没长而 job 还在 running），不是屏幕关键词。
实测 205 秒就叫出来了，比等 30 分钟超时早 26 分钟。
**别用关键词匹配屏幕**：TUI 会把空格挤掉，`Allow the stagepass MCP server` 在
scrollback 里长成 `AllowthestagepassMCPserver`，而且旧的提示会一直留在里面造成误报。

**而「只看裁判线程的 rollout」也不够** —— 裁判等子 Agent 的时候，它自己那条 rollout
本来就不长，真正在动的是子 Agent 那条。06:04 我就是这么误报了一次（屏幕上明明写着
「正方仍在形成计划产物……处理时间符合预期」）。**正确的判据要连子 Agent 的
rollout 一起看**：裁判线程和它这一轮派生的孩子**全都**超过 N 分钟没长，才算卡住。

**我猜错过一次，如实记下**：看到「一个 PRD 阶段的裁判进程在阶段批准两小时后还活着」，
我判断是两个插件实例抢同一个游标，并建议先收掉它再重跑。**那是错的方向** ——
真正的原因是许可门。那个孤儿进程是另一件事（见下），但它不是这两次超时的成因。

### 1b. 阶段批准之后，裁判进程没被收掉

`archiveFinished` 只归档了线程，**没关进程**。实测：PRD 在 00:29 批准，到 03:00 那个
`codex resume 019fcab5-…` 还活着（2 小时 30 分），带着同一个库、同一个
`STAGEPASS_CHANGE` 的插件配置。

不是上面那两次超时的成因，但它是个真漏 —— 一个批准过的阶段不该留着进程。

### 2. 「一路回车」会让需求变成空的

录需求那张表第一趟全是选项，一路回车＝每格取第一项。验机制够用，但那样录出来的
需求**没有内容**。2026-08-03 的 `CHG-1` 就是这么废的：说了「修一个能复现的错误」
却没说是哪个，于是两条 P0 五轮一动没动，红方编不出来。

对比 `CHG-001`（用户认真答的）：两轮就关掉六条。**差别不在机器，在输入。**

### 3. `ps` 会把非 ASCII 转义

查 argv 要从 rollout 或面板日志读原文。这一趟又踩了一次（`M-;M-eM-.M^C…`）。

### 4. 老坑照旧有效

- Bash 的 `curl` **这一趟能连上 localhost 了**（和之前记的相反，但别依赖它）
- `preview_start({name})` 起不来 → 后台 Bash 起进程 + `preview_start({url})`；
  **一个会话只开一次 tab，之后一律 navigate**
- 改完代码要重启面板，**别在有轮在跑的时候重启**
- 面板前端 `read_page` 返回空树，只能用 `javascript_tool`；坐标比例每次实测标定
  （这一趟量到 1.6006）
