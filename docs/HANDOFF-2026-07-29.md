## 四、这次验出来的、会再咬人的

### 4.1 `-a never` 会掐死 elicitation（可复现）

`-a never` 不只管 shell 审批，它让 Codex **自动 decline 掉 MCP 的
`elicitation/create`** —— 而那是 StagePass 唯一的问人通道。失败是静默的：回来的
是一个格式完全合法的 `{"action":"decline"}`，和"人按了 Esc"一模一样。

`pnpm probe:elicit never` / `on-request` 各跑两次，稳定：

| `-a` | 选择器 | 客户端回什么 |
|---|---|---|
| `never` | **不画** | `{"action":"decline"}`，秒回 |
| `on-request` | **画** | `{"action":"accept","content":{...}}` |

**类型上已经不可表达** —— `CodexInvocation.approval` 只接受
`"untrusted" | "on-request"`。写注释叮嘱下一个人不如让它编译不过。

### 4.2 `on-request` 会停在审批上等人 —— ~~而且没有解~~ **后半句是错的**

从面板派发一次真 PRD turn，模型要写文件，Codex 弹出审批 —— **整个 turn 停在
那儿**：rollout 二十分钟不长一个字节，进程活着，没有错误、没有任何迹象。按一下
Enter，**10 秒后 `task_complete` 出现**。

> **观察是真的。当时从它推出的「没有第三档、无人值守没有解」是错的。**
> 2026-07-29 晚用 `pnpm probe:sandbox` 推翻，详见 PRD §6.6 里那个 ⛔ 方框。

**当时只变了 `-a`，`-s` 从头到尾钉死在 `read-only`**（`scripts/panel.ts` 至今
如此）。而 read-only 的定义就是模型不能写文件 —— 它想写就必然要升级审批。
**那 20 分钟是 `-s` 逼出来的，不是 `-a` 的锅。**

同一个提示词、同一个 `-a on-request`，只变 `-s`，turn 跑起来后一个键都不按：

| `-s` | 结果 | 屏幕上 |
|---|---|---|
| `read-only` | 没写成，等满 150s | 停在 `Would you like to run the following command?` |
| `workspace-write` | **写成了，26.1s** | 没有任何审批提示，`• Added probe.txt (+1 -0)` |

**PRD §6.6 的《决定二》其实早就写着「约束模型能碰什么的是 `-s`，不是 `-a`」**
—— 那一节里两处说法本来就矛盾，错的是方框那处。

**还暴露出一件更要紧的事**：《决定二》把 PRD/Spec/TechSpec/Plan/TestPlan 配成
`read-only`，理由是"只该读和产出文档"—— 但产出文档就是写文件。**这一格 L5 开工
前必须定**（要么这些阶段也给 workspace-write，要么产物不能是模型自己写的文件）。

面板的价值这次说得更准了：它不是"权限模型唯一可用的前提"，它是**"当真的需要人
时，人看得见"**。elicitation 本来就是故意要停下来等人的，这条不因为无人值守有解
而变弱。

#### ⚠️ 这条坑我当天又踩了一次，所以单独写出来

实测完两小时后，我写 `scripts/verify-rubric-round.ts` 时**照抄了
`verify-round.ts` 的 `sandbox: "read-only"`**。结果整轮停在
`Would you like to make the following edits?` 上，等了三十分钟。

**凡是要产出文件的 turn，`-s` 就不能是 `read-only`。** 现存脚本里
`verify-round.ts` / `verify-rebuild.ts` / `probe-elicit-run.ts` 都还是 read-only ——
它们的 task 目前不写文件所以没暴露，但**照它们抄新脚本会中招**。

**取证也别学我：** 我先查 `~/.codex/sessions` 有没有新文件，没有就断定"turn 没
开始"—— 错的，这个 Codex 的线程不写那儿。**真正管用的一招是直接看那个窗口：**

```bash
osascript -e 'tell application "Terminal" to get contents of front window'
```

一眼就看见它停在哪。（`System Events` 那条查进程的会因权限失败，别用。）

### 4.2b rubric 行协议在真模型上**成立**（2026-07-29 实测，但整条链未走完）

L5-4 唯一离线证不了的问题是：**真模型拿到 rubric 契约之后，会不会照那个行协议
作答。** 答案是会。裁判窗口里逐字：

```
• /root/red 已完成并产出 Spec。现在我将派生 /root/blue…
• Started `/root/blue`
• Waiting for agents
• Finished waiting
  └ No agents completed yet
• {"verdicts":{}}
  RBC-b15ae469-2beb-42e4-9762-8a8458a2a55b yes 本阶段没有既有问题，因此不存在被沉默略过的问题。
  RBC-c5bb37eb-e822-497d-8786-448792ce8b43 yes 本轮没有关闭任何问题，因此不存在缺少关闭理由的情况。
```

那两个 key **精确匹配**那一次运行库里 verdict rubric 的两条 criterion（比对过
`rubric_criteria`）。所以：

| | |
|---|---|
| ✅ 契约进得去，模型照格式答得出 | 这是这一层的核心问题，成立 |
| ✅ 裁判仍然会派生 `/root/red` 和 `/root/blue` | 三份 rubric 契约**没有**把派生指令挤出注意力 |
| ❌ 子 Agent 没有完成 / 找不到 | `Finished waiting / No agents completed yet`，于是 `readRoleTranscript` 报 `no sub-agent at /root/red` |

**最后一条是 L4 层面的问题，不是 rubric 引进来的。** 下一个人要接着做的就是它。

> **取证方式记一下**：这段是从 Terminal 窗口里读出来的，不是从库里。库里
> `assessments` 是 0 —— 脚本在读红方 rollout 时就抛了，什么都没记。
> **「模型答没答」和「答案有没有落库」是两件事，别用后者去判断前者。**
> 原文存档：`scratchpad/judge-window.txt`（本次会话）。

### 4.3 `/opt/homebrew/bin/codex` 是个几 KB 的 Node 包装脚本，不是真二进制

对它跑 `strings` 会得到一片 0 命中，看起来像"这个配置键不存在"，**其实什么都
没搜到**。真二进制在 `@openai/codex-darwin-arm64/vendor/.../bin/codex`，259MB。
老交接 §五.9 那条"八个候选名全 0 命中"就是这么来的（结论碰巧仍成立，但当时没有
证据）。凡引用 `strings` 结论处，以真二进制为准。

### 4.4 TUI 的文字不能用普通正则匹配

它用**光标移动而不是空格**排版，`Allow the X MCP server` 在字节流里是
`AllowtheXMCPserver`；CSI 序列还有中间字节（`ESC [ 0 SP q`），
`[0-9;?]*[a-zA-Z]` 这种模式漏掉它。**先剥转义、再去掉全部空白，然后匹配。**
这个坑让我两轮把"探针没按到按钮"误读成"Codex 没画选择器"。

### 4.5 这个环境的 `grep` 是 ugrep，`\|` 不当或运算符用

我用它查 `/api/run` 得到"未命中"，差点以为改动丢了 —— 实际全在。**用 `-E`，
或者用 python 逐个数。** 这条会让你对代码现状做出完全错误的判断。

### 4.6 别让模型当触发器

最早的探针要模型去调工具，**六轮里四轮它根本没调**，每轮十几分钟什么也没答出来。
改成探针自带 MCP 服务端、在工具调用里直接发 elicitation，一轮几分钟且确定。

### 4.7 面板静态资源必须 `no-store`

改着改着浏览器拿缓存，看起来和"改了没生效"一模一样。已加，但**如果你看到界面
没跟着代码变，先确认不是在看 `file://` 那个预览 tab**（编辑 `panel.html` 时
harness 会自动开一个，那里 `/api/panel` 取不到，界面是残的 —— 不是面板坏了）。

### 4.8 harness 的 `preview_start` 在这个环境里起不来面板

`.claude/launch.json` 那条 `panel` 配置**跑不起来**，三种写法都挂在同一处：

```
shell-init: error retrieving current directory: getcwd: Operation not permitted
```

它 spawn 出来的进程 cwd 拿不到（`pnpm` 报 `uv_cwd EPERM`；换 `node --import tsx`
之后变成 `Cannot find package 'tsx' imported from /`，可见 **cwd 是 `/`**）。
不是配置写错了。

**能用的路子**：自己用后台 Bash 起 `node --import tsx scripts/panel.ts --port …`，
再 `preview_start {url: "http://localhost:…"}` 开 tab。注意**沙箱里 Bash 的 curl
连不上 localhost**（静默无输出），所以别拿 curl 判断服务起没起 —— 看进程 stdout
的那行 banner，或者直接用浏览器。

### 4.9 浏览器面板的点击坐标是**截图空间**，不是 viewport

`computer{action:"screenshot"}` 回来的是 800×450，而页面 viewport 是 1280×720。
`coordinate` 吃的是**前者**。拿 `getBoundingClientRect()` 的值直接点，会落在屏幕
外，**表现是"点了什么也没发生"** —— 看起来和"按钮坏了"一模一样，我在这上面白跑
了一轮。**乘 800/innerWidth 再点。**

另外 `read_page` 在这个面板上返回空树（`Viewport: 0x0`），`find` 因此也用不了。
用 `javascript_tool` 取 rect 自己换算是唯一可靠的路子。

`hover` / `left_click` 传 `ref` 不受这条影响（refs 来自 `read_page`，而它在这里
本来就取不到）。

4. **不要让 UI 被污染掉。**

第 4 条是前三条的总纲：**新东西默认不进主屏。** 现在主屏底部那条决策区

#### 5.0.1 「一个环」是什么意思（用户当场纠正过我一次，别再搞反）

我第一次理解成"把小环也精简掉"，**错了**。用户原话：

> 我只要一个 UI 界面的一个**大环**，不是说**小环**里面要去掉。
> 现在的 UI 不要填，我只觉得太拥挤了，我是想精简一点，不是说要变那个小环。

对应到代码：

| 说的是 | 代码里是 | 怎么办 |
|---|---|---|
| **大环** | `.halo` 那条实线轨道，**和 `.halo::after` 那圈内层虚线** | **只留一条。** 同心的第二圈去掉 |
| **小环** | `.stage-node button` —— 每个阶段那个细描边的圆 | **不动。** 它们是他要的，别削 |

**方向是减，不是加。** "现在的 UI 不要填" —— 任何"顺手补个提示/加个摘要"的
改动都违反这条。觉得主屏缺信息，答案是弹窗，不是往环那屏塞。

#### 5.0.2 阶段状态常驻面板（用户 2026-07-29 后来提的，可能替代弹窗）

原话：

> 原始的比例不是 2:2:6 吗？你说那个圆环其实占 6 的位置。我希望圆环那整个页面，
> **左边 40% 的位置可以用来常驻显示每个 stage 的状态**。比如说我的鼠标挪到了
> Spec 的位置，然后我左边就刷新成 Spec 的状态。然后我要是 PRD 的位置，那就显示
> PRD 的状态，**随着我的鼠标变动**。如果我的鼠标没有点任何的小圈儿 stage，
> **那就恢复到原始的状态**。

行为很清楚：**悬停驱动**。鼠标移到某个节点 → 左侧面板刷成那个阶段的状态；
鼠标离开所有节点 → 回到默认。

**两处歧义已经问过用户，都定了（2026-07-29）：**

1. **「左边 40%」是第三列内部的 40%。** 也就是那个 `6` 的区域再分
   **40 / 60** —— 左 40% 状态面板，右 60% 放环。
   **Projects / Changes 两列保持不动**，整页仍是 `2 : 2 : 6`。
   - **⚠️ 连带后果：环只剩第三列的 60%，会比现在更小。** 而他先前明确抱怨过
     环太小、比例不协调。**所以这一条不能只改宽度 —— 必须同时把环放大**
     （现在是 `.orbit-wrap { max-width: 78% }`，且高度先定；在 60% 的容器里
     要重新配比，让环看起来仍然是主角）。改完务必截图自查。
2. **是补充，不是替代。两个都要。**
   - **悬停** → 左侧常驻面板刷成那个阶段的状态（概要）
   - **点击** → 弹窗显示那个阶段完整的问题列表（明细）
   - 信息分两层。**注意弹窗会盖住环，所以它必须能干脆地关掉**，别变成第三层
     常驻内容。

**这一条不违反"不要污染 UI"** —— 它是把信息从主屏挪到一个常驻的、有固定位置
的地方，而不是往环那屏加东西。**同时，底部那条决策区要撤掉**（§5.0 第 4 条），
它的内容归到左侧面板与弹窗里。

#### 落地时要先定的四件事（我没有替他定）

- **~~一个环是几层~~ —— 这条用户已经说清楚了，见下面 §5.0.1，不要再当成待定。**
- **pass / fail 从哪里读。** 数据模型里**没有 per-phase 的 pass/fail 字段**。
  能用的原料：`change_events` 账本里的 `approve` / `reject`、`gaps` 里该阶段
  还有没有 open、`change_evidence` 有没有该阶段的行。**这个映射必须先定死并
  写进 PRD**，否则颜色会变成一个没人能说清含义的装饰。
- **绿/黄怎么落到这套色板里。** 设计稿 §3 明确禁止高饱和警示色，并写着
  **"不依赖颜色作为唯一状态表达"**。所以要用低饱和的灰绿与暖沙金/陶土，
  并且**颜色之外还要有第二个信号**（对勾、描边粗细、文案）。这不是跟用户
  拧着来 —— 是同一份设计稿的硬约束，实现时一起满足。
- **「请 Codex 问我」搬到哪。** 主屏要清空，这个主动作最自然的去处是弹窗里
  那个阶段的底部。**但它仍然只能是"把裁决交给 Codex 问"，不能变成弹窗里的
  approve/reject 按钮**（§5.3 第 2 条）。

#### 弹窗里放什么（有现成数据）

`GapStore.all(changeId, phase)` 已经给出该阶段全部 gap（含 `status`：
open / closed / waived、`openedRound`、`resolution`）。
`CommandStore.gateFor(changeId)` 给闸门结论。
**这两样都是读接口，不写 —— 弹窗只显示，不改状态。**

#### 5.0.3 落地了什么（2026-07-29 晚，`pnpm check` 246 绿）

| 那四条 | 做法 |
|---|---|
| 1 主屏只留一个环 | `.halo::after` 那圈同心虚线删了；`.gate-head` 并进左面板；**小环一个没动** |

且此后没有回到过它；黄 = 有 open gap / `blocked` / 被 reject 过）。判据实现在
`src/web/panel-server.ts` 的 `markOf`，8 个测试盯着它，包括 **Fix 被二次打回时

**环放大了 11%**（可见轨道直径 354 → 393px，实测于 1280×720）。做法不是改 40%

和 `placeNodes` 里的 `0.455` **必须同时改**，否则节点会浮在轨道内外），再把
`.orbit-stage` 左右留白压到 14px。

> 白空 170px）。想再大只能动 40% 那个数，而那是用户定的，我没改。

**顺手补上了 §5.1 的「已完成节点的对勾」**：已批准的节点里画对勾，有问题的画空心

### 5.2 我自己观察到的粗糙处

- **阶段视图里看不到闸门**：进了终端就只有终端。**注意这条和 §5.0 第 4 条有张力** —— 别为了补它又往主屏加东西，答案应该在弹窗里。
- **Projects 列永远只有一行**：`ProjectStore.ensure` 建一个，界面上没有建 Project 的入口；Change 列同理，没有新建 Change 的入口。
- **决策区风险多了会横向滚动**，滚动条藏了，看不出还有更多。
- **终端里的字偏灰** —— 那是 Codex 自己画的暗色 chrome，不是面板的问题；但如果你觉得该更亮，只能在 xterm 主题里把前景调亮，**不能去解析它的输出**（§9.3）。

### 5.3 改 UI 之前必须知道的三条硬约束

1. **`src/web/` 里不许把 pty 输出变成 string。** 常驻测试第五条会红。禁的 token：
   `TextDecoder` / `.toString(` / `JSON.parse` / `String.fromCharCode`。
   这不是洁癖 —— 它是终端面板被接受的前提条件（PRD §9.3）。
2. **网页上不许有 approve / reject 按钮。** 决策区只显示闸门说了什么，主动作是
   「请 Codex 问我」，裁决发生在 Codex 自己的选择器里。
3. **节点用三角函数放在同一个圆心和半径上**，不许各自用近似百分比定位（设计稿
   明写）。悬停放大只作用在自己身上，不许推动圆环。

**版式上已经踩过的两个坑**（别再踩）：`.col-head` 是 flex 且默认不换行，
`flex: 0 0 100%` 会把标题挤成零宽只剩一个字母；圆环若只按宽度定尺寸，标题一
占位底部节点就掉到列外 —— 要高度先定、宽度由 `aspect-ratio` 推出来。

## 七、我这次犯的错，写下来免得重犯

1. **说好让用户决定的事，自己顺手做了。** 我说 artifact「留不留是你的决定」，
   然后用 `git add docs/` 把它一起提交了。**范围语句一旦说出口，就要在动手时
   兑现。**
2. **拿 `grep` 的空结果当"代码里没有"。** 见 §4.5。差点据此得出"改动丢了"的
   错误结论。
3. **抄错了原型。** 阶段环的节点照着 brainstorm 里那份圆角方卡的探索稿做，而
   真正实现过的那版是圆的。**`01-stage-orbit.png` 是实现后的审计截图，它比任何
   探索稿都更接近"原来的样子"。**
4. **改判据时把它写宽了。** 决策区最初用 `permitted.length > 0` 决定能不能问人，
   而只有 approve/reject/retry 会被拿去问 —— 会问出一个 `no_decision_available`。
