## 二、批次 A：真 Codex 上验掉了，也撞出两个问题

在 CHG-003（捕鱼达人）上跑了两次「说清楚我要什么」。

**成立的部分**：17 格（8 题 × 2 + 全局那格）全画出来了；每题和它的「你自己怎么说」
相邻；逃逸项在选项末尾；模型没被绕晕（读了仓库、提 8 题、每题 5–7 个真选项、没自己
写「其他」、调完 `stagepass_ask` 就停）；Esc 回 `{"action":"cancel"}`，需求不落库。

两条合并规则在真答案上兑现：

```
选「都不对，我自己写」+ 写字 → 只留人的话，逃逸项本身不进需求
选某一项 + 写字             → 两句都留（单局最终总分 +「他补充：但只算这台设备上的」）
跳过「你自己怎么说」         → 不留任何痕迹
```

### 2.1 字段顺序不由我们决定 —— 客户端按字段名排序

这边按 `B1, B1x, …, B8, B8x, B0` 写出去，**选择器画出来的第一格是 `B0`**：人还没被
问到任何一个具体问题，先被问「还有什么必须说清楚的」。

改法：id 两位数补零（`B01` / `B01x`），全局那格改叫 `BZ`。**排序之后就是显示顺序。**
补零管的是 `MAX_ITEMS` 哪天被提上去 —— `B1 < B10 < B1x` 会把第 10 题插到第 1 题和它
自己那格中间。

### 2.2 `required` 是硬闸门，而空的自由文本格会吃掉回车

两条都在 Codex TUI 上实测，而且都**没有任何提示**：

- 还有必填没答时按回车 → 屏幕上什么都不发生。
- 光标停在一个**空的自由文本格**上按回车 → 也什么都不发生。`optional` 不管用、
  必填项全答完也不管用、底下明明写着 `enter to submit all` 也不管用。
- 而整张表**只能从最后一格提交**。

批次 A 把 17 格全塞进了 `required`，于是标着「（可以留空）」和「选了也可以补充」的
那 9 格一格都留不了空。改成 optional 之后又撞上第二条：最后一格是可留空的自由文本，
**整张表交不上去** —— 我自己就卡在那儿，按了三次回车什么都没发生。

出路只有两条：最后一格是**选项格**（回车总有个值可提交），或者它**必填**。

- 录需求那道题：最后那格（`BZ`）改成必填，文案跟着改成
  「最后一句（必填）：这次最要紧的是什么？上面没问到的也写在这里。」
  **这是实测逼出来的，不是产品偏好。** 代价是每次录需求都得亲手写一句；换来的是
  必填计数器会说「还差 1 个」，而不是一个交不上去又不说为什么的表单。
- 回应蓝方那道题：最后一格是 `decision`（选项格）。小写 `d` 排在 `R` 之后，
  **名字是这么挑的，不是巧合。**

### 2.3 判据放在唯一的出口上，不靠人记得

`domain/question.ts` 的 `compose` 现在挡住这两件事，三个组题函数全走它：

```
order_not_sorted           传进来的顺序必须已经等于排序后的顺序（不替你悄悄排：
                           那样组题的人写下的顺序和人看到的顺序永远对不上）
last_field_unsubmittable   最后一格不许是「可留空的自由文本」
```

两条都是**客户端的行为**，所以判据必须在代码里而不是在注释里。

### 3.1 ④：为什么它不违反 §9.3

§9.3 管的是**pty 的字节**（不许读懂 Codex 画在终端里的东西）。这里读的是模型**落在
磁盘上的产物**，和 `codex/rollout.ts` 读 rollout、`codex/subagent.ts` 读子 Agent 的
文件同一类动作。

两道闸都不省：路径必须出现在这个 (Change, 阶段) 的 `artifactIds` 里，**而且**必须落在
项目目录内。第二道不是多余的 —— `artifactIds` 是模型写的，一个想歪的模型可以往里放
`~/.ssh/id_rsa`，只查「库里列着的」挡不住那个。

弹窗顺带放大到 720×88vh：放大前 `.sheet-body` 只有 273px 高，**比正文框本身还矮**，
外层滚一层里层再滚一层，一次看得见十行。

### 3.2 C：三处顺序是承重的

```
1. 先查 fence      问的是「人回答的这段时间里，别人动过这份证据吗」
2. 再落表态        驳回会把一条 blocker 从名单里拿掉，而闸门算的正是那个名单
3. 最后走闸门      对着表态之后的新快照（apply 的 rebaseFence）
```

第 1 步放到第 2 步之后去查，查的就只是「我刚写完的东西还在不在」，fence 成了装饰。
第 3 步那个 `rebaseFence` **不是放宽 fence**：存下来的那份必然对不上，而对不上的原因
是人自己刚说的话 —— 那不是 fence 要防的东西。

**这不是新开一道题，是把原来那道闸门裁决问全了。** 同一个 `/api/ask`、同一个 kind、
同一个 `decisionFrom` —— §5.3「没有第二条能推动闸门的路」比新增一种问题更严格地成立。

### 3.3 D：只被「还有问题挡着」拒掉的 approve 照样提供

否则人在同一道题里把问题全驳回/接受掉之后，还要再问一遍才能批准。

**这不是放宽 §5.4**：那条挡的是**永远执行不了**的选项（老树那五个死按钮），而这一个
可执行，只是要人先把挡着的东西处理掉。他没处理，落地时闸门照样拒并把
`blocking_problem_outstanding` 报出来。「什么都没产出」那个拒清不掉，所以那时 approve
仍然不提供。

### 3.4 顺手修的两个真 bug

1. **`standard` 在 judgePrompt 里渲染成 `[null]`**（它没有 severity）。裁判正要对这条
   表态，而 `[null]` 是它看不懂的分级。现在写「标准」。
2. **同一个阶段跑出了两个 codex。** `close()` 只 `kill()`，进程的 `onExit` 是异步来的，
   而 D 的续跑正是 close 紧接着 launchInto：

   ```
   close → kill 旧的 → launchInto 存进新的 → 旧的 onExit 到了 → 把**新的**删掉
   ```

   注册表从此认为这个阶段没有活进程，下一个 `open()` 又起一个 —— `ps` 里实测两个
   codex 挂在同一个 (Change, 阶段) 上，一个带着裁判提示词、一个是空的浏览会话。
   §6.5 规则 5 的全部意义就是不许出现这个。**症状很难查**：人进终端看见的是那个空
   composer，正在跑的那一轮在另一个看不见的进程里。

   改法一行（`onExit` 只删自己那一条），测试先红后绿验过。

## 六、两件你说要先谈的

### 6.1 跑一轮时界面几分钟不说话

**我没动它**，因为要先跟你确认做法。先把可用的原料摊开（两条硬约束我都守住：不解析
pty 输出、不往阶段环那一屏加东西）：

| 能拿到的信号 | 从哪来 | 说得出什么 |
|---|---|---|
| `jobs.status` / `attempt` / `deadline_at` | 库，`/api/run` 排队时就写 | 「这一轮在跑，已经 3 分 20 秒」 |
| `changes.status` | 库 | running / settled / blocked |
| pty 进程活着没有 | `sessions.has()` | 「裁判那个进程还在」——进程死了立刻知道 |
| 红蓝的子 Agent 目录出现没有 | `~/.codex/…` 里那两个子 Agent 的文件 | **「红方在写 / 蓝方在挑」** |
| `gaps` / `rubric_assessments` 新增行 | 库 | 「裁判已经开始表态了」 |

第四行是唯一能说出「走到哪一步」的，而它是**读文件**（和 §9.3 无关，那条管 pty 字节）。
`codex/subagent.ts` 已经有 `createSubAgentLookup` / `readRoleTranscript`，判「那个路径
下有没有东西」比读内容轻得多。

**我建议的做法**（等你点头再做）：

1. `/api/run` 改成**不 await 整轮**：排队 + 起协程，立刻回 `{queued:true, jobId}`。
   按钮从「派发中…」变成「正在跑（3:20）」，而不是一直卡在那儿。
2. 加一个 `GET /api/progress?change=…`：只读，返回 `{job:{status,startedAt}, stage}`，
   其中 `stage` 从上表第 4、5 行算出来 —— `red_writing` / `blue_attacking` /
   `judge_ruling`，算不出来就是 `null`（**不猜**）。
3. 面板每几秒拉一次，写进**弹窗**和左侧常驻面板（不进环那一屏）。

要先跟你确认的两点：**(a)** 轮询还是 SSE（轮询更笨但更不容易骗人）；**(b)** `stage`
算不出来的时候显示什么 —— 我倾向于「在跑，3:20」加一句「还看不出走到哪一步」，
而不是编一个阶段名。

### 6.2 Build 阶段

**一行代码都没动**，按你说的先谈。四个问题我先说我的倾向，你拍板：

1. **红蓝怎么分。** 我倾向「红写代码、蓝审代码」，但蓝方现在的规矩是**不许读仓库**
   （只许基于正方产出提问题）—— 那条规矩在设计阶段是对的（不然「攻击这份文档」会
   变成「调查这个项目」），到了 Build 就把蓝方变成了只能看 diff 猜的人。
   **所以这条得为 Build 单独定，不能沿用。**
2. **沙箱要不要收紧。** 现在全部十一个阶段都是 `-s workspace-write`。Build 本来就要写
   代码，收紧没有意义；真要收的是**设计阶段**（现在它们也能改源码，只靠提示词和人看
   —— PRD §6.6 明确记着这是你接受的交换）。
3. **「产出」是文件、diff 还是 commit。** 我倾向 **commit**：`artifactIds` 现在是路径，
   而 Build 的产物天然是一组改动；一个 commit 有稳定 id、可以 revert、也能 fence
   （哈希进 snapshot）。文件列表说不出「改了什么」，diff 说不出「基于哪一版」。
4. **失败的 Build 回不回滚。** 我倾向**不自动回滚**，理由和 gap 一样：一次失败的 Build
   留在那儿，下一轮才有东西可看；自动回滚会让「这一轮改了什么」消失，而那正是这棵树
   从头到尾在防的静默。但要给一个明确的出口（「丢掉这一轮的改动」），而且它是人的
   裁决，所以在选择器里问。

## 八、坑（这次新增的，其余见 2026-07-29 那份）

| 事实 |
|---|
| **客户端按字段名排序显示 elicitation 的字段**，不按 properties 的书写顺序。顺序只能编码在名字里。 |
| **`required` 是硬闸门，而且失败是静默的** —— 还有必填没答时按回车，屏幕上什么都不发生。 |
| **空的自由文本格会吃掉回车**，`optional` 也一样；整张表只能从最后一格提交。所以最后一格要么是选项格、要么必填。 |
| **Codex 的目录信任不继承，而且它会当场问你**（`Do you trust the contents of this directory?`）。答「Yes」会往用户的 `~/.codex/config.toml` 里写一条 —— 验收用的临时目录**不要**放在 `/tmp`，放在已经受信任的仓库里（`.stagepass/verification/` 被 gitignore 了）。 |
| **`close()` 之后立刻 `launchInto()` 会被旧进程的异步 `onExit` 把新会话删掉**（已修，但这类「按 key 删」的地方值得再扫一遍）。 |
| **浏览器面板的坐标点击这次又变了一种花样**：截图变成 1:1、坐标点击无效、`computer{scroll}` 超时。`element.click()` 是可靠的退路，但它不是鼠标事件 —— 用了就要说。 |
