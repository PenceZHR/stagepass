## 三、这次做了什么

### 1. 批次 A 修：选择器有两条规矩，只有真跑才看得见

在 CHG-003（捕鱼达人）上跑了两次「说清楚我要什么」。**两字段那道题本身是成立的** ——
17 格全画出来、每题和它的「你自己怎么说」相邻、逃逸项在末尾、模型没被绕晕、
Esc 回 `{"action":"cancel"}` 且需求不落库。两条合并规则也在真答案上兑现了。

坏的两条，**都没有任何提示**：

**(a) 字段顺序不由我们决定 —— 客户端按字段名排序。** 这边按 `B1, B1x, …, B0` 写出去，
选择器画出来的第一格是 `B0`：人还没被问到任何具体问题，先被问「还有什么」。
改法：id 两位数补零（`B01` / `B01x`），全局那格改叫 `BZ`。**排序之后就是显示顺序。**

**(b) `required` 是硬闸门，而空的自由文本格会吃掉回车。** 还有必填没答时按回车，屏幕上
什么都不发生；光标停在一个**空的自由文本格**上按回车，也什么都不发生（`optional` 不管用、
底下写着 `enter to submit all` 也不管用）。而整张表**只能从最后一格提交**。

出路只有两条：最后一格是**选项格**，或者它**必填**。所以录需求那道题的最后一格（`BZ`）
改成必填，文案改成「最后一句（必填）：这次最要紧的是什么？」；回应蓝方那道题的最后一格
是 `decision`（选项格）—— 小写 `d` 排在 `R` 之后，**名字是这么挑的**。

**判据放在唯一的出口上**：`domain/question.ts` 的 `compose`，三个组题函数全走它，
两个错误码 `order_not_sorted` / `last_field_unsubmittable` 在组题时就拦。

### 3. B：人可以驳回，也可以自己提

```
waive    问题还在，我接受这个风险     -> waived，进交付说明
dismiss  这条不成立，别再拿它挡我     -> closed，不进交付说明
raise    我自己提一个                 -> HUMAN-<n> / finding / P1
```

`dismiss` 和 `waive` 一样拒绝 `standard`，但理由不同：一条标准还挂在 rubric 上，把它
派生的 gap 驳回了，**下一轮判定会再开一条一模一样的出来** —— 那是一条这一轮有效、
下一轮就失效的假出口。standard 的出口是撤下那条 criterion。

### 4. C + D：回应蓝方和裁决同一次问出来，选「再来一轮」当场续跑

```
R01   SPEC-1　验收标准不可测
      [同意，红方下轮必须改 / 不同意，这条不成立 / 先接受这个风险 / 我自己说]
R01x  ↑ 这一条你想说什么？（可留空）

```

**这不是新开一道题，是把原来那道闸门裁决问全了** —— 同一个 `/api/ask`、同一个 kind、
同一个 `decisionFrom`，§5.3「没有第二条能推动闸门的路」比新增一种问题更严格地成立。

**三处顺序是承重的**：① 先查 fence（问的是「别人动过吗」，放到后面查就只是「我刚写完的
还在不在」）；② 再落表态（驳回会把一条 blocker 拿掉，而闸门算的正是那个名单）；
③ 最后走闸门，对着新快照（`rebaseFence` **不是放宽 fence**：存下来那份对不上的原因是
人自己刚说的话）。

**裁决那一格说人话**：`reject` 这个词没人猜得到它是重跑。设计阶段写「再来一轮」，
Review / QA 写「打回去修（送到 Fix）」—— 同一个动作，两句不同的话，判据用已有的
`sendsToFix`。

**只被「还有问题挡着」拒掉的 approve 照样提供**：人在同一道题里把问题清掉之后就该能
批准。这不是放宽 §5.4（那条挡的是**永远执行不了**的选项）—— 他没清，落地时闸门照样拒
并报出 `blocking_problem_outstanding`。「什么都没产出」那个拒清不掉，那时 approve 不提供。

「再来一轮」和「重跑一次」都**当场续跑**；「打回去修」不续 —— 那时 Change 已经在 Fix 了，
自动在一个刚到的阶段上开跑等于替人决定了 Fix 该做什么。

### 5. 跑一轮时说得出它在干什么

`GET /api/progress`（只读）+ 面板每 3 秒拉一次，**只写弹窗，环那一屏什么都不加**。

```
{ phase, status, live, job:{status,startedAt,elapsedMs}, spawned, stage, processGone }
```

两条硬约束都守住：**一个字节都不碰 pty**；进度只来自库、进程状态、以及 Codex 自己的
`state_5.sqlite`（读的是「这个线程派生了哪几个子 Agent」）。

`stage` 只报**看得见的**：`/root/red` 出现 → 红方在写；`/root/blue` 也出现 → 蓝方在挑。
蓝方之后是「还在挑」还是「裁判在裁」这一侧分不出来，**不报第三档**。第一轮压根算不出来
（子 Agent 要从裁判 threadId 查，而绑定是一轮跑完才写的），那时说「还看不出走到哪一步」。

**`processGone` 是承重的那一格**（状态说在跑、可是没有活进程）。它当天就派上用场：

```
stage: "blue_attacking",  processGone: true,  elapsedMs: 1600978
```

一眼看出「跑到蓝方了，然后进程没了」—— 而在这之前，同一个状态在界面上只是「派发中…」。

### 6. 归档由 StagePass 自己管

一条被归档的会话，`codex resume` **一起来就退**，而这一侧只看得见「进程没了」。而
StagePass 是「一个 (Change, 阶段) 绑一条线程绑一辈子」（§6.5 规则 2），所以那个阶段从此
每次都撞同一面墙。

```
批准之前   每次 resume 先确认一遍，被归档就自动解开，历史完整保留
批准之后   由 StagePass 主动 codex archive —— 归档标记的是「这个阶段结束了」
```

**判据是 `threads.archived` 那一列，不是命令的退出码**：`codex unarchive` 对一条没被归档
的会话会**报错**（所以不能无脑先跑一遍），而做完之后要**再读一次那一列**才算数。读不到
那个库就说读不到，退回加这一层之前的行为。

归档不是 StagePass 干的（代码里零处），也不是进程退出触发的（**做过实验**：起一个 codex、
`archived=0` → kill → 还是 0）。它**成批**发生 —— 用户库里 51 条在 12 秒内被归档，
其中就有那条裁判线程派生的 `/root/red` 和 `/root/blue`。

### 7. 顺手修的六个真 bug

1. **`standard` 在 judgePrompt 里渲染成 `[null]`**（它没有 severity）。裁判正要对这条表态，
   而 `[null]` 是它看不懂的分级。现在写「标准」。
2. **同一个阶段跑出了两个 codex。** `close()` 只 `kill()`，`onExit` 是异步来的，而 D 的续跑
   正是 close 紧接着 launchInto —— 旧的 onExit 到了，把**新的**从注册表里删掉。`ps` 里实测
   两个 codex 挂在同一个 (Change, 阶段) 上。改法一行（`onExit` 只删自己那一条），
   测试先红后绿验过。
3. **L1 崩溃恢复一个生产调用者都没有。** `JobStore.recover` 写好了、离线证过，没人调。
   面板被杀掉就留下一个 `running` 的 Change —— 而 `running` 只允许 `settle` / `fail`，两个
   都不是人能裁决的动作，**那个 Change 永远动不了了**。现在 `recoverStuckTurns` 在面板启动
   时调一次，并且**把恢复了什么打出来**。
4. **`blocked` 上「跑这个阶段」是死按钮** —— HTTP 500、空 body、界面「没跑起来：undefined」，
   而下一步那行偏偏在让人按它。（改完第一版我把名单写成「只有 pending」，又把 retry 之后
   那一步堵死了；正确的名单跟着 `TurnLoop.queueTurn` 走：`pending` + `running`。）
5. **服务端把每一个 500 都吞掉了**（`catch(() => { 500; end(); })`）—— 一句都不记。那正是
   M7 记着的老树病，而它长在我们自己的新树上。现在错误同时写进面板 stdout 和回给浏览器。
6. **终端一起来就死时，三个等待循环会等满 15 分钟**，界面一句话不说 ——「在等你选」和
   「那边早就没了」长得一模一样。现在判据是进程状态，死了立刻回
   `session_died_before_answering`，**并把 threadId 一起给出去**（最常见的原因是归档）。

## 七、坑（这次新增的，其余见 2026-07-29 那份）

| 事实 |
|---|
| **elicitation 的字段显示顺序 = 字段名排序**，不是 properties 的书写顺序。顺序只能编码在名字里。 |
