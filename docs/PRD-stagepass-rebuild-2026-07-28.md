## 1. 一句话

> StagePass 只做两件事：**管状态、调 Codex**。凡是需要人看一眼再决定的，一律在 **Codex TUI** 里出现、人在那里选。选完，StagePass 接着往下走。

三个组件，职责不重叠：

| | 职责 | 明确不做 |
|---|---|---|
| **StagePass Server** | 状态机、gate、fence、租约、恢复；组问题；验答案；推进状态 | **不渲染任何东西** |
| **StagePass Web** | 看和启动：当前状态、证据、风险、start/retry/interrupt/recover；**托管终端面板** —— Codex TUI 真正运行在里面的那块 pty | **不承载任何业务决策入口** |
| **Codex 插件** | 通过 MCP `elicitation` 向人提问，把答案发回 StagePass | 不决策、不组题、不判断合法性 |

**终端面板是宿主，不是入口。** 上面那一格没有松动：决策仍然只发生在 elicitation 选择器里，只是那个选择器显示在浏览器的一块 pty 中，而不是 Terminal.app 的窗口里。Web 上没有、也不会有一个能推动闸门的按钮 —— 面板换掉的是那块玻璃谁写的，不是谁做决定。

**渲染由 Codex TUI 原生完成。StagePass 一行都不画** —— 包括执行过程和选择界面。这条是 2026-07-28 定的，取代了原先"在 Codex App 里弹 HTML 卡片"的写法；理由见 §2.4。

**「画在哪个窗口」和「谁在画」是两件独立的事。** 面板里跑的是同一个 `codex` 二进制，画面仍由它用转义序列自己画，StagePass 只把字节搬到浏览器。**搬窗口不等于换画的人** —— 所以上面那句在面板落地之后依然逐字成立，它约束的始终是"谁在画"。可机械检查的判据见 §9.3。

## 2. 为什么重建（这一节决定了后面所有取舍）

### 2.1 它从来没跑通过

不是"有 bug"，是**一次都没有走通**。跨本机全部四个数据库统计：

| 事实 | 数字 |
|---|---|
| 走通过的 Change（PRD → Done） | **0** |
| 历史上完成过的闸门命令 | **1**（`approve_intake`，surface 是 `stagepass_web_emergency`） |
| `gate_decision` 卡被呈现给人看过的次数 | **0**（生产库 2 pending、gateway-e2e 2 pending、r5 库 3 expired） |
| `human_decisions` 里真正由人产生的行 | **0**（7 行全是对抗轮次的系统产物，`actor_surface` 为空） |

**所以没有可回归的东西。** 反对重写的常规理由（会作废十万行测试、会丢失已验证行为）默认系统是能跑的 —— 它不能跑。这条理由在这里不成立。

### 2.2 遗留的真实代价是模型判断失准

这是重建的**首要理由**，不是次要的。

现有代码库里，人的决策面散在四个地方，其中三个不通：从未启动过的 host-attested MCP App（1232 行）、零挂载的 GatePanel、名叫"紧急"却是唯一成功过的 `stagepass_web_emergency`、以及真正在跑的 Codex 插件。**读这份代码的模型无法判断哪个是真的**，于是据此做出的每一个决定都可能是错的。

实测代价：2026-07-28 删除一个组件文件（`gate-panel.tsx`）之前，必须先查它有没有活的父组件、`specBattleFallback` 这个 prop 传给了谁、钉它的测试是不是 `describe.skip` —— **查了四轮才敢下手。一个文件。** 这样的文件有上百个。

在老树上"边删边判断"永远满足不了"不能有遗留"这条约束，因为**每一次删除都要依赖那个已经被证明不可靠的判断**。新树的属性是可判定的：**里面每一行都是有人特意放进去的。**

### 2.3 建得比接得快

2026-07-28 一轮就撞出五处"建好但没接上"：

- `request_{tech_spec,plan,test_plan}_changes` —— 有 contract 条目、有标签、有渲染，但不在任何 surface 的可执行集合里
- `waive_spec_p1` / `waive_plan_p1` —— schema 要 `gapId`/`riskId`，而卡片一次点击给不出来
- 承载卡片呈现的 job 是绿的，卡永远停在 `pending`

**五处没有一处被 103,241 行测试抓到**，因为每一层单独看都自洽，缺陷只活在层与层之间。这决定了新树必须有一类老树没有的测试（见 §7）。

### 2.4 人机交界的入口是 TUI，App 由人自己接力（2026-07-28 实测定案）

**两个表面都保留，它们是接力不是二选一。** 分工由一件事决定：**StagePass 只能驱动 TUI。**

| | StagePass 能发起吗 | 谁决定去那里 |
|---|---|---|
| **Codex TUI** | ✅ `codex resume <id> "<prompt>"`，自动发送，零按键 | StagePass |
| **Codex Desktop** | ❌ 无法自主发起 | **人，在 TUI 里敲 `/app`** |

TUI 的斜杠命令里有（从二进制读出，非推测）：

```
app       continue this session in Codex Desktop
          成功时："Opened this session in Codex Desktop."
rollout   print the rollout file path
```

**`/app` 是「继续」而不是「只读打开」** —— Desktop 接管之后的 turn 所有权，所以 HTML widget 在那边应该能渲染。这条尚未实测，但它不在关键路径上：**StagePass 不依赖它**。人想要更丰富的界面时自己敲一下，StagePass 既不知道也不需要知道。

这也是为什么提问必须用 `elicitation` 而不是 `ui://`：**选择器要在「此刻拥有 turn 的那个客户端」里渲染**，而那个客户端可能是 TUI，也可能是人刚刚 `/app` 过去的 Desktop。押注单一客户端的渲染实现，就会在人按下 `/app` 的那一刻断掉。

下面是四条路各自的实测结果。**全部由用户目视确认或探针日志记录，没有一条是推断的。**

| 路线 | 结果 |
|---|---|
| host-attested MCP App（需求文档 §5.1 指定的主表面） | ❌ 从未运行过，见 §2.1 |
| `codex mcp-server` + `codex://threads/<id>` 回看 | ❌ **Desktop 打开是空的**（注意：这是 deep link 直接开一个 mcp 线程；与人在 TUI 里 `/app` 接力是两回事）。线程 `source=mcp`、rollout 78KB/22 条一条不缺，窗口就是不显示内容。用户两次确认（turn 进行中、turn 结束后各一次） |
| `codex mcp-server` + StagePass 自己渲染流 | ⚠️ 技术上可行、已实现过，但**用户明确否决**："我不想在我的 StagePass 里渲染，我就要在 Codex 原生客户端里渲染" |
| **`codex resume <id> "<prompt>"` + MCP elicitation** | ✅ **闭合** |

> **脚注（2026-07-28 追加）：终端面板不属于第三行这条。**
>
> 上面表格第三行那句用户原话是本文的边界定义，**一个字不改**。它否决的是「StagePass 解析事件流、理解语义之后自己画界面」。终端面板不是那个：pty 里跑的是同一个 `codex` 二进制，画面仍由它自己画，StagePass 只把字节原样搬到浏览器。
>
> **"Codex 原生客户端"指的是 TUI 这个程序本身，不是包着它的那块玻璃。** `Terminal.app` 也不是 Codex 写的 —— 它是苹果写的通用终端模拟器，Codex 只是在里面跑。所以 osascript 窗口与终端面板**在架构上是同一个位置**：通用终端宿主 + Codex 在里面自己画，区别只是玻璃谁写的。区分这两者的机械判据见 §9.3。

TUI 那条路今天验到的四件事：

1. **能恢复 `mcp` 建的线程并显示完整历史** —— 用户确认
2. **prompt 自动发送，不需要任何按键** —— 用户确认。这是它和 App 的决定性差别：`codex://threads/new?prompt=` 只预填不发送，App 那条路必须人先按一次回车，**StagePass 无法自主发起**

   > **这句「零按键」有一个已知例外，范围限定在「无人值守」。** `codex` 启动时可能弹一个阻塞式更新提示（`Update available!` → 三选一 → `Press enter to continue`），它挡在 turn 前面。
   >
   > **这个二进制里没有关闭更新检查的配置键，也没有对应的命令行开关** —— 八个候选名（`check_for_updates` / `update_check` / `auto_update` / `disable_update` / `skip_update` / `hide_update` / `upgrade_notice` / `CODEX_DISABLE*`）在 `strings` 里全部 0 命中。**不要去找一个不存在的开关**，唯一的规避是 TUI 里那个持久化的 "Skip until next version"，按一次可顶到下个版本。
   >
   > 所以「零按键」在**人在面板前**的场景下成立（提示就在眼前，按一下 Enter 无所谓），**残留风险只剩「StagePass 无人值守跑 turn」一种场景**：那时提示无人应答，StagePass 会静默等满超时。
3. **HTML `ui://` widget 在 TUI 不显示** —— 用户确认。终端里没有 HTML 的位置，所以提问不能依赖它
4. **Codex 向 MCP 服务端声明 `elicitation` 能力**，选择器原生渲染，答案结构化回到插件：

```
CLIENT_CAPABILITIES: {"elicitation":{"form":{},"url":{}}}
CLIENT_INFO:         {"name":"codex-mcp-client","title":"Codex","version":"0.144.4"}
ELICIT_RESULT:       {"action":"accept","content":{"action":"approve_spec"}}
```

> **实测值的版本边界**：本节与 §6.4 的原始实测取自 `codex-cli 0.144.4`。**2026-07-29 在 `0.146.0` 上复核过**：`-s` / `-a` 的档位、`never` 的原文、bypass 的原文、以及那两个不存在的旧写法，全部不变；客户端仍然声明 `{"elicitation":{"form":{},"url":{}}}`。**这些结论扛过了这次版本跳变**，但它们依赖行为和文件约定而非公开接口（见 §10 已知风险），下次升级仍要重来一遍。以 `codex --help` 与实跑为准，不要以旧记忆为准。
>
> **顺带纠正一个方法**：`/opt/homebrew/bin/codex` 是一个几 KB 的 Node 包装脚本，不是真二进制（真的在 `@openai/codex-darwin-arm64/vendor/.../bin/codex`，259MB）。**对着包装脚本跑 `strings` 会得到一片 0 命中，看起来像"这个键不存在"，其实什么都没搜。** 本文凡是引用 `strings` 结论的地方，都以真二进制为准。

**为什么这不只是"换个能跑的方案"**：`ui://` widget 押注在某一个客户端的渲染实现上，那正是它今天死掉的原因。`elicitation` 是 **MCP 协议层的客户端能力** —— 谁拥有 turn，选择器就在谁那里渲染。今天是 TUI；哪天 App 变得可驱动，同一个插件不用改一行。这跟"能用公开的就用公开的"是同一条原则。

## 3. 什么可以进新树（可判定的判据）

新树的每一行都要能通过下面四关。**四关任意一关不过，就不进。**

**E1 —— 它服务于哪一个？** 只有两类东西可以存在：① 七个核心概念之一（§4）；② "调起 Codex" 或 "收卡片回执" 这两件事之一。答不上来的不进。

**E2 —— 它有生产调用者吗？** 任何 export 在其所属层验收时，必须被生产路径实际调用到。**零调用者不允许存在**，不允许"先建着以后接"。这条做成常驻测试。

**E3 —— 这条规则是不是已经有一份实现了？** 同一个判断不许出现第二处。老树里有两套 present、两套 record、一个阶段三个名字、`CHOICE_CARD_ROLES` 与解析器互相矛盾。**一个规则一份实现，一个概念一个名字。**

**E4 —— 它能被验收吗？** 说不出"什么表里出现什么行算它成立"的东西不进。

## 4. 七个核心概念

**这是需求，不是对现有实现的描述。七个全部重写。** 老树在这些地方有真金（fence 语义、心跳必须严格前移、越界判定、幂等键设计），移植时去读它，读完扔掉。

| # | 概念 | 必须做到 |
|---|---|---|
| 1 | **状态机** | 阶段与转移可穷举；非法转移被拒绝；每次转移落审计账本；没有任何路径能绕过账本 |
| 2 | **gate** | 放行与否由系统掌握的事实和规则算出，不依赖模型自评；证据过期时 gate 必须重算 |
| 3 | **fence** | 决策绑定它所依据的快照；快照变了，旧决策失效而不是静默生效 |
| 4 | **租约** | 长任务有主；主死了能被接管；心跳严格前移（老树的教训：租约钳到 deadline 会让心跳必然违法） |
| 5 | **恢复** | 进程重启后已确认的事实不丢；正在跑的活要么继续要么明确失败，不允许伪装成完成 |
| 6 | **对抗** | 红/蓝/裁判产出可裁决的结果；旧问题必须被明确复核，不能因为重新生成文档而消失 |
| 7 | **rubric** | 评分规则可解释；gap 持续跟踪；严重项阻断；接受风险必须由人带理由并指明是哪一条 |

## 5. 卡片模型

### 5.1 一张卡只有一种形状

**一批问题，每题若干选项。** 不允许有第二种卡片实现。

- 需求澄清 = N 个问题，选项是候选答案
- 阶段裁决 = 1 个问题，选项是闸门动作
- 接受 P1 风险 = N 个问题（**一个 P1 一题**），选项是接受 / 不接受

### 5.2 两种发起方式，判据是「结构由谁决定」

| | 模型发起 | **StagePass 发起** |
|---|---|---|
| 谁知道要问什么 | 只有模型知道 | 只有 StagePass 知道 |
| 谁组卡 | 模型（StagePass 固定 schema） | **StagePass 全权** |
| 模型交什么 | 完整卡片内容 | **一个不透明 id** |
| 用于 | 需求澄清 | 阶段裁决、风险接受 |

StagePass 发起的卡，模型拿不到问题文案、选项集合、以及回执要带的身份标识 —— **它没有机会改写，因为它从来没拿到过。**

### 5.2b 提问用 MCP elicitation，不用 HTML widget

一次提问就是一次 `elicitation/create`：

```
插件 → Codex：  { message, requestedSchema }
Codex        ：  TUI 原生渲染选择器
Codex → 插件 ：  { action: "accept" | ..., content: { <字段>: <选中值> } }
```

**选项集合就是 schema 里的 `enum`。** 这一条不是风格选择，是 §5.4 的实现手段：模型无法渲染一个 enum 之外的选项，因为渲染的不是它。

三种形状对应到 schema，**前两种 2026-07-28 在 TUI 里实测通过**：

| 形状 | requestedSchema | 实测返回 |
|---|---|---|
| 阶段裁决 | 一个必填字段，`enum` 是本阶段合法的闸门动作 | ✅ `{"action":"accept","content":{"action":"approve_spec"}}` |
| 需求澄清 | N 个必填字段，一题一个 | ✅ `{"action":"accept","content":{"q1":"个人开发者","q2":"自动重试","q3":true}}` |
| 接受 P1 风险 | 一个 P1 一个字段 | 与需求澄清同形状 |

第二行值得单独说：**三个问题（含一个布尔）在一次 elicitation 里一起问、一起答。** 所以"一批问题"这个形状不需要多轮往返，一个 `requestedSchema` 就够。

**不再有 `ui://` 资源、不再有 widget HTML、不再有「卡片」这个词** —— 它属于那条已经死掉的路线。本文其余部分说「问题」和「选择」。

### 5.3 一条答案路径

所有选择走同一个入口、同一套校验。**没有第二条能推动闸门的路。**

### 5.4 选项里不许出现选不动的东西

一个选项能出现在 `enum` 里，当且仅当：① 记录答案的 surface 接受它；② 它的 payload 能由组题时已知的信息构造出来。**不满足的不许出现。**

老树同时违反了两条：`request_{tech_spec,plan,test_plan}_changes` 有标签有渲染但不在任何 surface 的可执行集合里；`waive_spec_p1` / `waive_plan_p1` 的 schema 要 `gapId`/`riskId`，而一次点击给不出来。

### 5.5 surface 必须名副其实

人在 Codex 里做的决定，用一个语义正确的 surface 记录。老树把 16 条插件回执全记成 `codex_mcp_app`（而 MCP App 从未启动），把唯一一次真实批准记成 `stagepass_web_emergency`（而它不是紧急、是唯一能用的路）—— **分类字段撒谎比没有分类更糟。**

### 5.5b L3 验收证据（2026-07-28）

人在 Codex TUI 里选择，StagePass 的闸门前进 —— **这个项目历史上第一次**：

```
你选了     {"action":"accept","content":{"decision":"approve"}}
结果       {"kind":"advanced","action":"approve"}

question   { id: 'Q-DECIDE', kind: 'gate_decision', status: 'applied' }
answer     { question_id: 'Q-DECIDE', action: 'accept', content_json: '{"decision":"approve"}' }
ledger     0:create 1:start 2:settle 3:approve
change     { phase: 'PRD → Spec', status: 'pending' }
```

对照 §2.1 的基线：老树历史上完成过的闸门命令**总共 1 条**，走的是 web 的"紧急"表面；经由 Codex 的**是 0 条**。

### 5.6 人可以拒绝回答

实测（2026-07-28，用户按 Esc）：

```
RAW    {"result":{"action":"cancel"},"error":null}
```

**拒绝是一个正常的 result，`action:"cancel"`、不带 `content`。** 不是 JSON-RPC error，不是超时，不是空答案 —— 这三种 StagePass 都会误判成别的东西，所以这一条要验而不是猜。

StagePass 必须把它当成一个**明确的结果**：阶段停在原地、落一条记录、可重开。**不是失败，更不是默认批准。** 一个把 `cancel` 当超时处理的实现，会让"我先不决定"变成"这一轮白跑了"。

## 5.7 对抗的界面是裁判的界面（L4 的形状，2026-07-28 定）

**一个窗口，不是三个。** 红方和蓝方是裁判派生的**子 Agent**，不是另外开的 Terminal。

```
        你看到的 ─────► 裁判的 TUI 窗口
                            │
                    ┌───────┴───────┐
                 子 Agent        子 Agent
                  红方            蓝方
                （产出）        （质疑）
```

两条理由，第二条是技术性的：

1. **人只面对一个决策者。** 让人同时盯三个窗口，等于把"综合三方意见"这件事外包给人 —— 而那正是裁判存在的意义。
2. **子 Agent 有独立线程和上下文**，蓝方看不到红方的推理过程。同一线程里的顺序 turn 做不到这一点：蓝方会读到红方所有的自辩，质疑会退化成附和。

这条同时决定了 L4 不许做的事：**不许为红蓝各开一个 TUI。**

## 6. 分层与闸门

> **下层验收不通过，不许动上层。** 这是建造纪律，不是建议。

| 层 | 内容 | 验收方式 |
|---|---|---|
| **L0** | schema、状态机、状态转移、审计账本 | **完全离线** |
| **L1** | gate 计算、fence、租约、心跳、幂等、崩溃恢复 | **完全离线** |
| **L2** | 调起 Codex TUI：`codex resume <threadId> "<prompt>"`、thread 绑定、turn 记录、从 rollout 读结果。**终端面板是这一层的第二个 launch 实现，不是新的一层** | 需真 Codex |
| **L3** | 人机交界：组题 → TUI 原生选择器 → 人选 → 答案回来 → 状态前进 | 逻辑离线（假答案）+ 一次真选择 |
| **L4** | 对抗：红/蓝/裁判，结算出可裁决的结果 | 需真 Codex |
| **L5** | rubric、gap 跟踪 | 需真 Codex |
| **L6** | 铺开到其余阶段 | 需真 Codex |

**L2 已通过两次**：先用 `codex mcp-server`，再用 TUI。第二次是必须的 —— 换的是执行通道本身，mcp-server 是父进程直接拿返回值，TUI 是一个独立的交互式进程。

TUI 版验收证据（2026-07-28，独立从 session 文件复核而非只看脚本输出）：

```
threads 表     source=cli, cli_version=0.144.4     ← TUI 建的，不是 mcp
一个 rollout   行2–35 是第一轮，行37–45 是第二轮   ← resume 追加到同一线程
JOB-1 拿到 768B（第一轮 3 条 agent_message）
JOB-2 拿到 381B（第二轮 1 条）                     ← 没有重读第一轮
```

最后一行是关键：**若「哪一轮是我们的」判断有误，第二轮会再次返回 768B。**

**为什么还要第三次。** 终端面板不新增一层：`tui-transport.ts` 的 `launch` 早就是注入点（注释写着 *"Injected so the watching half can be proved offline"*），面板只是它的第二个实现 —— 从 osascript 开 Terminal.app，换成 StagePass 自己持有一块 pty。但有两件事各自都动了 L2 的地基，所以**这一层需要第三次验收**：

1. **binding 粒度改了** —— 主键从 `change_id` 变成 `(change_id, phase)`（见 §6.5）。两个方向的唯一性约束都要重写，`ThreadAlreadyBoundError` 的判定跟着改。
2. **执行通道换了** —— 从"把命令交给 Terminal.app、句柄扔掉"变成"StagePass 自持 pty"。这与第二次验收必须重做是同一个理由：换的是执行通道本身。

**已通过的两次不因此作废**，它们验的是 osascript 版；第三次验的是 pty 版加新粒度。§9.2 按两个实现分别记状态。

### 6.4 TUI 的 turn 怎么算结束（2026-07-28 实测）

不读 Codex 的私有数据库。**thread id 就在 rollout 的文件名里**：

```
~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<时间戳>-<threadId>.jsonl
```

`codex resume` **追加到同一个文件**，turn 边界是显式的 `event_msg`。实测一个文件里三个 turn（前两个来自 mcp-server，第三个来自 TUI resume）：

```
行2   task_started    行10  user_message    行27  task_complete
行28  task_started    行31  user_message    行36  task_complete
行38  task_started    行45  user_message    行57  task_complete
```

所以 StagePass 的做法是：起 turn → 盯住这个文件 → **等自己那次 `user_message` 之后的第一个 `task_complete`** → 从中间读 `agent_message`。

四个已知的坑，实现时必须处理，不许假设：

1. **不能等进程退出** —— TUI 跑完一个 turn 仍然开着，那是它的正常行为，不是卡住。
2. **必须认自己那一次** —— 同一个文件里有历史 turn，认错就会拿到上一轮的答案。
3. **文件可能还不存在** —— 一个全新 Change 的第一个 turn 要先创建它。
4. **同一个阶段线程，任何时刻只许有一个活着的进程** —— 两个 `codex resume <同一个 id>` 同时往一个 rollout 追加，第 2 条就废了：turn 边界交错，"自己那一次"会认到别人的答案上。理由与责任方见 §6.5 规则 5。

依赖的只是「文件名含 thread id」+「rollout 是 jsonl」两个约定，比读 `state_5.sqlite` 弱得多，但**仍然是约定不是公开接口** —— 记在 §10 的已知风险里。

### 6.5 阶段线程：一个 (Change, 阶段) 一个 thread（2026-07-28 定）

**绑定粒度是「一个 (Change, 阶段) 一个 Codex thread」，不是「一个 Change 一个」。**

#### 理由是 fence，不是「乱」

「一个 Change 一个终端会很乱」是真的，但那是审美理由，不足以定架构。真正的理由是 §4 概念 3：*决策绑定它所依据的快照；快照变了，旧决策失效而不是静默生效。*

一个 Change 一个线程，意味着 Spec 阶段的裁决**有一部分依据活在 Codex 的对话历史里** —— 模型记得 PRD 阶段聊过什么，而那段记忆不在 StagePass 的任何快照中。**fence 管不到它。这是结构性缺口，不是 bug。**

一阶段一线程之后，跨阶段信息**只能走文档**（PRD → Spec → TechSpec …），而文档正是能快照、能哈希、能 fence 的东西。**所以这不是把界面弄整齐，是让 fence 真的覆盖全部输入。**

第二条实际理由是上下文长度：十二个阶段 × 每阶段若干 turn，加上 L4 的红/蓝/裁判轮次，全塞一个线程，而 `codex resume` 每次恢复完整历史。

这笔交换的代价要记在账上：**每个阶段的开场 prompt 必须自己带上游文档**，组题工作变重。方向与 §5.2「StagePass 全权组题」一致，并且让"模型知道什么"从隐式变显式。

#### 五条规则

1. **十二个阶段**（以 `src/domain/phase.ts` 的 `PHASES` 为准），`Done` 是终态不发生 turn，所以**实际有线程的是 11 个**。
   - 老树曾在这件事上自相矛盾（两处各说了一个别的数字，都不匹配产品定义）。**这里只有这一个数字，不要引入第三个。**
2. **重入复用同一线程。** `Fix` 不在 `advancesTo` 里，一个 Change 可以进 Fix 很多次；设计阶段被拒是「原地再来一轮」。所以 `(Change, 阶段)` 在时间上不唯一 —— **重入 `codex resume` 同一个阶段线程，不新开。**
   - 理由：Fix 第三轮最需要的上下文，恰恰是「前两轮改了什么、为什么还没过」，那正在同一线程里。
   - 代价：被打回多次的阶段线程会变长。认了 —— 它长的是**同一件事**的历史，不是十二件事的。
   - 固定 11 块使面板可穷举，与 §4 概念 1「阶段与转移可穷举」同构；每次新开会让面板变成一个会长的列表，那正是老树「不知道有多少东西活着」的形状。
3. **跨阶段信息只能走文档。** 这是那笔交换的另一半，必须和粒度写在一起，否则下一个人会以为上下文还能靠对话历史传。
4. **不需要 11 个进程同时活着。** rollout 文件是持久的，任何一块随时能用 `codex resume` 复活、历史不丢。常驻 1–2 个，其余是**可复活的空壳**：点开就活，关掉不丢。
5. **同一个阶段线程，任何时刻只许有一个活着的进程。** 两个 `codex resume <同一个 id>` 同时往一个 rollout 追加，§6.4 坑 2 就废了 —— turn 边界交错，认错就拿到别人的答案。一阶段一线程降低了这个风险（并发的是不同文件），但**终端面板必须保证它**，因为面板让「同时开着好几块」变成常态。

#### 与对抗阶段的关系（容易搞错，写死）

**L4 的对抗阶段在面板里仍然只有一块终端 —— 裁判那块。** 红蓝是裁判派生的子 Agent，不是终端。任何"对抗阶段开三块面板"的设计直接违反 §5.7。

### 6.6 阶段线程的权限：走 invocation，一阶段一套

这是 §6.5 的直接推论，不是"顺便配一下"：粒度到了阶段，权限就该到阶段。

#### 现状（从 `~/.codex/config.toml` 与 `codex --help` 实读，0.144.4）

- `[projects."<绝对路径>"] trust_level = "trusted"` 机制**已存在**，本项目目录**已经在里面**，且其上层目录本身也是 trusted、桌面下的项目都已继承。**不要把「为项目开信任」写成待办 —— 它已经是事实。**
- **但 `trust_level` 只管一道门：「你信不信这个文件夹」。它不管审批策略。** 这两件事分开，是这一节存在的原因。

真正的两个开关：

| 开关 | 可选值 |
|---|---|
| `-s, --sandbox` | `read-only` / `workspace-write` / `danger-full-access` |
| `-a, --ask-for-approval` | `untrusted` / `on-request` / `never` |

`never` 的原文是 *Never ask for user approval. Execution failures are immediately returned to the model.* —— 零提示；被沙箱挡住的命令直接把错误回给模型。**已实测 `codex resume` 接受这两个参数。**

> ### ⚠ `-a never` 会掐死 elicitation（2026-07-29 实测，可复现）
>
> **`-a never` 不只管 shell 命令的审批，它同时让 Codex 自动拒绝 MCP 的 `elicitation/create`。** 而 elicitation 是 StagePass 唯一的问人通道（§5.2b）—— 用了 `never`，StagePass 就再也问不到人，且失败是静默的：插件收到一个格式完全合法的 `{"action":"decline"}`，看起来和"人按了 Esc"一模一样（§5.6）。
>
> 判据是 `pnpm probe:elicit <policy>`，各跑两次，结果稳定：
>
> | `-a` | `elicitation/create` | 选择器画出来了吗 | 客户端回什么 |
> |---|---|---|---|
> | `never` | 发出 | **没有** | `{"action":"decline"}`，秒回 |
> | `on-request` | 发出 | **画了** | `{"action":"accept","content":{"decision":"reject"}}` |
>
> 所以：**任何可能要问人的 turn，`-a` 不许是 `never`。** 这条比「零提示」优先 —— 零提示是舒适度，问得到人是这个产品本身。

> **版本陷阱**：旧文档和旧记忆里有两个此版本**不存在**的写法 —— 一个"全自动"总开关，以及一个介于 `on-request` 与 `never` 之间的档位。照抄会得到一个启动即失败的命令行。**以 `codex --help` 实读为准**，本文不复述那两个名字，免得被人 grep 走。

#### 决定一：不写进 `~/.codex/config.toml`

1. **StagePass 去改用户的全局 config，是 §7 M5「读接口不许写」的反面**，性质等同老树 `listBaselineDocs` 在 GET 里 scaffold 十个文件。
2. **会漏。** 全局配置会影响用户在别的终端、别的项目里手动跑的 codex。
3. **成本是一行。** `src/codex/tui-transport.ts` 已在拼 flags 数组，`-s` 就在那里。

（若将来需要文件形态，`-p, --profile <NAME>` 会层叠 `$CODEX_HOME/<name>.config.toml`，比改主 config 干净。默认走 flags。）

#### 决定二：一阶段一套权限

`-s` / `-a` 本就是 per-invocation，`CodexTuiTransportOptions.sandbox` 已经是参数 —— **这一层是免费的**：

| 阶段 | 给什么 |
|---|---|
| PRD / Spec / TechSpec / Plan / TestPlan | `-s read-only -a on-request` —— 这些阶段模型只该读和产出文档，**而它们正是要问人的阶段** |
| Build / Fix | `-s workspace-write -a on-request` |
| Review / QA | 沙箱按是否需要跑测试决定；`-a` 同上 |

**约束模型能碰什么的是 `-s`，不是 `-a`。** 上表用 `-s` 划边界（read-only 的阶段改不了任何文件，这一条不因 `-a` 而松动），`-a` 一律留在 `on-request` —— 因为 `never` 会顺带掐死 elicitation（见上面那个方框）。

**写进全局 config 反而做不到这个区分。**

#### 决定三：不用绕过沙箱的那个开关

help 原文把它标为 *EXTREMELY DANGEROUS. Intended solely for running in environments that are externally sandboxed.* —— 给已经跑在容器里的场景用的，本机不是。

`-s workspace-write` 已经划出边界：模型能改工作区，不能改工作区外面。加上绕过之后，代价是模型可在整机执行任意命令且无人过问 —— 而收益并不存在：**它绕过的是审批，而我们现在需要的恰恰是审批通道开着**（elicitation 走的就是那条路）。需要往仓库外写时，用 **`--add-dir <DIR>` 精确开口子**。

> 这一条的理由 2026-07-29 改过一次。原话是"`-a never` 已经达成零提示，所以 bypass 的收益为零"。那个前提已被实测推翻 —— `never` 不能用。结论不变，但**不要再用「零提示」去论证它**。

### 6.1 L0 / L1 是真正的底层

它们必须能在**没有 AI、没有 Codex、没有网络**的情况下被完整证明。这是"底层要好好搭建"的操作定义：**L0/L1 的任何行为，都能用一个离线测试跑出来给人看。**

### 6.2 L1 必须额外交付「假答案」能力

答案路径要能被**伪造的 elicitation 返回**驱动。这样 L3 的全部逻辑（校验链、动作解析、状态推进）可以离线验证，只剩"选择器是不是真的出现了"这一件事需要人在 TUI 里选。

**理由是实测的**：L2 往上的每一次验收都要占用你本人的时间，这个设计是为了把这个成本压到最低。（`ScriptedTurnRunner` 已经是这条原则在 L1 的实现。）

### 6.3 层间依赖单向

上层可以 import 下层，**下层永远不许 import 上层**。做成常驻测试。

## 8. 与老树的关系

- 老树是**参考资料**，不是基座。同仓库新目录，能随时 grep 对照。
- 移植纪律：**先读、后写、再删**。读老树某个概念的实现 → 在新树按新需求重写 → 把老树对应部分标记为已移植。
- **全部移植完之后，老树整体删除。** 不保留"以后可能有用"的部分 —— 那正是遗留的定义。
- 老树里唯一有实测证据的部分是 Codex 插件（16 条回执落库）。它也重写，但它已验证过的行为（jsonl 一卡一行追加、跨进程卡片记忆、widget 协议）优先照抄。

## 9. 验收

### 9.1 终局

一个 Change 从 PRD 走到 Done，**人只在 Codex TUI 里做决定**，做完回 StagePass 看见状态已经前进。全程 **StagePass 不渲染任何执行过程或选择界面**。

### 9.2 逐层（每层过了才允许动下一层）

| 层 | 通过条件 | 现状 |
|---|---|---|
| L0 | 所有合法转移被穷举测试；非法转移被拒；每次转移落账本；全部离线 | ✅ |
| L1 | 崩溃注入后能恢复；租约过期能被接管；重复命令幂等；fence 冲突被拒；全部离线 | ✅ |
| L2 · osascript 版 | `codex resume` 起一个真 turn，StagePass 按 §6.4 认出它结束、从 rollout 拿到结果，binding 与 turn 落库 | ✅ 2026-07-28 通过（两次：先 mcp-server，再 TUI） |
| L2 · pty 版 | 同上，但执行通道是 StagePass 自持的终端面板 pty；**且** binding 按 `(change_id, phase)` 落库、两个方向的唯一性都重新成立（§6.5）。验收方式：面板建好之后**一次真选择验完**，不为它单独安排一次 L3 演练 | ⬜ |
| L3 | 假答案驱动全链路离线通过；**且**你在 TUI 里真选一次，`changes.status` 前进 | ✅ 2026-07-28 通过 |
| L4 | 一轮真对抗结算出 gate 能用的结果 | ✅ 2026-07-29 通过 |
| L5 | rubric 出分、gap 落库并阻断；接受风险能指明具体条目 | ⬜ |
| L6 | 五个阶段的裁决都能问出来、答回来、推进状态 | ⬜ |

#### L4 验收证据（2026-07-29）

`pnpm verify:round` 真跑一轮，裁判自己派生红蓝，StagePass 从**各自的 rollout** 读结果：

```
judge      019fac7a-c8c2-7093-b509-3518aa7105ae
spawned    /root/red, /root/blue          ← 裁判真的按指定路径派生了两个子 Agent
红方自己的文件  artifactIds:[spec.md]  blockers:[]
蓝方自己的文件  blockers: 9 条，稳定 id（SPEC-SCHEMA-1 / SPEC-COORD-1 / …）
gaps 表     9 行，全部 open，opened_round=1
闸门        关着 —— 6 个 P1 + 3 个 P2 挡住它
```

关键在**蓝方那 9 条是从蓝方自己的文件读的，没有经过裁判转述**（§5.7 的第二条理由）。用 `pnpm verify:round --read <thread>` 可以对同一个线程独立复核一遍，不碰任何数据库。

### 9.3 常驻（任何时候都不许红）

零调用者计数 = 0；层间依赖单向；`enum` 里的选项全部可执行；一个概念一个名字；**pty 的输出在 StagePass 这一侧永远不落成 string**。

#### 最后一条：pty 输出不可解释

它替换掉原先的「`src/` 里没有任何渲染代码」。**换判据是因为原判据在终端面板之后不再适用，不是因为放松了要求** —— 新判据必须和那条 grep 一样机械。

判据本体，两句话：**允许把 pty 的字节原样转发给浏览器；禁止读懂那些字节。** 落成可查的形式：

- **类型上不给出 string。** pty 输出在 `src/` 里只以 `Uint8Array` 流转。这条链路上不许出现返回 `string` 的签名、不许给 `encoding` 参数、不许 `Buffer.toString()`。**想解释就得先拿到 string，而类型上根本拿不到，于是"想解释"在编译期就失败。**
- **不许有内容判断。** pty 输出上不许作用 `toString()`、正则匹配、`JSON.parse`，以及 `includes` / `indexOf` 这类按内容分支的调用。服务端只做转发。
- **跑什么能知道它过没过**：`pnpm check`。严格 typecheck 挡住类型那一半；另一半由 `src/architecture.test.ts` 里一条常驻测试挡住（与该文件现有四条同形，**随终端面板一起落地**）。一条命令，红或绿，**不需要任何人判断"这段算不算解释"**。

**这一条是终端面板被接受的前提条件，不是一条没来由的洁癖约束。** 因果关系必须写出来：

被否决过的那条路（§2.4 表格第三行）是 StagePass 解析 Codex 的事件流、**自己理解语义再画界面**。终端面板与它的区别**只有「不理解语义」这一条** —— 别的都一样：看的地方都回到了 StagePass，字节都流经 StagePass 的进程。所以这条区别一旦松掉，面板就是那条被否决的路。

而「不许解释语义」如果要靠人判断，它一定会滑：先是"turn 结束加个高亮吧"（要 parse），再是"选择器滚上去看不见了，顶部加个提示吧"（要 parse），最后回到那条被否决的路上。每一步单独看都很合理，这正是滑坡的形状。

**所以判据必须机械，不能靠自觉。** §2.2 说重建的首要理由是「没人能判断哪部分是真的」；判据一旦需要判断，那个问题就原样回来了。**面板成立的条件就是这条判据成立** —— 谁要放宽它，等于重开 §2.4 第三行那个已经被否决的决定。

## 10. 明确不做

- 多 Provider、Claude 兼容、模型路由
- 网页上的业务决策入口（含"紧急表面"—— 新树不预留）
- host-attested MCP / private IPC / bundle attestation / app-server 私有协议
- **`ui://` HTML widget，以及任何形式的「卡片」** —— 实测走不通，见 §2.4
- **StagePass 解析 Codex 的输出、理解语义之后自己画界面** —— 就是 §2.4 表格第三行那条被用户否决的路。这条已从"曾经做过"变成"明确不做"，判据见 §9.3
  - 与之相对，**现在要做**的是：托管一块 pty，让 Codex 在里面自己画。**托管不是渲染** —— 搬运字节允许，读懂字节不允许。这两件事是分开的，别当成一条被放宽了
- Live QA
- **老树任何东西的自动继承**

**已知风险（不是不做，是知道它可能咬人）**：

1. **turn 结束检测依赖两个约定** —— rollout 的文件名与 jsonl 格式（§6.4）。Codex 改了它们就会断。比老树押注私有 IPC 协议 + bundleVersion 白名单弱得多，但不是零。断掉时的表现必须是**明确失败**，不能是静默等待 —— 那正是老树 82 个 turn 卡在 `running` 的形状。

2. **依赖面变大。** 新树的运行时依赖很少，终端面板是第一次引入前端栈。这是真实成本，记在这里。
   - **「node-pty 要编译、Node 升级要重编」这个担心已被实测排除**（预编译包，Node 25.9.0 上 8 秒装完）。**不要把已排除的风险当成风险留着** —— 那会让下一个人为一个不存在的问题做设计。
   - 真正要记的是 `spawn-helper` 装完没有执行位（prebuild 里是 `-rw-r--r--`，表现为一句不指明文件的 `posix_spawnp failed`）。**它属于安装步骤，不属于风险** —— 固化进安装步骤即可。

3. **pty 里还剩两件事没验，要逐条确认后才能写成事实**：① 在 pty 里敲 `/app` 能否唤起 Desktop；② SIGWINCH（改窗口尺寸）下的表现。
   - 对照，这两条**已经不是未知，不要再列成风险**：
     - **「TUI 在浏览器 pty 里渲染正常」** —— 用户目视确认。
     - **「elicitation 选择器在 pty 里可用」** —— 2026-07-29 机械验过并复现（`pnpm probe:elicit`）：选择器画得出、方向键选得动、回车提交，客户端回 `{"action":"accept","content":{"decision":"reject"}}`。**这是面板方案的地基，现在它是绿的** —— 但只在 `-a on-request` 下成立，见 §6.6 那个方框。

**面板同时带来一个收益，不只是好看**：今天 `defaultLaunch` 是 `detached: true` + `.unref()`，**StagePass 连子进程句柄都扔了**，不知道 TUI 还在不在 —— 所以 §6.4 坑 1（不能等进程退出）只能靠超时兜底。**pty 握在 StagePass 手里之后，这个风险从「靠超时猜」变成「进程死了立刻知道」。** 顺带去掉 osascript 这个 macOS 绑定。

> `TUI` 曾经在这一列里（"当前不开发 TUI"，需求文档 §5.5）。那说的是**StagePass 自己的 TUI 客户端**，现在仍然不做。本文说的 TUI 是 **Codex 的** TUI —— 是执行与交互面，不是 StagePass 的第二个前端。两者不要混。
