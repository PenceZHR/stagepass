# 九个阶段的产出模板与评分标准

> **这份文档是从代码生成的**（`domain/phase-template.ts` + `domain/rubric-defaults.ts`），
> 不是手抄的。改了代码就重新生成：`node --import tsx scripts/dump-rubrics.ts`

> **它们是起点，不是权威。** 真正的权威是你在面板「标准」页签里改出来的那一版 ——
> 这里只保证一个新项目不是从空白开始。改动会随「把出厂标准升到最新版」进到已有项目，
> **但只升从没被人改过的那些**。

## 怎么读这张表

| | |
|---|---|
| **模板** | 红方**必须照着写**，标题原样用。缺一节 → 开一条 `TEMPLATE-<节>` 挡住闸门（P1，你能 waive） |
| **producer 标准** | 反方逐条判 yes/no，**挂了节的出厂就阻断**。这是这个阶段的尺度 —— 挂不上的问题就是越界，不许报 |
| **critic / verdict 标准** | 讲的是**方法**不是产物，十二个阶段共用一份，永远不挂节、永远不阻断 |

**有模板的**：PRD / Spec / TechSpec / Plan / TestPlan / Review / QA / Merge / Retro

**没有模板的**：Build / Fix —— 它们交的是 commit 不是文档，套模板等于造一份永远缺齐所有节的产出。

# PRD

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（7 节）

```markdown
## 要解决谁的什么问题
谁在用、他今天怎么受阻、不解决会怎样。不要写要做什么功能。

## 做完之后什么变了
可观察的结果，不是功能清单。

## 验收标准
每条可观察、可测量 —— 到「一个称职的实施者照着做不会做错」为止，不要求每个词都能唯一裁定。

## 这次不做什么
明确排除掉的。

## 前提
至少一条会让整个方案不成立的前提，以及怎么判它成不成立。

## 已经定死的约束
人已经拍死、这次不容商量的：技术栈、平台、必须兼容什么、不许动什么。**只转述，不新定** —— 这里写的每一条都要说得出是谁定的。没有就写「没有」。

## 留给下游决定的
有意留给下游去定的，写明留给哪个阶段。架构、模块划分、接口、测试用例、实现步骤都不在 PRD 里定；**已经被人定死的不写这儿，写上一节**。
```

## 评分标准 · producer（13 条）

**要解决谁的什么问题**（`problem`）

- 写清楚了用的人是谁、他今天怎么受阻，而不是先写要做什么功能
- 写了不解决会怎样，而不只是说「需要改进」

**做完之后什么变了**（`outcome`）

- 写的是做完之后可观察的变化，不是一张功能清单

**验收标准**（`acceptance`）

- 每条验收标准都可观察、可测量
- 验收标准细到「一个称职的实施者照着做不会做错」就够了，没有去追每个词的唯一裁定
- 每条验收标准都对得上前面写的那个结果，没有凭空多出来的

**这次不做什么**（`out-of-scope`）

- 明确写出了这一次不做什么

**前提**（`assumption`）

- 列出了至少一个会让整个方案不成立的前提
- 每条前提都写了怎么判它成不成立

**已经定死的约束**（`fixed`）

- 这一节里的每一条都说得出是谁定的，没有把自己的设计决定混进来当成既定约束
- 没有定死的约束时明写了「没有」，而不是留空

**留给下游决定的**（`deferred`）

- 架构、模块划分、接口、测试用例、实现步骤都没有在这一份里**新定**；人已经定死的写在「已经定死的约束」那一节，不写这儿
- 有意留给下游的每一项都写明了留给哪个阶段


# Spec

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 这份 Spec 覆盖 PRD 的哪几条
逐条对应回 PRD，写清哪条验收标准由这里的哪几段行为满足。没有凭空多出来的。

## 行为
每条行为的正常路径：给什么、做什么、出什么。

## 边界和出错
每条行为在边界上和出错时的表现。没有「其余情况未定义」这种写法。

## 用词
这份文档里的关键词各是什么意思。和上游一致，同一个概念不发明第二个名字。

## 留给下游决定的
有意不在 Spec 定的，写明留给哪个阶段。数据怎么存、模块怎么划分、用什么技术都不在 Spec 里定 —— 需要提到就写在这一节。
```

## 评分标准 · producer（8 条）

**这份 Spec 覆盖 PRD 的哪几条**（`scope`）

- 每条需求都能对应回 PRD 里的某一条，没有凭空多出来的
- PRD 的每条验收标准都说明了由这里的哪几段行为满足，没有漏掉的

**行为**（`behaviour`）

- 每条行为都写清了给什么、做什么、出什么

**边界和出错**（`edge`）

- 每条行为都写了它的边界情况和出错时的表现
- 没有用「其余情况未定义」这类写法把边界推给下游

**用词**（`terms`）

- 用词和上游文档一致，没有为同一个概念发明第二个名字

**留给下游决定的**（`deferred`）

- 数据怎么存、模块怎么划分、用什么技术都没有在这一份里**新定** —— 上游已经定死的照抄过来不算
- 有意留给下游的每一项都写明了留给哪个阶段


# TechSpec

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（6 节）

```markdown
## 数据怎么存、状态怎么迁移
不只是模块怎么划分。哪些是权威、哪些是镜像，状态之间怎么走。

## 接口与契约
模块之间谁调谁、传什么、返回什么、出错时返回什么。

## 选择和它的代价
每一个技术选择都写代价，不只写好处。没有代价的选择说明还没想。

## 最可能出错的一处
指名一处，写为什么是它。并列罗列多项风险不算回答了这一节。

## 对得回 Spec
这里的每条设计对应 Spec 的哪一条。没有引入 Spec 里不存在的行为。

## 留给下游决定的
有意留给 Plan 或 Build 的，写明留给哪个阶段。
```

## 评分标准 · producer（8 条）

**数据怎么存、状态怎么迁移**（`data`）

- 写清楚了数据怎么存、状态怎么迁移，而不只是模块怎么划分
- 说清了哪些是权威、哪些是镜像

**接口与契约**（`interfaces`）

- 模块之间谁调谁、传什么、返回什么都写了，出错时返回什么也写了

**选择和它的代价**（`tradeoffs`）

- 每一个技术选择都写了它的代价，不只是好处

**最可能出错的一处**（`riskiest`）

- 指名了最可能出错的一处，而不是并列罗列多项风险

**对得回 Spec**（`traceability`）

- 没有引入 Spec 里不存在的行为
- 每条设计都对得回 Spec 的某一条

**留给下游决定的**（`deferred`）

- 有意留给下游的每一项都写明了留给哪个阶段


# Plan

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 步骤
每一步一个能独立交付的东西。一步做完就能看出对不对。

## 依赖和顺序
哪几步必须先后，为什么。没有两步在改同一处却没定顺序。

## 每一步怎么验
每一步各自的判据，不要等到最后才知道对不对。

## 出问题怎么退
实施到一半失败了怎么退回去。只写停止条件不算回答了这一节。

## 哪一步风险最高
指名一步，以及为什么先做或后做它。
```

## 评分标准 · producer（5 条）

**步骤**（`steps`）

- 每一步都有一个能独立交付的东西，不是一句「做 X 相关的工作」

**依赖和顺序**（`order`）

- 步骤之间的依赖是明确的，没有两步在改同一处却没定顺序

**每一步怎么验**（`verification`）

- 每一步都能独立验证，不需要等到最后才知道对不对

**出问题怎么退**（`rollback`）

- 写了实施到一半失败时怎么退回去，而不只是停止条件

**哪一步风险最高**（`riskiest`）

- 指名了哪一步风险最高，以及为什么先做或后做


# TestPlan

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 验收标准到用例的映射
上游每条验收标准对应这里的哪几个用例。逐条列，不留空。

## 用例
每个用例：给什么输入、在什么前置状态下、期望什么输出。

## 失败长什么样
不只写成功。每个用例失败时看到的是什么，怎么和「测试自己写错了」区分开。

## 哪些必须通过
区分「必须通过」和「知道会失败但先记着」，后者写明为什么先记着。

## 怎么跑
命令、环境、前置条件。别人照着能重现。没有「跑一遍看看」这种写法。
```

## 评分标准 · producer（7 条）

**验收标准到用例的映射**（`coverage`）

- 上游每条验收标准都至少有一个用例对着它，逐条列出来了

**用例**（`cases`）

- 每个用例都写了输入、前置状态和期望输出

**失败长什么样**（`failure`）

- 写了失败长什么样，而不只是成功长什么样
- 写了怎么把「功能没实现」的失败和「测试自己写错」的失败区分开

**哪些必须通过**（`gating`）

- 区分了「必须通过」和「知道会失败但先记着」，后者写了为什么

**怎么跑**（`how`）

- 命令、环境、前置条件都写了，别人照着能重现
- 没有把「跑一遍看看」当成一条用例


# Build

反方在这一阶段：**自己去看，照旧交问题清单（无上限）**

**没有模板** —— 产出是一个 commit。

## 评分标准 · producer（9 条，都不挂节、都不阻断）

- 改动范围和 Plan 一致，没有顺手做计划外的事
- 命名和上游文档一致：Spec / TechSpec 里叫什么，代码里就叫什么，没有为同一个概念在代码里发明第二个名字
- 实现的行为对得上 Spec 写的那几条；多做或少做的地方在代码或报告里写明了为什么
- 新写的代码和它周围、以及它的直接调用方风格一致：命名、错误处理、文件位置都跟着现有做法，没有在同一个仓库里另起一套
- 每一处不明显的决定都在代码里留下了为什么
- 同一条规则只有一个定义处，没有把同一份逻辑抄成第二份
- 新增或改名的每个导出都有调用方，没有留下没人调用的代码或半途的开关
- 受影响的调用点都跟着改了，没有把现成的调用方留在对不上的状态
- 交出了运行证据：跑了哪条命令、输出是什么，而不是只说「应该能跑」


# Review

反方在这一阶段：**自己去看，照旧交问题清单（无上限）**

## 填写模板（5 节）

```markdown
## 审的是哪一个 commit
写出 sha。不要笼统地说「当前代码」—— 这份报告会被下一轮和下一个阶段当事实引用。

## 逐条对照上游的结果
对着 Spec 和 TechSpec 一条条看的结果，不是通读一遍谈感受。

## 发现的问题
每条指明文件和位置，看的人能直接翻到那儿。没有就明写没有。

## 哪些必须改
区分「必须改」和「可以这样也可以那样」。

## 错误路径和边界
查过的错误路径和边界情况，不只是主流程。
```

## 评分标准 · producer（6 条）

**审的是哪一个 commit**（`subject`）

- 写清楚审的是哪一个 commit，而不是笼统地说「当前代码」

**逐条对照上游的结果**（`against`）

- 逐条对照了 Spec 和 TechSpec，而不是通读一遍谈感受

**发现的问题**（`findings`）

- 每条意见都指明了文件和位置，看的人能直接翻到那儿
- 没有发现问题时明写了没有，而不是留空

**哪些必须改**（`severity`）

- 区分了「必须改」和「可以这样也可以那样」

**错误路径和边界**（`paths`）

- 检查了错误路径和边界，而不只是主流程


# Fix

反方在这一阶段：**自己去看，照旧交问题清单（无上限）**

**没有模板** —— 产出是一个 commit。

## 评分标准 · producer（4 条，都不挂节、都不阻断）

- 每一条修的都对应一条具体的问题，没有夹带
- 说明了为什么这么修能让那条问题不再成立

# QA

反方在这一阶段：**自己去看，照旧交问题清单（无上限）**

## 填写模板（5 节）

```markdown
## 测的是哪一个 commit
写出 sha。不要笼统地说「当前代码」。

## 按 TestPlan 逐条执行的结果
一条都不跳。跳过的写明为什么。

## 失败的用例
实际输出是什么、它来自哪一条用例。不只写「没过」。

## 有没有让别处退化
这一轮的改动之外的地方，查过没有、结果是什么。

## 怎么重现
跑的命令和环境写下来，别人照着能重现。
```

## 评分标准 · producer（5 条）

**测的是哪一个 commit**（`subject`）

- 写清楚测的是哪一个 commit，而不是笼统地说「当前代码」

**按 TestPlan 逐条执行的结果**（`executed`）

- 按 TestPlan 逐条执行了，没有跳过，跳过的写明了为什么

**失败的用例**（`failures`）

- 失败的用例记下了实际输出和它来自哪一条用例，而不只是「没过」

**有没有让别处退化**（`regression`）

- 确认过这一轮的改动没有让别处退化，并写了是怎么确认的

**怎么重现**（`repro`）

- 跑的命令和环境写下来了，别人照着能重现

# Retro

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（4 节）

```markdown
## 这一次真实发生了什么
真实发生的事，不是应该发生的事。
```

**这一次真实发生了什么**（`happened`）

- 写的是这一次真实发生的事，不是应该发生的事

**关于流程本身的**（`process`）

- 至少有一条是关于流程本身的，而不全是关于代码

**下次会不一样的做法**（`next`）

- 每条结论都能落到一个具体的下次会不一样的做法

**这次做对的事**（`kept`）

- 记下了这次做对的事，不只是做错的

# 所有阶段共用的两份

> 它们讲的是**方法**：怎么质疑一份东西、怎么裁一场争论。这两件事在 PRD 和在 Merge
> 是一样的，所以只有一份 —— 给每个阶段各抄一份只会得到十一份同样的话，然后各自漂移。

## critic · 反方怎么质疑

- 它说的每一句都建立在实际看过的东西上，没有靠猜、也没有假设一件它没核实过的事
- 每条判定都写了依据，而不只是一个 yes 或 no
- 判 no 的每一条都说得出产出里是哪一节、哪一句不满足它
- 那句整体判断说清了这一轮够不够格以及为什么，不是复述逐条判定

**Build 额外多判这几条**（追加，不是另一份）：

- 每条问题都指向产出里的具体位置，而不是泛泛地说「不够清楚」
- 每条问题都说明了它为什么是问题，而不只是说它存在
- 同一个问题在后续轮次沿用了同一个 id，没有换个说法重开一条
- 除了功能对不对，也看了编码上的毛病：风格和周围的代码对不对得上、命名和上游文档对不对得上、同一条规则有没有被抄成两份

## verdict · 裁判怎么裁

- 对每一条已经存在的问题都明确表了态，没有沉默略过任何一条
- 关闭任何一条时都写清楚了它为什么不再成立，而不是「已修复」四个字
- 结论建立在它自己读过的上游文档和两方产出上，而不是复述正方或反方说过的话
- 没有把「这一轮没提到」当成「已经解决」
- 给出了「还要不要再来一轮」的结论，并写清楚依据是什么

**Build 额外多判这几条**（追加，不是另一份）：
