# 环 v3 八个阶段的产出模板与评分标准

> **这份文档是从代码生成的**（`domain/phase-template.ts` + `domain/rubric-defaults.ts`），
> 不是手抄的。改了代码就重新生成：`node --import tsx scripts/dump-rubrics.ts`

> **它们是起点，不是权威。** 真正的权威是你在面板「标准」页签里改出来的那一版 ——
> 这里只保证一个新项目不是从空白开始。改动会随「把出厂标准升到最新版」进到已有项目，
> **但只升从没被人改过的那些**。

## 怎么读这张表

| | |
|---|---|
| **模板** | 红方**必须照着写**，标题原样用。缺一节 → 开一条 `TEMPLATE-<节>` 挡住闸门（P1，你能 waive） |
| **producer 标准** | 反方逐条判 yes/no，**挂了节的出厂就阻断**。这是这个阶段的尺度 —— 挂不上的问题就是越界，不许报 |
| **critic / verdict 标准** | 讲的是**方法**不是产物，十二个阶段共用一份，永远不挂节、永远不阻断 |

**主线八个阶段每个都有模板**：PRD / Spec / Arch / BuildPlan / TestPlan / Build / Test / QA

**退休的不在这份文档里**（TechSpec / Plan / Review / Fix / Merge / Retro / Done）——名字只为读历史而留着，没有 Change 会再走到它们。

# PRD

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（7 节）

```markdown
## 要解决谁的什么问题
谁在用、他今天怎么受阻、不解决会怎样。不要写要做什么功能。**用的人要点得出名字**：哪一类人、在什么场景下，不是一句「用户」；怎么受阻要写出他今天实际走的那几步、卡在哪一步，不是「体验不好」。

## 做完之后什么变了
可观察的结果，不是功能清单。每条写清谁、在什么时候、看到什么不一样了；和今天比是从什么变成什么 —— 能写出数的地方写数，「更快」「更稳」后面必须跟着从多少到多少。

## 验收标准
每条可观察、可测量 —— 到「一个称职的实施者照着做不会做错」为止，不要求每个词都能唯一裁定。但**下限是三样都写出来**：在什么条件下、量的是哪个指标、到什么数（或什么状态算通过）。这两句不冲突：前一句说的是不必再往下抠词，这一句说的是这三样一样都不能少。

## 这次不做什么
明确排除掉的。每条点到具体的那件事，不是一个大类 ——「暂不做性能优化」不算一条，要写出不做的是哪个场景下的哪件事，以及不做它谁会受影响。

## 前提
至少一条会让整个方案不成立的前提，以及怎么判它成不成立。判法要写成**一个做得出来的动作加一条明确的分界**：谁去做什么、看到什么就算它不成立 ——「需要进一步验证」不是判法。

## 已经定死的约束
人已经拍死、这次不容商量的：技术栈、平台、必须兼容什么、不许动什么。**只转述，不新定** —— 这里写的每一条都要说得出是谁定的。没有就写「没有」。每条要点到名字和版本：哪个框架、哪个版本、哪个平台、哪个不许动的文件或接口——「沿用现有技术栈」没说出任何一个名字，下游照样得猜。

## 留给下游决定的
有意留给下游去定的，写明留给哪个阶段。架构、模块划分、接口、测试用例、实现步骤都不在 PRD 里定；**已经被人定死的不写这儿，写上一节**。每条除了写留给哪个阶段，还要把**要它答的那个问题**写出来 ——「架构留给 Arch」不算一条，「A 和 B 要不要合成一个模块，留给 Arch」才是。
```

## 评分标准 · producer（15 条）

**要解决谁的什么问题**（`problem`）

- 写清楚了用的人是谁、他今天怎么受阻，而不是先写要做什么功能
- 写了不解决会怎样，而不只是说「需要改进」
- 用的人点到了是哪一类人、在什么场景下，并写出了他今天实际走的那几步卡在哪一步，没有停在「用户」「体验不好」这种谁都套得上的说法

**做完之后什么变了**（`outcome`）

- 写的是做完之后可观察的变化，不是一张功能清单

**验收标准**（`acceptance`）

- 每条验收标准都可观察、可测量
- 验收标准细到「一个称职的实施者照着做不会做错」就够了，没有去追每个词的唯一裁定
- 每条验收标准都对得上前面写的那个结果，没有凭空多出来的
- 每条验收标准都写出了条件、指标和数值（或什么状态算通过），没有一条停在「更快」「更稳定」「体验更好」这种量不出来的词上

**这次不做什么**（`out-of-scope`）

- 明确写出了这一次不做什么

**前提**（`assumption`）

- 列出了至少一个会让整个方案不成立的前提
- 每条前提都写了怎么判它成不成立

**已经定死的约束**（`fixed`）

- 这一节里的每一条都说得出是谁定的，没有把自己的设计决定混进来当成既定约束
- 没有定死的约束时明写了「没有」，而不是留空

**留给下游决定的**（`deferred`）

- 架构、模块划分、接口、测试用例、实现步骤都没有在这一份里**新定**；人已经定死的写在「已经定死的约束」那一节，不写这儿
- 有意留给下游的每一项都写明了留给哪个阶段


# Spec

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 这份 Spec 覆盖 PRD 的哪几条
逐条对应回 PRD，写清哪条验收标准由这里的哪几段行为满足。没有凭空多出来的。**两边都要点到名**：PRD 那一条写出它的编号或原话，这里这几条写出它们的名字或编号 ——「已覆盖 PRD 的验收标准」不是一条对应关系，它两边都没点到。

## 行为
每条行为的正常路径：给什么、做什么、出什么。**每条行为要有一个名字或编号**，下游靠它引用；输入逐项列（每项叫什么、什么含义、必填还是可选、取什么值算合法），输出写出具体是什么 ——「处理请求并返回结果」一项都没交代。说的是**行为层面的输入输出，不是函数签名** —— 那些属于 Arch。

## 边界和出错
每条行为在边界上和出错时的表现。没有「其余情况未定义」这种写法。每条要写出**触发条件**（哪个输入、取什么值、在什么状态下）和**当时的具体表现**（出什么、报哪一种错、做了一半的怎么办）——「报错」不是表现，它没说是哪一种错。

## 用词
这份文档里的关键词各是什么意思。和上游一致，同一个概念不发明第二个名字。每个词要说得出**什么算、什么不算**，而不是把这个词换个说法再说一遍；和 PRD 用词不同的，写出它对的是 PRD 里的哪个词。

## 留给下游决定的
有意不在 Spec 定的，写明留给哪个阶段。数据怎么存、模块怎么划分、用什么技术都不在 Spec 里定 —— 需要提到就写在这一节。每条要把**要下游答的那个问题**写出来 ——「存储方案留给 Arch」不算，「这份状态要不要落盘、落在哪儿，留给 Arch」才是。
```

## 评分标准 · producer（10 条）

**这份 Spec 覆盖 PRD 的哪几条**（`scope`）

- 每条需求都能对应回 PRD 里的某一条，没有凭空多出来的
- PRD 的每条验收标准都说明了由这里的哪几段行为满足，没有漏掉的

**行为**（`behaviour`）

- 每条行为都写清了给什么、做什么、出什么
- 每条行为都有名字或编号，输入逐项写了名称、含义和合法取值，输出写了具体是什么；没有一条停在「处理请求并返回结果」这种一项都没交代的写法

**边界和出错**（`edge`）

- 每条行为都写了它的边界情况和出错时的表现
- 没有用「其余情况未定义」这类写法把边界推给下游
- 每条边界和出错都写出了触发条件和当时的具体表现，没有一条只写「报错」「失败」而不说是哪一种

**用词**（`terms`）

- 用词和上游文档一致，没有为同一个概念发明第二个名字

**留给下游决定的**（`deferred`）

- 数据怎么存、模块怎么划分、用什么技术都没有在这一份里**新定** —— 上游已经定死的照抄过来不算
- 有意留给下游的每一项都写明了留给哪个阶段


# Arch

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（11 节）

```markdown
## 这次动哪几个模块
已有的哪几个、新增哪几个。**每个模块写出它的目录或文件路径**，不能只给一个概念名字。每个新增的写清它为什么不能并进已有的。

## 文件与函数清单
**逐个文件列**：路径、这个文件负责什么、它导出哪几个函数或类型（**把名字写出来**）、谁调它们。新建的和要改的都列，改的写清改哪几个导出。这一节不许出现「等实现时再定」—— 定不下来的函数说明模块还没划清。

## 数据怎么存、状态怎么迁移
**每个数据结构写出它的字段名和类型**；哪些是权威、哪些是镜像；状态之间怎么走（写出状态名和触发它的那个函数）。没有持久化数据时明写「没有」，而不是跳过这一节。

## 接口与契约
**逐个写出上一节点过名的函数的签名**：参数名和类型、返回什么、出错时返回什么或抛什么。跨模块调用的每一条都要有；模块内部的私有函数不用写。「返回一个结果对象」这种不算 —— 写出它有哪几个字段。

## 新增了哪些依赖边
**每条写成「哪个文件 import 哪个文件」**，再写为什么非加不可 ——说得出少了它哪个行为做不成。没有新增时明写「没有」：这一节是 Build 反馈回流的落点，空着和「没有」是两回事。

## 边界划在哪
每个被动到的模块对外露什么、不露什么 —— **露的那些要点名到导出的函数或类型**，不能只说「只露出配置能力」。用 Spec 的词，不发明新名字。

## 想过但没选的划法，和选了的代价
至少一个没选的划法，写为什么没选（没有备选说明还没想）；**以及选了的这一套要付的代价** —— 一个只有好处的选择说明代价还没被看见。

## 最可能出错的一处
**指名一处**，写为什么是它、错了会怎样。并列罗列多项风险不算回答了这一节 —— 那等于没有判断。

## 对得回 Spec
这里的每一组决定对应 Spec 的哪一条。**没有引入 Spec 里不存在的行为**；真需要新行为，说明它是 Spec 漏了（那要打回 Spec），不是在这里补。

## 留给下游决定的
有意留给 Plan 或 Build 的，写明留给哪个阶段、以及为什么现在定不了。**「实现细节」不是理由** —— 函数名、签名、数据结构都属于这一份，推给下游的只能是「怎么排步骤」和「具体怎么写代码」。

## 机器可读的架构图（文件，不是文档里的一节）
把上面各节的结论**另存成一个 JSON 文件**：`docs/stagepass/<本 Change 的 id>/arch.graph.json`。固定形状，三个键都必须有：
`concepts`（数组，每项 `{"id", "name"}` —— 这次改动涉及的概念，id 用稳定的短英文）；
`relations`（数组，每项 `{"from", "to", "why"}` —— from/to 是概念 id，why 一句话说这条关系是什么）；
`serves`（对象，`{"仓库相对文件路径": ["概念 id"]}` —— **「文件与函数清单」那一节点过名的每个文件都要在这里认领它服务的概念**，说不出服务谁的文件说明它不该出现在清单里）。
这份文件会被机器对账（规划 vs 真实代码）并画在图谱上 —— 图没法宽泛，写不出来的关系就是还没想清的关系。
```

## 评分标准 · producer（18 条）

**这次动哪几个模块**（`modules`）

- 写清了动的是哪几个已有模块、新增哪几个；每个新增的都写了为什么不能并进已有的
- 每个模块都写出了它的目录或文件路径，没有一处只给概念名字（比如「配置模块」而不说它在哪）

**文件与函数清单**（`files`）

- 逐个文件列出了路径、职责、它导出的函数或类型的名字，以及谁调它们
- 没有一处写「等实现时再定」或「视情况而定」—— 定不下来的函数说明模块还没划清

**数据怎么存、状态怎么迁移**（`data`）

- 每个数据结构都写出了字段名和类型，说清了哪些是权威、哪些是镜像；没有持久化数据时明写了「没有」
- 状态迁移写出了状态名和触发它的那个函数，不是「状态会随流程推进」这种叙述

**接口与契约**（`interfaces`）

- 文件与函数那一节点过名的跨模块函数，这里都写了签名：参数名和类型、返回什么、出错时返回什么
- 没有一处用「返回一个结果对象」代替字段清单

**新增了哪些依赖边**（`edges`）

- 每条新增依赖边都写了为什么非加不可；没有新增时明写了「没有」，而不是留空
- 每条边都写成了「哪个文件 import 哪个文件」，而不是「A 模块需要 B 模块」

**边界划在哪**（`boundaries`）

- 每个被动到的模块都写了对外露什么、不露什么，露的那些点名到了导出的函数或类型
- 用词和 Spec 一致，没有为同一个概念发明第二个名字

**想过但没选的划法，和选了的代价**（`alternatives`）

- 至少写了一个想过但没选的划法和为什么没选，并且写了选中这一套要付的代价

**最可能出错的一处**（`riskiest`）

- 指名了最可能出错的一处，而不是并列罗列多项风险

**对得回 Spec**（`traceability`）

- 每一组决定都对得回 Spec 的某一条，没有引入 Spec 里不存在的行为

**留给下游决定的**（`deferred`）

- 留给下游的每一项都写明了留给哪个阶段和为什么现在定不了；没有把函数名、签名或数据结构推给下游

**机器可读的架构图（文件，不是文档里的一节）**（`graph`）

- arch.graph.json 存在且是合法 JSON，concepts / relations / serves 三个键都有，概念 id 没有重复
- 「文件与函数清单」点过名的每个文件都在 serves 里认领了概念；relations 的 from/to 都指向存在的概念 id


# BuildPlan

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 步骤
每一步一个能独立交付的东西。一步做完就能看出对不对。**每一步要写出它动哪几个文件**（路径写全，新建的写清准备放在哪儿），以及在每个文件里加什么、改什么（函数名、导出名、配置项名）——「实现 X 模块」不是一步，它没说出一个文件。确实不动文件的步骤（比如只跑一次验证）写清它跑什么、看什么。

## 依赖和顺序
哪几步必须先后，为什么。没有两步在改同一处却没定顺序。每条依赖写成「哪一步在哪一步之前」（用步骤号），理由要点到**它们共用的那个东西**：哪个文件、哪个函数、哪张表 ——「有依赖关系」不是理由，它没说共用的是什么。

## 每一步怎么验
每一步各自的判据，不要等到最后才知道对不对。每一步写出**跑哪条命令**（原样写出来）、**看到什么算过**；不是命令能验的，写出去看哪个文件的哪一处、看到什么算过 ——「跑一下测试」「确认功能正常」都不是判据，它们没有对象。

## 出问题怎么退
实施到一半失败了怎么退回去。只写停止条件不算回答了这一节。要写出**做哪几个动作**：退哪个 commit 或哪几个文件、已经改掉的数据要不要反着改回来、退完之后看什么确认退干净了 —— 少了最后一样，退没退成没人知道。

## 哪一步风险最高
指名一步，以及为什么先做或后做它。指的是**第几步**（写出步骤号或标题），理由落到那一步动的那个具体东西上：哪个文件、哪条依赖、哪个还没验过的假设 ——「涉及核心逻辑」没有指到任何一处。
```

## 评分标准 · producer（7 条）

**步骤**（`steps`）

- 每一步都有一个能独立交付的东西，不是一句「做 X 相关的工作」
- 每一步都写出了它动哪几个文件（路径写全）以及在每个文件里加什么改什么，没有一步只写了模块名或功能名；确实不动文件的步骤写清了它跑什么、看什么

**依赖和顺序**（`order`）

- 步骤之间的依赖是明确的，没有两步在改同一处却没定顺序

**每一步怎么验**（`verification`）

- 每一步都能独立验证，不需要等到最后才知道对不对
- 每一步的判据都写到了照着能做：命令原样写出来、看到什么算过；没有一步停在「跑测试」「确认正常」这种没有对象的说法

**出问题怎么退**（`rollback`）

- 写了实施到一半失败时怎么退回去，而不只是停止条件

**哪一步风险最高**（`riskiest`）

- 指名了哪一步风险最高，以及为什么先做或后做


# TestPlan

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（5 节）

```markdown
## 验收标准到用例的映射
上游每条验收标准对应这里的哪几个用例。逐条列，不留空。**两边都点到名**：验收标准写出它的编号或原话，用例写出它的 id ——「已全部覆盖」不是一条映射，它一个 id 都没写出来。

## 用例
每个用例：给什么输入、在什么前置状态下、期望什么输出。**每个用例要有一个 id，还要声明它将落在哪个测试文件的哪个用例名上** —— 写测试的是 Test 阶段，它照这份声明落笔；跑测试的是 QA，按 id 单独跑它。落点声明同时是工作区围栏的边界：施工轨不碰这些文件。输入写出实际的值，不是「一个合法的输入」；前置状态写出具体有哪些数据、系统在哪个状态；期望输出写到能逐字比对 ——「返回成功」没说要比对什么。

## 失败长什么样
不只写成功。每个用例失败时看到的是什么，怎么和「测试自己写错了」区分开。**失败要写到能对上号**：报出来的是哪一句、断言差在哪两个值之间；区分方法要写成一个做得出来的动作（跑哪条命令、改哪一处再跑一次看什么变了），不是「检查测试代码」。

## 哪些必须通过
区分「必须通过」和「知道会失败但先记着」，后者写明为什么先记着。**两边都按用例 id 逐个列**，不是「核心用例都要过」；先记着的每条还要写出什么条件下它会被解除 —— 没有解除条件的「先记着」就是永远记着。

## 怎么跑
命令、环境、前置条件。**跑的人不是你** —— QA 在两轨都交工之后照这一节执行，所以它必须细到不在场的人照着能跑。没有「跑一遍看看」这种写法。命令**原样写出来能直接粘**（连同在哪个目录下跑），环境写到版本号（运行时、包管理器、要不要先装依赖），并且写出**只跑其中一条用例**的命令 —— QA 是按 id 复核的，它得单独跑得动某一条。
```

## 评分标准 · producer（9 条）

**验收标准到用例的映射**（`coverage`）

- 上游每条验收标准都至少有一个用例对着它，逐条列出来了

**用例**（`cases`）

- 每个用例都写了输入、前置状态和期望输出
- 每个用例都写出了实际的输入值、具体的前置状态和能逐字比对的期望输出，没有一条停在「输入合法数据」「返回成功」这种没有值的说法
- 每个用例都写出了它的 id 和它落在哪个测试文件的哪个用例名上 —— 下游按 id 单独跑它，按文件名翻到它

**失败长什么样**（`failure`）

- 写了失败长什么样，而不只是成功长什么样
- 写了怎么把「功能没实现」的失败和「测试自己写错」的失败区分开

**哪些必须通过**（`gating`）

- 区分了「必须通过」和「知道会失败但先记着」，后者写了为什么

**怎么跑**（`how`）

- 命令、环境、前置条件都写了，**不在场的人**照着能跑 —— 跑它的是 QA，不是写它的人
- 没有把「跑一遍看看」当成一条用例


# Build

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（6 节）

```markdown
## 这一轮改了什么
按 BuildPlan 的哪几步做的，实际动了哪些文件。不要复述 BuildPlan。**文件逐个列出路径**，每个后面写清在里面加了改了哪个函数、哪个导出、哪一段；再写出它对应 BuildPlan 的第几步（写编号就够了，那一步的内容不用抄过来）——「重构了配置模块」没说出一个文件。

## 自己跑了什么来验证
跑的是改动本身（编译、启动、走一遍改的路径），命令和输出贴出来。**这一阶段不读、不写、不跑任何测试代码** —— 测试是另一条轨（Test）的活儿，跑起来对撞是 QA 的事。需要新用例就说明缺哪一条，写进「没做完的」。命令原样贴（连同在哪个目录下跑的），输出贴出**判它成了的那几行原文**，不是一句「编译通过」。

## 和 BuildPlan 不一样的地方
多做的、少做的、换了做法的，逐条写为什么。一条都没有就明写「没有」。每条要指到 BuildPlan 的第几步和实际动的哪个文件，并把两边都写出来：计划说的是什么、实际做的是什么 ——「做了些调整」既没指到步，也没说改成了什么。

## 不明显的决定
代码里看不出为什么的那几处，在这儿说清。**每处指到文件和函数名**，看的人能直接翻到那儿；理由要落到一个具体的后果或另一种做法上（不这么做会怎样、当时另一种写法为什么不行）—— 落不到这两样上的话，「不明显的决定」和一句复述没区别。

## 这一轮最可能出问题的一处
指名一处，写为什么是它。并列罗列多项不算回答了这一节。**指到文件和函数名**，并写出它真出问题时看到的是什么（哪条路径会走错、报出来的会是什么）——「并发处理有风险」没有指到任何一处。

## 没做完的
知道还差什么、留给谁。没有就明写「没有」。每条写出差的是哪个文件的哪一处、留给哪个阶段 ——「还有一些边界情况没处理」既没说哪个文件，也没说留给谁，下一个阶段接不住。
```

## 评分标准 · producer（15 条）

**这一轮改了什么**（`did`）

- 改动范围和 BuildPlan 一致，没有顺手做计划外的事
- 命名和上游文档一致：Spec / Arch 里叫什么，代码里就叫什么，没有为同一个概念在代码里发明第二个名字
- 实现的行为对得上 Spec 写的那几条
- 新写的代码和它周围、以及它的直接调用方风格一致：命名、错误处理、文件位置都跟着现有做法
- 同一条规则只有一个定义处，没有把同一份逻辑抄成第二份
- 新增或改名的每个导出都有调用方，没有留下没人调用的代码或半途的开关
- 受影响的调用点都跟着改了，没有把现成的调用方留在对不上的状态
- 动过的文件逐个列了路径，每个都写了在里面改的是哪个函数、哪个导出或哪一段；没有一处只写了模块名或「相关文件」

**自己跑了什么来验证**（`tests`）

- 这一轮的改动没有碰任何测试代码；缺用例的地方是说明缺哪一条、写进「没做完的」
- 自己跑了改动本身（编译、启动、走一遍改的路径）并贴了命令和输出，而不是只说「应该能跑」

**和 BuildPlan 不一样的地方**（`deviation`）

- 和 BuildPlan 不一样的地方逐条写了为什么；一条都没有时明写了「没有」

**不明显的决定**（`decisions`）

- 每一处不明显的决定都写清了为什么

**这一轮最可能出问题的一处**（`risk`）

- 指名了这一轮最可能出问题的一处，而不是并列罗列多项
- 指名那一处落到了文件和函数名上，并写了它出问题时看到的是什么，而不是一句「某某逻辑有风险」

**没做完的**（`leftover`）

- 没做完的写明了差什么、留给谁；没有时明写了「没有」


# Test

反方在这一阶段：**只判下面那几条标准，不另外提问题（每轮上限 = 标准条数，收敛 = 全 yes）**

## 填写模板（4 节）

```markdown
## 这一轮写了哪些测试
逐个用例：TestPlan 里的哪一条、落在哪个文件（路径写全）。方案里有而这儿没有的，写进「没做完的」，不许静默少。

## 和方案的对应
TestPlan 的每条用例 id 对到测试代码里的具体测试名。对不上的说为什么。

## 自己跑了什么来验证
测试代码本身跑得动吗（语法、依赖、fixture）。**不许拿实现来跑** ——测试对不对得上实现是 QA 对撞的事，这儿只证测试自己站得住。

没写的用例、写了但自己都觉得站不住的 —— 一条条列，空着要写「无」。
```

## 评分标准 · producer（7 条）

**这一轮写了哪些测试**（`written`）

- TestPlan 的每条用例都写成了测试，或者明写在「没做完的」里；没有静默少掉的
- 每条测试都写出了落点文件的完整路径，没有一条只写「测试文件」
- 测试断言的是 TestPlan 写的期望输出，没有把断言写成「不抛错就算过」这类空判

**和方案的对应**（`mapping`）

- 每条用例 id 都对到了测试代码里的具体测试名，对不上的写了为什么

**自己跑了什么来验证**（`selfrun`）

- 证明了测试代码自己站得住（语法、依赖、fixture 齐全），而没有拿实现来跑
- 站得住的证据贴了命令和输出原文（编译、静态检查或 dry-run 那几行），不是一句「检查过了」

**没做完的**（`unfinished`）

- 没做完的逐条列了差什么；没有时明写了「无」


# QA

反方在这一阶段：**自己去看，照旧交问题清单（无上限）**

## 填写模板（8 节）

```markdown
## 测的是哪一个 commit
写出 sha —— **两条轨各一个**（Build 的代码 commit、Test 的测试 commit），不要笼统地说「当前代码」。**sha 至少写到前 12 位**，再写出你是在哪个目录、哪个分支、什么环境下测的 —— 反方要在同一处跑一遍核对你说的。

## 逐条对照上游的结果
对着 Spec 和 Arch 一条条看 Build 的代码，不是通读一遍谈感受。每条写成三样：**上游那一条**（编号或原话）、**代码里落在哪个文件的哪个函数**、**对上了还是没对上** ——「整体符合设计」这三样一样都没有。

## 读出来的问题
静态审查发现的缺陷，每条指明文件和位置，看的人能直接翻到那儿。没有就明写没有。**位置要到文件路径加函数名或行号**，还要写出这条在什么输入、什么状态下会真的出问题 ——「错误处理不够完善」既不是位置，也不是条件。

## 按 TestPlan 逐条执行的结果
一条都不跳。跳过的写明为什么。**按 TestPlan 的用例 id 逐条列**，每条写清跑的是哪条命令、结果是过还是没过 ——「全部用例执行通过」不是逐条，它一个 id 都没写出来。

## 失败的用例
实际输出是什么、它来自哪一条用例。不只写「没过」。**输出贴原文**（报错那几行、断言里实际值和期望值各是什么），并写出它的用例 id 和所在的测试文件 ——转述一遍，下一轮就没法拿它比对了。

## 有没有让别处退化
这一轮的改动之外的地方，查过没有、结果是什么。**写出查的是哪几处**：跑了哪条命令、覆盖了哪些用例或哪些文件，结果各是什么 ——「未发现回归」没说查过什么，和没查看起来一模一样。

## 变异检验：测试自己站不站得住
两个方向都要做、都贴证据：**还原必红** —— 把 Build 的改动临时还原（`git stash` / `git revert -n`，做完恢复原样），必过用例必须变红，全绿说明测试没测到这次改动；**no-op 仍绿** —— 给实现打一个不改行为的变异（比如改一句注释、换一个内部变量名），用例必须仍然全绿，红了说明测试钉的是源码文本不是行为。每个方向写出动了什么、跑了哪条命令、看到什么 —— 两样都是对**测试**的攻击，串过供的一致什么都不是，这两下就是拆串供的。

## 怎么重现
跑的命令和环境写下来，别人照着能重现。**命令原样能粘**（连同在哪个目录下跑），环境写到版本号，从零开始要做的那几步一步不落（装什么、准备哪些数据、清理什么）—— 少一步别人就重现不出来。
```

## 评分标准 · producer（13 条）

**测的是哪一个 commit**（`subject`）

- 写清楚测的是哪两个 commit（Build 的代码、Test 的测试），而不是笼统地说「当前代码」

**逐条对照上游的结果**（`against`）

- 逐条对照了 Spec 和 Arch，每条都点到了上游那一条和它在代码里的落点（文件加函数），没有一条只给结论不给这两样

**读出来的问题**（`findings`）

- 读出来的每条问题位置到了文件路径加函数名或行号，并写出了它在什么输入或状态下会真的出问题；没有发现时明写了没有

**按 TestPlan 逐条执行的结果**（`executed`）

- 按 TestPlan 逐条执行了，没有跳过，跳过的写明了为什么
- TestPlan 标为「必须通过」的用例在这一轮的代码上全部通过，没通过的每条都对得上原因
- 按 TestPlan 的用例 id 逐条列了结果，每条写了跑的命令和过没过；没有把多条并成一句「全部通过」

**失败的用例**（`failures`）

- 失败的用例记下了实际输出和它来自哪一条用例，而不只是「没过」
- 失败的用例贴了输出原文（报错那几行、实际值和期望值），而不是转述一句「结果不对」

**有没有让别处退化**（`regression`）

- 确认过这一轮的改动没有让别处退化，并写了是怎么确认的
- 回归确认点名了跑的是哪个套件或哪几条命令、多少条过多少条没过，不是一句「无回归」

**变异检验：测试自己站不站得住**（`mutation`）

- 还原方向做了并贴了证据：临时还原 Build 的改动后必过用例变红了 —— 全绿说明测试没测到这次改动
- no-op 方向做了并贴了证据：不改行为的变异之后用例仍然全绿 —— 红了说明测试钉的是源码文本不是行为

**怎么重现**（`repro`）

- 跑的命令和环境写下来了，别人照着能重现

# 所有阶段共用的两份

> 它们讲的是**方法**：怎么质疑一份东西、怎么裁一场争论。这两件事在 PRD 和在 Merge
> 是一样的，所以只有一份 —— 给每个阶段各抄一份只会得到十一份同样的话，然后各自漂移。

## critic · 反方怎么质疑

- 它说的每一句都建立在实际看过的东西上，没有靠猜、也没有假设一件它没核实过的事
- 每条判定都写了依据，而不只是一个 yes 或 no
- 判 no 的每一条都说得出产出里是哪一节、哪一句不满足它
- 那句整体判断说清了这一轮够不够格以及为什么，不是复述逐条判定

**Build 额外多判这几条**（追加，不是另一份）：

- 除了功能对不对，也看了编码上的毛病：风格和周围的代码对不对得上、命名和上游文档对不对得上、同一条规则有没有被抄成两份

## verdict · 裁判怎么裁

- 对每一条已经存在的问题都明确表了态，没有沉默略过任何一条
- 关闭任何一条时都写清楚了它为什么不再成立，而不是「已修复」四个字
- 结论建立在它自己读过的上游文档和两方产出上，而不是复述正方或反方说过的话
- 没有把「这一轮没提到」当成「已经解决」
- 给出了「还要不要再来一轮」的结论，并写清楚依据是什么

**Build 额外多判这几条**（追加，不是另一份）：

- 没有因为「不影响功能」就把编码规范类的问题关掉 —— 那类问题的出口是人接受风险，不是裁判判它不成立
