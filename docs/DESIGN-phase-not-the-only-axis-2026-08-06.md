# 地基改动方案：把「阶段」从唯一的组织维度降级

> 2026-08-06 晚，用户一整轮谈话的收敛点。**方案，不是计划**。
> 三个开放问题当天全拍了（见 §六），只剩一个。
>
> 背景与证据：`docs/HANDOFF-2026-08-06.md` §5.8 / §5.9 / §5.10。

---

## 一、要治的是什么

今天 `ChangeState.phase` 是**一个字段、十二选一**，而下面这三类东西**都挂不上去**：

| 类别 | 例子 | 今天怎么被硬塞进去 |
|---|---|---|
| **跨阶段的联动** | Review 盯着 Build、Fix 改 Build | `returnStack` 替它记「谁在等谁」；`SENDS_TO_FIX` 和「Fix 不在主线上」是另两处补丁 |
| **多阶段同时** | TestPlan ∥ Build、Plan ∥ TestPlan | 做不到。`phase` 是单数 |
| **不属于任何阶段** | 先闲聊再 PRD、中途问个名词 | `change_bindings` 按 `(change, phase)` 建键 —— **会话必须属于某个阶段**，于是「问名词」和「跑一轮」抢同一把椅子 |

**一个根：今天每一样东西都必须挂在一个阶段上。**

---

## 二、目标形状

一个 Change 上同时可以有三样东西，**各自有生命周期，互不占座**：

```
Change
├── 状态（state）      主线走到哪。可以不止一个（TestPlan ∥ Build）
├── 联动（activity）   挂在某个状态上的持续活动（Review 盯 Build）
└── 旁路会话（aside）  不属于任何状态，不产出、不推闸门、不占座
```

### 2.1 十二个阶段重新分类

用户的判据（§5.8）：**这个阶段的产出，是它自己的，还是关于别人的产出的？**

| | 有哪些 | 为什么 |
|---|---|---|
| **状态**（11） | PRD / Spec / TechSpec / **Arch** / Plan / TestPlan / Build / **QA** / Merge / Retro / Done | 产出是它自己的，有闸门 |
| **联动**（2） | **Review / Fix** | 产出都是「关于 Build 那份代码的」 |

> **QA 不并**（用户 2026-08-06 拍）。它和 Build 的蓝方跑的**不是同一件事**：
> 蓝方跑的是「这一轮改的东西通不通」，QA 跑的是「**整体验收 + 有没有让别处退化**」。
> 范围不同，而且 QA 有自己的闸门 —— Merge 之前那道独立的验收因此保留。

**Review 和 Fix 不再是阶段，是 Build 这个状态上的角色**（QA 仍是状态）。于是：

```
Build 状态里同时在跑：
  红方   写代码（看不到测试源码）
  蓝方   **红方写完之后**跑 TestPlan 交的测试 → 反馈「哪条失败、输出是什么」
  Review 全程盯：审代码，也审测试代码本身对不对
  「Fix」= 红方响应意见继续改 —— 那是下一轮，不是新阶段
```

**「Fix」不是新阶段**：红方响应 Review 的意见继续改 —— 那是 Build 的下一轮。

### 2.1.1 加一个 **Arch** 状态（用户 2026-08-06 提，位置待拍）

> 原话：「build 我需要细分，我要先定架构，再 build，要加一个 arch stage。」

**它解释了一个一直没落地的东西。** BACKLOG §5.5（用户 2026-08-04 定的反馈链路）
里那条机械分界线写着：

> 修一个模块时，如果它需要新增一条图上没有的依赖边 —— 那就不是模块问题，
> 是架构问题。立刻停手，**攒进架构那一批**。

**「攒进架构那一批」——攒到哪儿去？今天没有那个格子。** TechSpec 定的是数据怎么存、
接口契约；Plan 拆的是步骤。**「这次要碰哪些模块、新增哪些、边界划在哪」没有阶段
装它**，于是它要么散在 TechSpec 里，要么在 Build 里被现编。

加 Arch 之后 §5.5 第一次有落点：**Build 的反馈回流到 Arch，而不是回流到一份没人
负责的散文。**

#### 位置：**已拍（2026-08-06 晚）—— TechSpec 之前**

```
PRD → Spec → Arch → TechSpec → Plan → TestPlan ∥ Build → QA → Merge → Retro
```

用户选的是**先划骨架再填数据**（推翻了这份方案原先「TechSpec 之后」的倾向）：
Arch 消费 Spec，产出「动哪几个模块 + 新增哪些边 + 边界 + 没选的划法」；
TechSpec 在既定模块边界内写数据和接口 —— Arch 的产出约束它，不是反过来。

#### Arch 的模板（草案，四节）

| key | 标题 | 要回答什么 |
|---|---|---|
| `modules` | 这次动哪几个模块 | 已有的哪几个、新增哪几个 |
| `edges` | 新增了哪些依赖边 | 每条写为什么非加不可 —— **这是 §5.5 那条分界线的落点** |
| `boundaries` | 边界划在哪 | 每个模块对外露什么、不露什么 |
| `alternatives` | 想过但没选的划法 | 至少一个，写为什么没选 |

### 2.2 闸门落在哪

**人在状态的出口表一次态**，回答的是「这个状态交出来的东西够好了吗」。

联动内部的往返（Review 报了、红方改了、蓝方重跑）**不需要人逐次表态** —— 它们是
Build 那一轮对抗的内部循环，和设计阶段的「红方产出 + 反方质疑 + 人裁决」是**同一个
形状的一次实例**，只是循环发生在里面。

这顺手解掉 §8.9：「回程跳回不重走」之所以是洞，正因为 Review→TestPlan→Build 被当成
三次位移，而它本来是一次联动内部的往返。

## 三、数据模型

### 3.1 `changes.phase` → `change_states`

```sql
CREATE TABLE change_states (
  change_id  TEXT NOT NULL REFERENCES changes(id),
  phase      TEXT NOT NULL,          -- 只许是「状态」那十一个
  status     TEXT NOT NULL,          -- pending/running/settled/blocked
  updated_at TEXT NOT NULL,
  PRIMARY KEY (change_id, phase)
);
```

`ChangeState.phase: Phase` → `states: ReadonlyMap<Phase, Status>`。

**主线仍然是全序**（`projects.phase_order` 不变），并行只是「同时有多个 active」，
不是重排 —— `phaseGraphOf` 那条「拒绝一切非子序列」原样成立。

### 3.2 `returnStack` 退休，换成 `change_activities`

```sql
CREATE TABLE change_activities (
  change_id TEXT NOT NULL,
  kind      TEXT NOT NULL,   -- review | fix   （QA 不并，它仍是状态）
  on_phase  TEXT NOT NULL,   -- 它盯着哪个状态（今天恒为 Build）
  status    TEXT NOT NULL,   -- open | settled
  opened_round INTEGER NOT NULL,
  PRIMARY KEY (change_id, kind, on_phase)
);
```

**`returnStack` 记的本来就是关系数据**（谁在等谁改完），只是被塞进了位置字段。
换成这张表之后 `assertStateValid` 里那条「严格下游」的校验也一起退休 —— 它挡的
「状态机走进没有出口的格子」，在这个模型里由「联动必须挂在一个存在的状态上」来保证。

### 3.3 `change_bindings` 加一个 `kind`，`phase` 可空

```
kind:  round | aside
phase: 状态名（round）或 NULL（aside —— 旁路会话）
```

**旁路会话不占「一个阶段只许一个进程」那个座位**（`phaseBusy` 只数 `kind='round'`）。
于是「问个名词」和「跑一轮对抗」不再抢同一把椅子。

### 3.4 闲聊：`brief` 从问卷变成一段对话

今天 `domain/brief.ts` 是 elicitation 问卷，2026-07-30 用户就说过「**是问卷不是对话**」，
而这个 Change 的 brief 实测**只有 9 个字**。

改法：**闲聊就是一个旁路会话**（`kind='aside'`），人跟它谈到满意，然后**把这段对话
收敛成 brief**。不新增机制 —— 它就是 3.3 那条能力的第一个用户。

**收敛方式（用户 2026-08-06 拍）：模型起草，人改。** 谈完之后模型把这段对话整理成
一份 brief 草稿，**人在上面改，改完那一版才是 brief**。

判据仍然守得住：`round-turn-runner` 那句「人要的是这些，他自己答的，不是模型猜的」——
人改过的那一版就是他的话。**但草稿必须让人真的看见并动过手**，直接接受模型草稿等于
没改，那条注释就成了假话。**这一点要有机械判据，不能只靠流程叮嘱**（比如：brief
未经编辑就不许离开闲聊）。

## 四、分批的顺序

**每一批单独可验收、可回滚。不许一次全上。**

### 批 0 · 先修投递层（不动地基）

`HANDOFF-2026-08-06.md` §5.5 那五条：会话不关、出口按注册表判、轮询死了不自愈、
错误信息是旧的、拒绝理由不上屏。

**理由不是保守**：今天六个阶段里对抗机制一次没错，**每次卡住都是它们**。地基改动
要跑很多轮才验得完，而现在每一轮都要交这个税。

**验收**：连着跑三轮不同阶段，一次都不需要手动 kill 进程或改库。

### 批 1 · 旁路会话（3.3）

只加 `change_bindings.kind`，`phaseBusy` 只数 `round`。**不动状态机。**

**验收**：一个阶段正在跑轮的同时，能开一个窗口问名词，两边互不干扰。

**这一批为什么排第一**：它是三类诉求里**唯一不需要动状态机**的，而且它立刻能用 ——
「一条路走到黑」这个体感当场消失。

### 批 2 · 闲聊 → brief（3.4）

批 1 落地之后，闲聊就是它的第一个用户。**模型起草、人改**（§六·B 已拍）——
难点在那条机械判据：**未经人编辑的草稿不算 brief**。

**验收**：新建一个 Change，谈十分钟，brief 是几百字而不是 9 个字。

### 批 3 · 多状态（3.1）

`ChangeState.phase` → `states`。**这一批最贵，而且它一动，六个阶段那份实测账全部作废。**

先做**只读的兼容层**：`state.phase` 保留为「主状态」的派生 getter，让绝大多数调用点
不用改。然后逐个把真正需要多状态的调用点（`upstreamOf`、`journey`、闸门、面板）
迁过去。

**验收**：TestPlan 和 Build 同时 active，各自跑轮、各自有闸门，互不打断。

### 批 4 · 联动（3.2）

Review 和 Fix 从 `PHASES` 里摘出来，变成 `change_activities`。`returnStack` 退休。
**QA 不动** —— 它仍是状态，仍有自己的闸门。

**这一批必须在 Review 真跑过至少一轮之后做** —— 它要建的形状有一端从没在真机上
出现过（§5.9）。

**验收**：Build 状态上挂着一个 open 的 review 联动，红方改、蓝方跑、Review 盯，
人只在 Build 出口表一次态。

### 批 5 · 十二阶段重定义（2.1 / §5.9）

TestPlan 交测试代码、Build 的红方看不到它、Build 的蓝方跑它、Review 审测试本身。

**§8.7·1 已答（用户 2026-08-06）：不要求 TestPlan 交的测试当场能跑、当场是红的。**
「**肯定是 build 做完了跑 test**」—— 执行的责任在 **Build 的蓝方**，时点在**红方写完
之后**。

所以 TestPlan 只交两样：**测试方案 + 测试代码**，它自己不跑。

> ⚠ 这条推翻了 2026-08-06 给 TestPlan 加的「实际跑出来的结果」那一节 ——
> **那一节要撤掉**，`ran` 那两条标准跟着撤。TestPlan 进 `PRODUCES_COMMIT` 保留
> （它要交代码），但和「它得先跑一遍」无关。

## 六、三条已经拍了（2026-08-06）

| | 拍的是 |
|---|---|
| **A** | **QA 不并。** 它和 Build 的蓝方范围不同（整体验收 + 回归 vs 这一轮通不通），Merge 前那道独立闸门保留 |
| **B** | **模型起草，人改。** 未经人编辑的草稿不算 brief —— 要机械判据，不能只靠叮嘱 |
| **§8.7·1** | **不要求。**「肯定是 build 做完了跑 test」—— 执行在 Build 的蓝方，时点在红方写完之后。TestPlan 只交方案和代码 |

**剩下一个没答的**：Review 既然「全程盯」，它自己有没有闸门？还是它的结论只作为
Build 出口那一次表态的输入？（方案默认后者 —— 联动内部的往返不需要人逐次表态。）

## 六点五、**为什么这些细节和「公司里没有 AI 时的软开」不一样**

> 用户 2026-08-06：「我的思路是和公司里没有 AI 时的软开是不一样的，AI 的软开可能
> 整体流程差不多，但是**很多细节是完全不一样的**。」

今天一整轮的每一条改动都是这句话的实例 —— **列出来是为了让下一轮不要按「正常
软件流程」去简化它们**：

| 人怎么做 | AI 必须怎么做 | 今天的证据 |
|---|---|---|
| 不会在 PRD 里追「13.0 的词法形式」 | **模板 + rubric 硬约束边界** | PRD 四轮同一句抱怨在降尺度 |
| 「别自己审自己」是常识 | **必须是机械闸门** | Build 自己写 `verify.mjs`，关一个绕过点长一个 |
| 评审是连续的 | **必须离散化才收敛** | 139 条 finding vs 17 条判定 |
| 不懂就问 | **不懂会编** | 所以要旁路会话（§3.3） |
| **架构在脑子里** | **写不下来就不存在** | 所以 Arch 得有产出、有闸门（§2.1.1） |

最后一条是 Arch 存在的理由：**人的架构可以是隐性的，AI 的不行。**

---

## 七、一句话

**不是重写架构。** 今天十几次提交、十份模板、Build 三刀改造，一次都没碰状态机 ——
这架构承载力没问题。它承载不了的只有一类东西：**不属于任何单个阶段的东西**。

而批 0 和批 1 加起来就能让「一条路走到黑」这个体感消失，**它们都不动状态机**。
真正的地基改动（批 3、批 4）可以等到 Review 跑过、投递层修完之后再动。
