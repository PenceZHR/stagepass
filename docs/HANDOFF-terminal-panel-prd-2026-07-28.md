## 一、两个决定

**决定一：Codex TUI 运行在 StagePass Web 里的一块 pty 面板中，不再是 Terminal.app 窗口。**

**决定二：Codex 线程的绑定粒度从「一个 Change 一个」改成「一个 (Change, 阶段) 一个」。**

两个决定是一起的，不能只取一个：粒度改细的前提是有地方把 11 块终端组织起来，而面板存在的价值一半来自它能组织它们。

---

## 二、为什么（这一节决定了后面每一处措辞）

### 2.1 决定一不违反「StagePass 不渲染」，但判据必须换

被否决过的那条路（§2.4 表格第三行）是：StagePass 解析 `codex mcp-server` 的事件流，**自己理解语义再画界面**。

这次不是。pty 里跑的是同一个 `codex` 二进制，画面仍然由它用转义序列自己画，xterm.js 只把转义序列还原成像素——它不知道什么是「thinking 块」、什么是「选择器」。**换的是窗口宿主，不是渲染者。**

**但这带来一个真问题：判据从可机械检查变成了要人判断。**

今天 §9.3 那条「`src/` 里没有任何渲染代码」grep 一下就知道过没过。换成「不许解释 Codex 的语义」，就需要有人判断某段代码算不算解释。而 §2.2 说重建的**首要理由**正是「遗留让模型判断失准」——判据一旦要判断，它就会滑：先是「turn 结束加个高亮吧」（要 parse），再是「选择器滚上去看不见了，顶部加个提示吧」（要 parse），最后回到那条被否决的路上。§2.3 那五处「建好但没接上」就是这个滑坡已经发生过一次的证据。

所以新判据必须**仍然可机械检查**。做法在 §四给出。

### 2.2 决定二的理由是 fence，不是「乱」

「一个 Change 一个终端会很乱」是真的，但它是审美理由，扛不住反驳。真正的理由是 §4 概念 3：

> **fence** —— 决策绑定它所依据的快照；快照变了，旧决策失效而不是静默生效。

一个 Change 一个线程，意味着 Spec 阶段的裁决**有一部分依据活在 Codex 的对话历史里**——模型记得 PRD 阶段聊过什么，而那段记忆不在 StagePass 的任何快照中。**fence 管不到它**：快照变了，那段记忆不会失效，照样影响下一个决策。这是 fence 语义上的结构性缺口。

一阶段一线程之后，跨阶段的信息**只能走文档**（PRD → Spec → TechSpec …），而文档正是 StagePass 能快照、能哈希、能 fence 的东西。**所以这不是把界面弄整齐，是让 fence 真的覆盖全部输入。**

第二条实际理由：上下文长度。12 个阶段 × 每阶段若干 turn，加上 L4 的红/蓝/裁判对抗轮次，全塞一个线程，而 `codex resume` 每次恢复完整历史——走到 Build 时输入会大到不可用。

### 2.3 现有代码写的是相反的决定，这条必须一起处理

`src/store/binding-store.ts` 第 5–13 行的文档注释写着：

> One Change, one persistent Codex thread. ... 线程是整个 Change 上下文所在。如果 StagePass 说不出哪个线程属于哪个 Change，**每个阶段都会开一段不知道前面发生过什么的新对话**——而人会看着自己的活散在十几个 task 里。

它给了两条理由，现在的状态是：

| 原理由 | 现在成不成立 |
|---|---|
| 人的活会散在十几个 task 里 | **不成立了。** 12 个线程如果是一块面板里按阶段排的 tab，那不叫散，那叫有组织。**这正是决定一改变的东西**——它把「一阶段一线程」从代价变成收益 |
| 每个阶段开一段不知道前面的新对话 | **成立，是真代价。** 换来的是 fence 完整 + 上下文不爆。这笔换我们认，但账要记：**每个阶段的开场 prompt 必须自己带上游文档**，StagePass 的组题工作变重（方向与 §5.2「StagePass 全权组题」一致，且让「模型知道什么」从隐式变成显式可审计） |

**这段注释不改掉就是 §2.2 描述的那种毒**——下一个读代码的模型会看到一段理直气壮论证相反决定的文字，且没有任何标记说它已作废。改 PRD 的同时必须改它。

### 2.4 可行性已实测（2026-07-28）

技术可行性不是推断的。以下四条已测，环境是本机 macOS / arm64 / Node **25.9.0** / `codex-cli 0.144.4`：

| 测什么 | 结果 |
|---|---|
| node-pty 装得上吗（Node 25 是很新的大版本，原生模块是最可能卡住的地方） | ✅ 8 秒装完，**走预编译包，没有 node-gyp 编译** |
| pty 能起进程吗 | ✅ `/bin/sh` 拿到 `/dev/ttys008`、`TERM=xterm-256color` |
| Codex TUI 能渲染进 pty 吗 | ✅ 3.5 秒收到 3803 字节真实画面 |
| **在浏览器里渲染正常吗** | ✅ **用户目视确认** |

**踩到的坑（必须记，否则下一个人会再踩一次）**：node-pty 1.1.0 的 prebuild 里 `spawn-helper` 装完是 `-rw-r--r--`，**没有执行位**。表现是一句不指明文件的 `posix_spawnp failed`。`chmod +x node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper` 即可。安装步骤里要固化这一条。

**键盘协议**：Codex 会推 bracketed paste（`\e[?2004h`）与 kitty 键盘协议（`\e[>7u`）。xterm.js 对后者支持有限——但不构成风险：**Terminal.app 完全不支持 kitty 协议，而 Codex 在 Terminal.app 里工作正常，说明它有降级路径。**

**尚未验证，不许当成已验证**：

1. **elicitation 选择器在 pty 里能不能正常出现并接受键盘选择** —— 这是 L3 的命脉。它需要一个声明 `elicitation` 能力的 MCP 服务端参与才会出现，裸跑 `codex` 看不到它
2. 在 pty 里敲 `/app` 能不能唤起 Codex Desktop
3. 窗口尺寸变化（SIGWINCH）下全屏 TUI 的表现

## 四、PRD 逐处改动

下面每一条都给出**当前原文**和**改完必须成立的意思**。措辞由你定，但意思不能少也不能多。

### 改动 1 —— §1 的表，StagePass Web 那一行

当前：

```
| **StagePass Web** | 看和启动：当前状态、证据、风险、start/retry/interrupt/recover | **不承载任何业务决策入口** |
```

改完要成立的意思：StagePass Web 除了「看和启动」，**还托管 Codex TUI 运行所在的终端面板**。

**「不承载任何业务决策入口」这一格不许改。** 这是全文最容易被这次改动带歪的地方：决策仍然只在 Codex 的 elicitation 选择器里发生，只是那个选择器现在显示在浏览器里的 pty 中。**面板是宿主，不是入口。** 建议在这一格后面补一句把这个区分说死，因为半年后读这份 PRD 的人一定会问。

### 改动 2 —— §1 结尾那句

当前：

```
**渲染由 Codex TUI 原生完成。StagePass 一行都不画** —— 包括执行过程和选择界面。这条是 2026-07-28 定的，取代了原先"在 Codex App 里弹 HTML 卡片"的写法；理由见 §2.5。
```

两件事：

1. **这句话本身仍然成立，不要删。** StagePass 确实一行都不画，画的是 Codex。要补的是一句限定：**「画在哪个窗口」和「谁在画」是两件独立的事**，搬窗口不等于改画的人。
2. **「理由见 §2.5」是悬空引用** —— 第 2 节只有 2.1–2.4，理由实际在 **§2.4**。顺手改掉。

### 改动 3 —— §9.3 常驻判据（**本次最重要的一条**）

当前：

```
零调用者计数 = 0；层间依赖单向；`enum` 里的选项全部可执行；一个概念一个名字；**`src/` 里没有任何渲染代码**。
```

最后一条要换成一条**仍然可机械检查**的判据。要求它同时满足：

- 允许「把 pty 的字节原样转发给浏览器」
- 禁止「读懂那些字节」

具体做法（写进 PRD，因为它是判据不是实现细节）：**pty 的输出在 StagePass 这一侧永远不落成 string。** 只以 `Uint8Array` 流转，服务端只做转发；不允许任何 `toString()`、正则匹配、`JSON.parse` 作用在 pty 输出上。类型上就不给出 string，于是「想解释」这件事在编译期就失败。

这条要和现有那几条并列，成为常驻测试的一员。

**这一条是决定一被接受的前提条件。** 没有它，「不渲染」就只剩一句口号——请在 PRD 里把这个因果关系写出来，不要只列判据。

### 改动 4 —— §10「明确不做」的那一条

当前：

```
- **StagePass 自己渲染 Codex 的执行过程或选择界面** —— 渲染是 Codex TUI 的事，这条已从"曾经做过"变成"明确不做"
```

改成把两件事分开：

- **仍然不做**：解析 Codex 的输出、理解其语义之后自己画界面（即 §2.4 表格第三行那条被否决的路）
- **现在要做**：托管一块 pty，让 Codex 在里面自己画

§2.4 表格第三行那句用户原话（"我不想在我的 StagePass 里渲染，我就要在 Codex 原生客户端里渲染"）**不要删也不要改**——它是这次改动的边界定义，删了以后没人知道禁的到底是什么。可以在它后面加一个脚注说明「pty 面板不属于这条」。

### 改动 5 —— 新增一节：阶段线程（建议放 §6.5，紧跟 §6.4）

PRD 目前没有明写 binding 粒度，只在 §6 的 L2 行提到「thread 绑定」。新增一节说清：

1. **一个 (Change, 阶段) 一个 Codex 线程。** 12 个阶段中 `Done` 是终态、不发生 turn，所以实际有线程的是 **11 个**。
   - 阶段清单以 `src/domain/phase.ts` 的 `PHASES` 为准，**是 12 个**。该文件第 16–18 行记着老树曾在这件事上自相矛盾（`CONTENT_PHASES` 说 13、`PipelinePhase` 说 9），PRD 不要引入第三个数字。
2. **重入复用同一线程。** `Fix` 不在 `advancesTo` 里（`phase.ts:60`），一个 Change 可以进 Fix 很多次；设计阶段被拒是「原地再来一轮」（`phase.ts:71-77`）。所以 `(change, 阶段)` 在时间上不唯一。**已决定：重入 `codex resume` 同一个阶段线程，不新开。**
   - 理由：Fix 第三轮最需要的上下文，恰恰是「前两轮改了什么、为什么还是没过」，那正在同一线程里。
   - 代价：被打回多次的阶段线程会变长。认了——它长的是**同一件事**的历史，不是十二件事的。
   - 另一个理由：固定 11 块使面板可穷举，与 §4 概念 1「阶段与转移可穷举」同构；每次新开会让面板变成一个会长的列表，那是老树「不知道有多少东西活着」的形状。
3. **跨阶段信息只能走文档。** 这是 §2.2 那笔交换的另一半，必须和粒度写在一起，否则下一个人会以为上下文还能靠对话历史传。
4. **面板不需要 11 个进程同时活着。** rollout 文件是持久的，任何一块随时能用 `codex resume` 复活、历史不丢。常驻的是 1–2 个，其余是**可复活的空壳**：点开就活，关掉不丢。

### 改动 6 —— §6.4 补一条不变量

§6.4 现在列了三个坑。补第四条：

**同一个阶段线程，任何时刻只许有一个活着的进程。**

理由：两个 `codex resume <同一个 id>` 同时往一个 rollout 追加，§6.4 那条「必须认自己那一次」就废了——turn 边界会交错，认错就拿到别人的答案。一阶段一线程本身降低了这个风险（并发的是不同文件），但面板必须保证它，因为面板让「同时开着好几块」变成了常态。

### 改动 7 —— §6 和 §9.2 的 L2 行

终端面板**不是新的一层**，它是 L2 的第二个 launch 实现（`src/codex/tui-transport.ts:60` 的 `launch` 已经是注入点，注释写着 "Injected so the watching half can be proved offline"）。

但两件事让 L2 需要**第三次验收**：

1. binding 主键从 `change_id` 变成 `(change_id, phase)`，两个方向的唯一性约束都要重写，`ThreadAlreadyBoundError` 的判定跟着改——这是 L1/L2 的数据模型改动
2. 执行通道从「osascript 开 Terminal.app」换成「StagePass 自己持有的 pty」

§9.2 里 L2 那行当前是 `✅ 2026-07-28 通过`。改成能区分两个实现的写法（例如 osascript 版 ✅ / pty 版 ⬜），并在通过条件里补上 binding 粒度那一条。

**不要把 L2 直接标回 ⬜** —— 已经通过的那两次是真的，抹掉它就丢了「TUI 这条路能走通」这个证据。

### 改动 8 —— §10 的已知风险段

当前那段只提了一条风险（turn 结束检测依赖 rollout 文件名与 jsonl 两个约定）。补两条：

1. **依赖面变大。** 新树目前只有 4 个运行时依赖（better-sqlite3 + tsx + typescript + @types），这是第一次引入前端栈。
   - 注意：**「node-pty 要编译、Node 升级要重编」这个担心已被实测排除**（见本文 2.4：预编译包，8 秒装完）。写进 PRD 时不要把已排除的风险当成风险留着——那会让下一个人为一个不存在的问题做设计。
   - 真正要记的是 `spawn-helper` 执行位那条坑（2.4），它属于安装步骤而不是风险。
2. **pty 里仍有三件事没验**，要像 §2.4 那样逐条目视确认后才能写成事实，不许推断：**elicitation 选择器能否正常出现并接受键盘选择**（L3 命脉）、`/app` 能否唤起 Desktop、SIGWINCH 下的表现。
   - 「TUI 在浏览器 pty 里渲染正常」**已经验过了**，不要再列成未知。

### 改动 9 —— §2.4 第 2 点有一个待验的威胁（**先验再动笔**）

PRD §2.4 把 TUI 打败 App 路线的**决定性理由**写成：

> prompt 自动发送，不需要任何按键。这是它和 App 的决定性差别……StagePass 无法自主发起

2026-07-28 实测：裸跑 `codex` 时，它会先显示一个**阻塞式**提示——

```
Update available! 0.144.4 -> 0.146.0
1. Update now   2. Skip   3. Skip until next version
Press enter to continue
```

**如果 `codex resume <id> "<prompt>"` 也会先弹这个，上面那条决定性理由当场不成立**，而且表现会是 L2 静默卡住直到 30 分钟超时——正是 §10 点名要避免的形状（老树 82 个 turn 卡在 `running`）。

**这条与终端面板无关，它现在就可能影响已经通过的 L2。** 验之前不要往 PRD 里写任何结论；验完按结果决定是补一条风险、还是补一个必须做的规避（例如启动时带 `--skip-update-check` 之类的开关，如果存在）。

顺带：`0.146.0` 已发布。PRD §2.4 / §6.4 的实测值标的是 `0.144.4`，**升级之后那些结论要重新确认一遍**，不能默认继承。

顺带一条**收益**也要写进 PRD，它不是锦上添花：今天 `defaultLaunch`（`tui-transport.ts:217`）是 `detached: true` + `.unref()`，**StagePass 连子进程句柄都扔了**，不知道 TUI 还在不在。所以 §6.4 第一个坑（不能等进程退出）今天只能靠 30 分钟超时兜底，而 §10 明写着「断掉时的表现必须是明确失败，不能是静默等待——那正是老树 82 个 turn 卡在 `running` 的形状」。**pty 握在 StagePass 手里，这个风险从「靠超时猜」变成「进程死了立刻知道」。** 另外顺手去掉 osascript 这个 macOS 绑定。

## 六、一个未决问题，请先问用户再动笔

**L3 和终端面板的先后没有定。**

- **选项甲（我的建议）**：L3 先用现成的 Terminal.app 跑通，拿到这个项目从来没有过的东西——**一次真人决策推动了状态**（§2.1：走通过的 Change 是 0）。然后再建面板，重验 L2 + 重跑一次 L3 的真选择。
  - 理由：L3 的逻辑链（组题 → elicitation → 答案回来 → 状态前进）与终端在哪无关；在 Terminal.app 里选和在 pty 里选，对它是同一件事。而先建面板意味着为一个还没证明能闭合的交互链，先引入 node-pty + xterm.js + web 框架 + WS 服务。**「先建表面，再发现底下没通」正是这个项目已经死过一次的形状（§2.3）。**
  - additional：面板要改 binding 模型，而 binding 是 L1/L2 的东西。L3 没过就回头改 L2 的数据模型，等于同时动两层，违反 §6 那条「下层验收不通过，不许动上层」的精神。
- **选项乙**：先建面板，L3 直接在面板里验收，只验一次。

**这个选择只影响 §9.2 状态列的写法和一两句话**，改动 1–8 无论选哪个都要做。但 PRD 里**必须写明选了哪个**——留空是老树那种「每层单独看都自洽、缺陷活在层与层之间」的温床。
