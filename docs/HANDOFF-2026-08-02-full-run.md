## 三、验证过真身的机制（本场首次真机）

- 批注链路：`gap.note` 的「人说：」随任务书到红方，多次单轮收口
- not_assessed 归因：那句话精确到线程 id 与归责（补问失败 vs 拒答分开）
- 补问：真触发（第 9 轮）、撞 bug、修掉
- 双前缀（RV-/RVB-、QA-/QAB-）同场不撞
- Review→Fix→Review、QA→Fix→QA 两个闭环各走通一次
- commit 形态产出 + 干净树预检 + C1 上游预检
- detach-on-failure 生产实战多次
- 「编造子 Agent」被 fail-closed 拦住（Plan 第 2 轮：裁判报了不存在的蓝方 id）

## 四、浮出的设计问题（没修，要先谈）

1. **模型能推翻人的驳回。** re-finding 会重开 closed 的 gap —— 对模型自愈是对的，
   但操作员实证 dismiss 过的照样被下一轮蓝方重开（QAB-001/002 重开过一次，
   QA-007 三次）。「以人为主」没被机制保住。候选：人关的 gap 重开需要新证据，
   或人关的进不可重开名单。
2. **阶段间没有「已裁定事项」记忆。** 同一主题跨阶段被新蓝方反复重提（范围定义
   3 次、去重语义 5 次）。候选：已裁定清单随上游产物传下去。
3. **蓝方无限铸币，对抗不收敛。** 每轮关 N 条铸 M 条，纯轮次永不清零。目前靠
   批注钉收口 + 操作员裁决。候选：轮次预算 / 新发现需引用未覆盖的验收条款。
4. **报告类产物污染干净树。** Review/QA/Merge/Retro 写文件不 commit，下一个
   producesCommit 阶段被自己的上游拦住（这场手动入档 5 次）。候选：报告产物由
   StagePass 代 commit。
5. **「同阶段再来一轮」在 Review/QA 上没有动作。** reject 语义是送修；执行方法类
   问题只能空转一趟 Fix（这场发生一次，账本里有痕）。
6. **操作员批注与上游文档打架会制造震荡**（三字段 vs 四字段是我造的）。批注要
   对着上游写，或直接改上游。
