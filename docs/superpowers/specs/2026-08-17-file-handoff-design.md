# 问人改走文件交接（C 方案）

日期：2026-08-17

分支：`codex/native-streaming-app-server`

状态：用户 2026-08-17 拍板走 C，并定下三条硬约束。

## 一、为什么换

现在这条链路要成立，必须满足一个**一次性且事后不可补**的前提：每条线程都由
StagePass 亲手创建，且创建那一瞬间 `mcp_servers.stagepass.*` 就在配置里。

2026-08-17 实测确认了它不可补：

1. `thread/start` 带 config 会拉起插件进程，且能扛过 `thread/unsubscribe` 和连接关闭；
2. `thread/resume` 在线程会话活着时直接失败（`app_server_request_failed`）；
3. 从配置起来的 MCP server 拿不到任何座位身份 —— env 为空，`initialize` 只有
   protocolVersion / capabilities / clientInfo，`cwd` 是**守护进程的 cwd**；
4. `codex resume --remote` 上的 `-c` 不注册 MCP server（参数在命令行上，进程数为 0）；
5. 真实线程 `01a0058a` 从 2026-08-15 建立至今**一次 MCP 调用都没有过** ——
   全部工具只有 `exec` / `wait` / `spawn_agent` / `wait_agent` / `followup_task`。

凡是「一次性且不可补」的前提，时间一长必然被违反。另外 MCP 每会话要人按一次许可，
这条正面挡着「无人值守」。

## 二、新链路

```text
StagePass 写题面文件 + 预铺好的答案文件
   → 信封进 TUI（只有一行路径）
   → 模型只往预留格子里填，填完结束这一轮
   → StagePass 认出轮次结束，读答案文件
   → 浏览器渲染，人在浏览器里答
   → StagePass 写回答文件，下一轮信封指过去
```

只依赖两件事：**文件**，和**往 TUI 里投一行字**。这两件在这棵树里已经是最稳的原语。

## 三、三条硬约束（用户 2026-08-17 定）

1. **模型不创建 JSON。** StagePass 预先铺好整份文件的结构，模型只填格子里的值。
   判据仍是那一条：结构由谁决定，而不是格式是不是 JSON。
2. **每轮最多填 10 条。** 超过 10 条视为这一轮违约。
3. **文件预留 15 个格子。** 多出来的 5 个是余量，不是配额 —— 允许模型挑着填、
   跳着填，但填满的总数不得超过 10。

## 四、格子的形状

沿用现成的 blocker 形状，不另发明：

```json
{
  "stagepass": { "change": "CHG-002", "phase": "PRD", "round": 7, "maxFilled": 10 },
  "slots": [
    { "id": "G-1", "severity": null, "title": null, "where": null, "why": null, "owner": null },
    { "id": "G-2", "severity": null, "title": null, "where": null, "why": null, "owner": null }
  ]
}
```

- **`id` 由 StagePass 预先写死**（`G-1` … `G-15`）。模型不写 id，也就不存在手抄。
- 模型只把 `null` 改成值。`severity` 只能是枚举内的值。
- 不填的格子原样留着 `null`，读的时候跳过 —— 这就是「余量」的含义。
- `stagepass` 那一节是只读抬头，被改动即整份作废。

## 五、判定与失败模式

读回来时按这个顺序判，**第一条不过就整份拒绝**，并把原因原样留给下一轮：

1. `stagepass` 抬头与写出去时逐字节一致（change / phase / round / maxFilled）；
2. `slots` 长度仍是 15，`id` 逐个仍是 `G-1` … `G-15`，顺序未变；
3. 每个格子的键集合未变（不许新增字段、不许删字段）；
4. 已填格子数 ≤ `maxFilled`；
5. 已填格子里 `severity` 在枚举内，`title` 非空；
6. 一个格子只要有任何一个字段被填，就算「已填」；`title` 为空视为未完成的填写，
   整份拒绝（半条 blocker 比没有更糟）。

拒绝不是静默的：理由写进这一轮的失败记录，下一轮的题面里原样带上。

**不做**：不替模型补字段、不猜 severity、不把超出 10 条的部分截断后当成功
—— 截断会让「它到底想说几条」永远查不清。

## 六、和现有账本怎么接

- 已填格子直接进现有的 gap / question 通路，字段一一对应，不新建第二套语义；
- 浏览器那张表原样复用 —— 人本来就坐在浏览器前，不需要 TUI 里的 elicitation；
- `questions` 表、`outcome` 语义、恢复机制全部不动。

## 六·五、逐条关掉不稳定来源

用户 2026-08-17 定的总判据：**排除一切不稳定因素**。所以每一条都要有确定的关法，
「概率上不会发生」不算关掉。

| 不稳定来源 | 关法 |
|---|---|
| 模型把 JSON 写坏 | 解析失败 = 整份拒绝，把解析器的原话写进失败记录，下一轮题面带上。不尝试修复、不猜。 |
| 模型改结构 / 改 id / 改抬头 | 抬头逐字节比对；slots 长度与 id 序列逐个比对。不一致即作废。 |
| 模型填超过 10 条 | 直接拒绝，不截断 —— 截断会让「它到底想说几条」永远查不清。 |
| 半条 blocker（有 where 没 title） | 视为未完成的填写，整份拒绝。半条比没有更糟。 |
| 文件被临时目录清掉 | 答案文件放**持久**路径（`~/.stagepass/rounds/<change>/<phase>/r<round>.json`），不放 `/var/folders`。题面文件仍可临时，它是只读的。 |
| 上一轮的旧文件被当成这一轮 | 路径带轮次，抬头也带轮次；两者对不上即作废。 |
| 模型写到一半被读走 | 只在**轮次结束之后**读；写到一半必然不是合法 JSON，落到「写坏」那条。 |
| 两个座位抢同一个文件 | 路径按 change + phase + round 唯一，天然不共享。 |
| 面板重启丢进度 | 文件在磁盘上，轮次事实在库里，两边都不依赖进程内状态。 |
| 模型不结束轮次 | 不依赖它结束 —— 沿用现有的轮次终态判定；超时按现有租约处理。 |
| 模型压根没填 | 空文件是合法状态（= 这一轮没有要问的），不是错误。 |
| 两条路同时活着 | MCP 那条整条拆掉，不留回退。 |

## 七、不做

- 不让模型创建文件（文件必须已存在，否则这一轮作废）；
- 不让模型改结构、改 id、改抬头；
- 不引入第二条推进状态机的路 —— 文件只是产出，闸门还在原处；
- 不保留 MCP 那条路作为回退（两条路同时活着 = 又一个只有一条做对的坑）。
