# 设计：让每一轮的判定真的到人手上

状态：**已与用户逐条确认（2026-07-31），未实现。**
前置：`docs/PRD-stagepass-rebuild-2026-07-28.md` 仍是唯一权威。
它取代的不是 `DESIGN-rubric-tiers-and-delivery-2026-07-21.md` —— 那一份是**老树**的，
写在重建之前，这里不引用它的任何结论。

---

## 1. 要解决什么

用户 2026-07-31 的原话，这一份的验收标准全部从这几句来：

> 某一条被判 No 就被判 No，就是每一轮我需要知道是什么情况，也就是说，**每对抗一轮，
> 我都是要知情的**。**蓝方一定是要勾的**，判 No 就判 No，无所谓。我会选择把它勾上或者
> 去掉，但是**前提是他要给我**，一切都是由我来决定。

拆成可验收的六条：

| | 要求 | 今天满足吗 |
|---|---|---|
| R1 | 每一轮的判定必须真的到人手上 | **否** —— 六个阶段里三个的蓝方判定没到 |
| R2 | 蓝方必须答那份标准 | **否** —— 三个阶段蓝方没答或答错 |
| R3 | 判 `no` 就是判 `no`，不自动触发别的 | 是 |
| R4 | 勾不勾阻断、留不留那条标准，人决定 | 是（机制在，没人用过） |
| R5 | 裁判给出「还要不要再来一轮 + 理由」，**人按按钮** | **否** —— 裁判不下这个结论 |
| R6 | 裁判下结论时读 PRD / 前期规范 / 红方产出 / 蓝方意见 | **否** —— 提示词写着「只做一件事」 |

另外两条同一次谈定的：

| R7 | 蓝方除逐条外多给一句整体结论，**不动闸门** |
| R8 | Build 的蓝方能读上游文档 —— 否则「有没有完成 PRD/Spec 的要求」只能靠猜 |

**R4 的读法要注意：它不是「要不要做阻断」，是「阻断归人管」。** 出厂默认继续一条都不
阻断（`rubric-defaults.ts` 开头那条拍板不动），用户在面板上勾。这一份**不改出厂值**。

## 2. 今天为什么不满足 —— 三种失效，各有实证

数据源：`.stagepass/verification/build-0730/panel.db` 与对应的 Codex rollout 原文，
2026-07-31 逐条核过。全程 **67 条判定**，其中 **16 条 `not_assessed`**。

`producer` 那份由**蓝方**答，`critic` 那份由**裁判**答（`rubric-round.ts` 的
`ASSESSED_BY`）。16 条的分布是 12 条在蓝方那一侧、4 条在裁判那一侧，而这 16 条里
藏着**三种完全不同的失效**：

### 2.1 契约根本没送到（Review，4 条）

蓝方那份契约是**贴在裁判的提示词里**的，紧跟「2. 反方。任务：…」后面，第二人称
祈使句，**没有一句说这是要转达给反方的**。

实证：Review 那一轮蓝方的 rollout 里**没有任何 `RBC-` 字样**。它不是不答，是没人
给过它清单。

推论：`HANDOFF-2026-07-31-fixes.md` §2.3 那条「一个参与者只能背一份标准」的硬约束，
**在裁判身上结构上已经被违反** —— 蓝方那份必须经它的手，它就必然同时持有两份。

### 2.2 多答一份 → 本职那几条被连坐作废（Review，4 条）

同一轮，裁判把 **8 条全答了**（4 条 producer key + 4 条 critic key，含两条实打实的
`no`）。`readAssessments(裁判的话, critic那四条)` 撞上前四个不认识的 key →
`unknown_key` → **把它答对的那四条一起扔掉**。

它不是漏答，是**做得比要求的多，然后被判全废**。

### 2.3 答错了对象，而且被静默吞掉（Retro，4 条）

裁判把**两份契约都转给了蓝方**。蓝方挑了错的那份答 —— 它写的 4 个 key 全是
**critic** 的，也就是在给自己挑问题的表现打分（自评，正是 2026-07-30 拿掉的东西）。

而且它没包 ```rubric 围栏，于是走
[`rubric-protocol.ts:126`](../src/domain/rubric-protocol.ts:126) 那条
「没围栏就整段捡认识的 key」的宽容路径 —— 4 行全不认识，**`continue` 静默跳过**，
落库是 `not_assessed` + evidence `NULL`，**和「蓝方什么都没说」长得一模一样**。

（第四种情况 QA：契约送到了，蓝方一条没答。这一种今天记的也是 `NULL`，同样分不出来。）

### 2.4 一个必须先说清楚的限制

**StagePass 够不着蓝方。** 它只跟裁判说话，蓝方的契约只能经裁判的手转达，蓝方的话
只能从 rollout 里读回来。所以 R2「蓝方一定要勾」**在现有结构下无法被保证** ——
这一份能做到的是：让它大概率发生，并且**不发生时大声说出来**，而不是伪装成发生了。

真正的保证要靠「补问一次」（§8），而那条线还没验过，不在这一份里。

## 3. 设计

六处改动。前四处合起来解决 R1/R2，后两处是 R5–R8。

### 3.1 契约的转达要有明确的收件人（`domain/round.ts`）

`judgePrompt` 里两份契约现在是两段裸的祈使句并排放着，裁判分不出哪份是自己的。改成
各带一个抬头：

```
蓝方那一份：
   **下面这段原样转达给反方，一个字都不要改。这不是给你答的。**

裁判自己那一份：
   **这一份标准是给你的，只答这一份。** 反方那一份不归你答。
```

**为什么这不是「靠提示词治病」。** 今天的问题不是模型不听话，是**它收到的文本里
根本没有收件人这个信息** —— 一份主语中立的祈使句递到裁判手上，它当成对自己说的，
是照着字面办事。这一步补的是缺失的信息，不是加强语气。

它单独**不足以**保证送达（所以有 3.3 和 §8），但它是其余几步的前提。

### 3.2 只有「谁都不认识」的 key 才作废整份（`domain/rubric-protocol.ts`）

`readAssessments` 多收一个参数：**这一轮别的角色那份的 key**。

```ts
readAssessments(
  text: string,
  criteria: readonly Criterion[],
  elsewhere: ReadonlySet<string> = new Set(),
): ReadAssessment[]
```

fence 里遇到不认识的 key 时：

```
在 elsewhere 里  -> 跳过这一行，不作废（它是别人那份，答错了对象是另一件事，见 3.4）
谁都不认识      -> 照旧 throw RubricOutputVoidError("unknown_key")
```

**作废那条规则本身不撤。** 它挡的是「模型凭空多答一条不存在的标准」，那一条仍然要
作废整份 —— 一个没有标准的判定是假证据。改的只是判据：**「不属于你」和「不存在」
今天被当成同一件事，而它们完全不同。**

Review 那次 8 条全答的情形，改完之后裁判本职的 4 条正常落库，多答的 4 条按 3.4 记账。

### 3.3 契约送没送到，机械可查（`domain/rubric-protocol.ts` + 一个新 reader）

判据是机械的：**那几个 `RBC-<uuid>` 有没有出现在这条线程的 rollout 里**。key 是 uuid，
散文撞上的可能性可以忽略。

**但现有的 reader 看不到它。** `findLastCompletedTurn`
（[`codex/rollout.ts:120`](../src/codex/rollout.ts:120)）只收 `agent_message`，
也就是**模型说过的话**；而契约在**它被问到的那一段**里。所以要加一个并列的读法：

```ts
/** 这条线程里出现过的全部文本 —— 它说的，和它被告知的。 */
export function allTextIn(records: readonly RolloutRecord[]): string
```

同一个模块、同样是纯的（records 进，字符串出），不碰 Codex 私有库，仍然只读 rollout。

**已经实测过这条路走得通**（2026-07-31）：按这个办法扫，Review 的蓝方查无 `RBC-`，
而 Fix / QA / Merge / Retro 的蓝方都查得到 —— 送没送到确实分得出来。

注入形式：`RubricRoundDependencies` 多一个
`readThreadWhole: (threadId: string) => string`，和现有的 `readThread` 并列。
两个 reader 两个用途，名字上就分得开：**`readThread` 是它说了什么，`readThreadWhole`
是它经历了什么。**

### 3.4 每一条 `not_assessed` 都必须说出是哪一种（`work/rubric-round.ts`）

**这是 R1 的落点。** 今天 `evidence` 为 `NULL` 的那 12 条，人看到的是「没评估」，
分不出是没送到、没作答、答错了对象，还是被别人代答了 —— 而这四种要做的事完全不同。

`runRubricRound` 读完三方之后已经握有全部信息，在那里一次算清。每条 `not_assessed`
的 `evidence` 由两个从句拼成，**每一句都是 StagePass 自己核实过的事实**：

```
送达      契约没有送到反方（裁判没有转达）
          契约送到了反方
谁答的    它没有作答
          它答的是裁判那份标准，不是这一份
          这一条由裁判作答，而它不是这一份的判定人，不采信
```

拼法有一条规矩，免得凑出废话：**「送达」那一句永远写；「谁答的」那一句只在它带来
新信息时才写。** 契约压根没送到的时候，「它没有作答」是同义反复，不写；但「这一条
由裁判代答了」即使在没送到时也要写 —— 那是另一件独立发生的事。

于是 §2 那三种失效各自变成一句人读得懂的话：

| 实际发生 | 落库的 evidence |
|---|---|
| Review | 契约没有送到反方（裁判没有转达）；这一条由裁判作答，不采信 |
| QA | 契约送到了反方；它没有作答 |
| Retro | 契约送到了反方；它答的是裁判那份标准，不是这一份 |

**不采信别人代答的，是 R2 的直接后果**（「蓝方一定是要勾的」）。裁判答的 producer
判定**照实记进 evidence 让人看见，但不算数** —— 记下来是 R1，不算数是 R2，两条
同时成立。

`verdict` 仍然是 `not_assessed`，**fail-closed 的语义一个字不动**：勾了阻断的漏答
照样挡门。改的只是「人看得见它为什么没答上」。

### 3.5 裁判给结论，人按按钮（`domain/round.ts`）

R5 + R6。裁判的提示词现在写着「**只做一件事**：对下面这些已经存在的问题逐条表态」，
改成两件事，并且明确要它去读上游：

```
两件事：
1. 对下面这些已经存在的问题逐条表态。
2. 读一遍上面列出的已批准上游产物、正方这一轮的产出、反方这一轮的意见，
   然后给一个结论：还要不要再来一轮，为什么。
   **这是给人看的建议，按不按由他决定 —— 你不需要考虑闸门。**
```

答复格式加一个字段：

```json
{"agents": {...},
 "verdicts": {...},
 "conclusion": {"another_round": true, "reason": "<为什么>"}}
```

**错处理和 `verdicts` 不一样，这是有意的。** 一个坏掉的 `verdicts` 今天会抛、整轮
失败，因为它决定 gap 的状态 —— 拿一份读不准的东西去改状态，比不改危险。而
`conclusion` **不决定任何状态**（R5：人按按钮），为它作废一轮几分钟的对抗不成比例。

所以：

```
没有 conclusion        -> 这一轮没有建议。不抛。
conclusion 结构坏掉    -> 不抛；往 round_notes 记一条「裁判的结论读不出来：<原文前 200 字>」
```

第二条**不是静默跳过** —— 人照样在弹窗里看见「读不出来」，那是 R1。判据是一致的：
**改状态的东西读不准就拒，给人看的东西读不准就照实说读不准。**

**`VERDICT` 那份出厂 rubric 里「没有替正方复述或辩解 —— 裁决只针对问题本身」这条
要重写。** 它是照着「裁判只做一件事」写的，现在裁判被要求就事论事下判断，那条会把
它该做的事判成违规 —— 和 2026-07-30 撞过的那次（`CRITIC` 第三条把蓝方读代码判成违规）
是同一个病。新措辞：结论要建立在它实际读过的东西上，而不是复述两方的话。

### 3.6 蓝方多给一句整体结论（`domain/round.ts` + `domain/turn.ts`）

R7。蓝方那一节加一行，要它在同一个 json 块里多给一个 `overall` 字段：

```json
{"artifactIds": [], "blockers": [...], "overall": "<一句话：整体上这一轮够不够格，为什么>"}
```

**只有蓝方加，红方不加。** 红方给自己的产出写一句整体评价就是自评，那是 2026-07-30
拿掉的东西。所以 `RESULT_CONTRACT` 本身不动，这一行写在 `judgePrompt` 的蓝方那一节。

这条路走得通是因为 `parseTurnResult`（`domain/turn.ts`）**只读它认识的字段，多一个
key 不会拒** —— 已核过。所以红方那边多不多这个字段都不会炸，而蓝方那边要新增一次
具名读取；顺带一提，这也意味着**红方哪天真写了 `overall` 也不会被采信**，因为没有
人去读它。

**不动闸门**（用户明确选的）：它不派生 gap、不进 `blockers`、不参与任何判定。它只
和裁判的结论并排出现在弹窗里。

### 3.7 Build 的蓝方能读上游文档（`domain/round.ts` 的 `blueReach`）

R8。现在 Build 给蓝方的原话是「可以读这一轮改动涉及的文件，以及它们的直接调用方 ——
**只读这些，不要把整个仓库读一遍**」。而 `PRD.md` / `Spec.md` 不在「这一轮改动涉及
的文件」里。

用户要蓝方用 rubric 判「有没有完成 PRD/Spec 的要求」，这个判据它今天够不着 ——
而 `rubric-defaults.ts` 里恰好写着这条教训：**一条只能靠猜的标准比没有更糟**。

改成：改动涉及的文件 + 它们的直接调用方 + **这个阶段的已批准上游产物**（那几个路径
本来就在任务书里列着，是同一份名单，不另算）。

**边界没有被放开成「整个仓库」**：加进来的是一份**有限且已知**的名单，
「攻击这份产出」不会滑成「调查这个项目」——那正是 `blueReach` 那段注释在防的事。

## 4. 这两句话存哪儿

裁判的结论和蓝方的整体判断都是**一轮的话**，而现有三张表都装不下：`gaps` 是问题、
`rubric_assessments` 是逐条判定、`change_evidence` 是闸门看的东西（按 change+phase，
每轮替换）。

新一张小表：

```sql
CREATE TABLE round_notes (
  change_id     TEXT    NOT NULL REFERENCES changes(id),
  -- 照抄 db/schema.ts 里其余每张表用的那份名单，一字不改：
  phase         TEXT    NOT NULL CHECK (phase IN ('PRD','Spec','TechSpec','Plan',
                        'TestPlan','Build','Review','Fix','QA','Merge','Retro','Done')),
  round         INTEGER NOT NULL,
  source        TEXT    NOT NULL CHECK (source IN ('judge_conclusion','blue_overall')),
  -- 只有裁判的结论带这一位。配对 CHECK 和 gaps 那条 severity/kind 的配对同一个路子：
  -- 让「哪种来源该有哪些字段」由 schema 保证，而不是靠调用方记得。
  another_round INTEGER NULL CHECK (another_round IN (0,1)),
  text          TEXT    NOT NULL CHECK (length(trim(text)) > 0),
  created_at    TEXT    NOT NULL,
  CHECK ((source = 'judge_conclusion') = (another_round IS NOT NULL)),
  PRIMARY KEY (change_id, phase, round, source)
);
```

按轮存，不替换 —— **和 `rubric_assessments` 同一个理由：「第几轮说了什么」要留得住。**

### 落到人眼前的那一刻

弹窗的题面在 [`panel-server.ts:1236`](../src/web/panel-server.ts:1236) 由
`gateDecisionQuestion({summary})` 拼出来，`summary` 现在是「几项问题挡着闸门」+
`summariseAssessments(...)`。这两句话接在后面：

```
裁判的结论：还需要再来一轮 —— <reason>
反方的整体判断：<overall>
```

**为什么必须落在这里**：裁决发生在 Codex 画的选择器里，人按下去那一刻眼前只有那张表。
`summariseAssessments` 上面那段注释已经把这个道理写清楚了 —— 要他判断的信息不在
那张表上，就等于要他凭记忆判断。R1 的最后一米在这儿。

## 6. 怎么证

全部离线，不需要真 Codex。判据是**打真实症状**，不是打我改的那个函数
（这一条踩过：测试对着新函数绿、真实路径照旧红）。

| 测试 | 打的是哪个真实症状 |
|---|---|
| 裁判把 8 条全答了 → 它本职那 4 条正常落库，多答的 4 条不采信并写进 evidence | Review 那次连坐作废 |
| 蓝方的 rollout 里没有那几个 key → 4 条 `not_assessed`，evidence 说「契约没有送到反方」 | Review 那次没送到 |
| 蓝方答的是裁判那份的 key、且没有围栏 → evidence 说「它答的是裁判那份标准」 | Retro 那次静默吞掉 |
| 蓝方收到了、一条没答 → evidence 说「契约送到了反方；它没有作答」 | QA 那次 |
| fence 里出现一个**谁都不认识**的 key → 仍然作废整份 | 3.2 没有把作废规则改松 |
| 勾了阻断的 criterion 落成 `not_assessed` → 闸门仍然关着 | fail-closed 没被 3.4 改掉 |
| 裁判的 `conclusion` 读得到 → 进 `round_notes`；读不到 → 这一轮不作废 | 3.5 的宽容 |
| `conclusion` 结构坏掉 → **不抛**，记一条「读不出来」，弹窗里看得见 | 3.5：给人看的东西读不准就照实说 |
| 同一轮里 `verdicts` 结构坏掉 → 仍然抛、整轮失败 | 上面那条没有把 verdicts 一起改松 |
| 弹窗题面里同时出现裁判结论与蓝方整体判断 | R1 的最后一米 |

**这些用例的输入直接取自 `build-0730` 那次真实数据**（裁判那 8 行原文、蓝方那 4 行
错位的原文），不自己编 —— 编出来的输入证明不了「它挡得住真实发生过的那次」。

## 7. 这一份不做什么

- **不改出厂 `blocking`**。R4 是「阻断归人管」，不是「该有阻断」。`installDefaults`
  只补空缺，改默认也只影响新项目 —— 现有两个项目留着它们装上时那一版。
- **不改 rubric 的正文内容**。用户说「我会给一个 Rubric」，编码规范那几条由他在面板上写。
  出厂那几条是起点不是权威。
- **不动账本**。`build-0730` 和用户真库里那些在 bug 下产生的数据一条不改。
- **不碰 `verdict` 那份的归属**。它仍然不进对抗、交给人看。

## 8. 留着的一根线：补问一次

R2「蓝方一定是要勾的」在现有结构下**保证不了**（§2.4）。真正能兑现它的做法是：
这一轮读完发现蓝方没答或答错，StagePass **直接 resume 蓝方那条线程**，把契约原样
发过去，读它的回答 —— 把不可靠的转达换成直连。

**它不在这一份里，因为那根线一次都没验过。** 这棵树的规矩是不在没验过的线上盖东西
（老树一百根「建好了、看着挺像、从没端到端跑过」的线就是这么来的）。

先单独证：拿 `build-0730` 库里现成的蓝方 thread id 去 `codex resume`，看它答不答。
证得通，补问是本设计的一个增量，`readThreadWhole` 和 evidence 那套都能直接复用，
不用返工；证不通，本设计已经把「它在骗你」修掉了，剩下的是「它没答，而你看得见
它没答」—— 那仍然满足 R1，只是不满足 R2。
