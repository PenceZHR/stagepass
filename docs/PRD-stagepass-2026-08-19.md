## 一、这是什么

**一台给单人用的、AI 时代的项目流程仪器。**

它不写代码、不跑轮、不开会话、不管安全。Codex 和 Claude 已经很强，
StagePass 不碰它们做得好的任何事。

它只做两件：

| 柱子 | 一句话 |
|---|---|
| **可审计** | 半年后你能回答「当初为什么否掉方案 A」——问过什么、答过什么、判据是哪条 |
| **状态流转** | 这个 Change 现在在哪个阶段、凭什么能往前走、什么挡着它 |

「安全」不是第三根柱子：预防性的（拦危险操作）归厂商，你已经没有执行通道，拦不住；
事后可查的那种，本来就是可审计。

### 谁用

一个人。你。不做多人、不做团队、不做无人值守。

### 它防的是什么

**遗忘，不是作弊。** 产物文件理论上你可以手写——这个系统不试图防你自己。
所以不需要防篡改，只需要能取回。这一条放开，能塌掉一大半复杂度。

## 二、三个作者 —— 全篇最重要的一条

每一个字段、每一个判断，必须能说出它的作者是谁。只有三种：

| 作者 | 判什么 | 确定性 |
|---|---|---|
| **代码** | 文件在不在、引用的路径存不存在、格子空没空、条数够不够、测试过没过 | 真的不会错 |
| **人** | 剩下的一切 | 「每轮我都要知情」的落点 |
| **模型** | **只填证据，不填判决** | —— |

模型该写：我改了哪些文件、这条问题在哪一行、我的理由是什么、我声称满足了哪条判据。
模型不该写：这条算不算 P0、这个阶段能不能过。

> **验收这份 PRD 的方式**：指着任何一个字段问「谁是作者」，答不出来就是设计没做完。

## 三、四个机制

### 3.1 判据单（Rubric Sheet）—— 闸门的地基

每个阶段有一张判据单。StagePass 从 markdown 源装配，**代码预铺，模型只填空**。
一条长这样：

```
rubricId   SPEC-04          代码预填
text       「每条需求都写明了不做什么」   代码预填（判据原文）
claim      pass | blocked | n_a          模型填，必填，枚举
evidence   spec.md §2.3                  模型填；claim=pass 时必填
verdict    （空）                        人或代码填。空 = 未裁
```

**闸门规则**（`computeGate` 的新输入）：

```
代码硬闸（自动，无人参与）：
  每条判据都有 claim                     缺一条 → 状态不许动
  claim=pass 的，evidence 非空            缺一条 → 状态不许动
  evidence 引用的路径真的存在              找不到 → 状态不许动

人闸：
  硬闸全绿之后，面板把整张单子摆出来，你点。
```

模型的 `claim=pass` **不是通过**，是「我声称满足了，证据在这里」。
能不能过，要先过代码的形式检查，再过你。

**为什么这样拆**：现在树上 `computeGate` 只看两件事——产物空不空、有没有未解决的
blocker。而 `unresolved()` 的实际代码是：

```ts
blocker.kind === "standard"                        // 永远挡
|| blocker.severity === "P0"                       // 永远挡
|| (blocker.severity === "P1" && !waived.has(id))  // 人可放行
```

**P2 一条都不挡，而 severity 是模型填的。** 也就是说今天模型写一个词，一条问题就从
闸门上彻底消失，且不需要任何人点头。判据单把闸门的地基从「模型报了什么问题」换成
「判据单齐不齐」——**齐不齐是代码判的**。

### 3.2 提问（Asking）—— 必须挂在判据上

模型在对话中需要你做决定时，调：

```
stagepass_ask(rubricId, question, options[], why?) → { chosen, note? }
```

**`rubricId` 是硬闸门**：代码校验它属于当前阶段的判据单。不属于 → **拒绝调用，
返回错误，表单根本不弹**。

这就是「不许问别的阶段」的落地方式：把**相关性**从语义判断变成**引用完整性判断**。
代码判不了「这个问题算不算 Spec 阶段的」，但代码判得了「这个 id 在不在本阶段单子里」。

**副产品**：每个问题自动归属到一条判据。于是账本可以按判据聚合，而
**被问得最多的那条判据，就是写得最烂的那条**。流程从自己的使用记录里学会瘦身。

**跨阶段的东西怎么办**：那不是提问，是 blocker。走格子文件，用 `owner` 归因到目标
阶段。**提问和报问题是两条路，别混。**

**选项由 StagePass 给，不由模型编**。`src/domain/question.ts` 已经有整套
（`RESPONSE_AGREE` / `DISMISS` / `WAIVE` / `OWN`，且 P0 拿不到 WAIVE）。
模型可以另给一组选项，但措辞固定的那几类只能引用，不能重写。

### 3.3 留档（Audit Log）

每一次 asking 落一条记录，**不可变，只追加**：

```json
{
  "id": "ASK-0007",
  "changeId": "CHG-001", "phase": "Spec", "round": 3,
  "rubricVersionId": "RB-9f3c…",
  "askedAt": "2026-08-19T21:04:11Z",
  "question": "……", "why": "……",
  "options": ["……", "……"],
  "chosen": "……", "note": "……",
  "answeredAt": "2026-08-19T21:04:53Z",
  "threadHint": "（模型给的，可空，不作判据用）"
}
```

- **文件为准**：`.stagepass/asks.jsonl`，在项目仓库里，可 diff、可 commit、跟着
  Change 走。
- **`rubricVersionId` 存的是版本，不是判据**（2026-08-19 用户定案：「只存版本 id，
  版本 id 由我来维护」）。定位一条判据要 **(版本 id, 序号)** 两个一起。
  **代价**：§3.2 那个副产品（「被问得最多的那条判据就是写得最烂的那条」）跨版本聚合
  时会漂 —— 序号一改，同一个序号就指向别的判据了。让它成立的判据是**人的纪律**：
  同一份 rubric 内只追加、不重排已有条目。代码不强制这一条。
- **库为索引**：`panel.db` 只存查询用的投影。库丢了能从文件重建，反过来不行。
- **未答的也留**：模型问了但你没答（会话关了）也要有记录。缺答案的记录本身是信息。

同一套留档形状也用于：判据单的每次提交、每次状态流转、每次人的裁决。
**账本记的是分叉，不只是进展**——「考虑过 A/B/C，选了 B，因为红方对 A 那条攻击没挡住」，
这句半年后还有用，「Spec 通过了」没有。

### 3.4 工作台（Web Browser）

一个本地 http server，浏览器里开。**职责严格限于三件**：

1. **渲染** —— asking 流、判据单、格子文件、产物清单、账本历史
2. **状态流转** —— 硬闸全绿后，把裁决摆给你点
3. **交题面** —— 把这一轮的信封给你（按钮 + 可复制），你粘进自己的会话

**它不是阻塞路径。** 面板没开着，asking 照样能在会话里问、照样落档。
面板是回看和裁决的地方，不是工作必经之处。

## 四、边界

**永远做：**
- 每个字段说得出作者
- 留档只追加，不改写
- 判据判不出来的，不做闸门，只做题面里的建议
- 精确标识符由代码预填，人和模型都不手抄

**先问再做：**
- 加任何新依赖（现在只有 `better-sqlite3` + `three`；`ws` 那次烧掉了一整夜）
- 任何需要读 Codex 内部状态（`thread/list`、rollout、私有 IPC）才能成立的功能
- 改 `src/domain/` 的判据语义

**永远不做：**
- 执行 turn、开会话、开终端
- 无人值守 / 自动派轮
- 预防性安全（沙箱、审批拦截、hook 阻断）
- 打包成 Codex 插件包走 marketplace / 用 widget 渲染主界面
- 让模型决定能不能进下一阶段

## 五、验收判据（真机，不是测试绿）

每一条都要在一条真实会话上点出来：

1. 模型在 Codex 会话里调 `stagepass_ask`，弹出表单，你点选，答案回到模型。
   **全程没有任何一次手抄。**
2. 同一次提问出现在浏览器面板上，字段完整（含 rubricId、选项原文、你选了哪个）。
3. 模型拿一个**不属于本阶段**的 rubricId 调用 → 工具返回拒绝，**表单不弹**。
4. 判据单缺一条 `claim` → 面板上「进入下一阶段」是灰的，**并说得出缺的是哪一条**。
5. 杀掉工作台进程、重开 → 全部留档还在，且能从 `.stagepass/asks.jsonl` 重建。
6. **全程 StagePass 不需要读 Codex 的线程列表。**
7. 模型把一条问题标成 P2 → 它仍然出现在下一轮的题面里（不挡闸门，但逃不掉）。

## 六、分期

| 期 | 内容 | 完成的判据 |
|---|---|---|
| **P0** | MCP 提问面 + JSONL 留档 | 验收 1、2、5 |
| **P1** | 面板渲染 asking 流 | 验收 2 |
| **P2** | 判据单形状 + rubricId 校验 | 验收 3、4 |
| **P3** | 硬闸接进 `computeGate`，状态流转跟着走 | 验收 4、7 |
| **P4** | 结算：从**产物文件**读回一轮的结果 | 验收 6 |

**P0 独立可用**——它不需要八阶段、不需要 Change、不需要判据单（`rubricId` 可空时
退化成「随便问」）。做完当天你在每条 Codex 会话里都用得上，缺陷会在一周内自己暴露。

**P4 是那把刀**：结算只读产物文件，就不用认回线程、不用滤子 Agent、不用血缘判定。
`thread/list` 的判据昨天写「已实测别再重验」，今晚被推翻——**这一整类问题不是要
解决，是要消失。**

执行通道（`runtime` / `seats` / `await-turn` / `codex/app-server-*`）在 P4 通过之前
不删。通过之后按依赖闭包取证再删。

## 七、悬着的问题

1. **§0.1 那条解读对不对**（模型的 `claim` 是声称还是判决）。这一条错了，§3.1 全废。
2. **MCP elicitation 是 pull 还是 push？** 按协议形状，server 只能在处理一次工具
   调用的过程中弹表单，不能主动推。**没在你机器上验过。** 如果是 pull-only，
   a 的轮间裁决推不进会话，面板必须留着——这决定面板的存亡，值得第一个验。
3. **留档放项目仓库还是 `~/.stagepass/`？** 我倾向项目仓库（跟着 Change 走、
   可 commit），但那意味着 StagePass 会往你的项目里写文件，人的回答：可以接受。
4. **`severity` 那一格最终归谁**。现在归模型，而它是唯一能直接改变闸门结果的字段。
   彻底的解法是「模型只填踩了哪条 rubric，分量由代码从 rubric 算」——但那要求
   你把每条 rubric 的分量事先写死。（你说先不管 rubric，所以这条挂着。）
5. **a 和 b 是一个进程还是两个？** 建议：MCP server 做成薄客户端，状态全部 HTTP
   打到工作台那一个进程。这样「MCP server 按会话起、一台机器上三个进程锁三份代码」
   那个坑自动消失。人的回答：接受
