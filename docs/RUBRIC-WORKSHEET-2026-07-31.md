**裁判那一份（verdict）的第三条，外加一条新的：**

```
删：没有替正方复述或辩解 —— 裁决只针对问题本身

再加一条：给出了「还要不要再来一轮」的结论，并写清楚依据是什么
```

> **为什么必须改**：裁判现在要读上游、要给「还要不要再来一轮」的结论（你 07-31 定的）。
> 旧措辞会把它现在该做的事判成越界 —— 和上面那条是同一个病。
>
> verdict 那份**不进对抗、没有模型判它**，是给你自己对照裁判的表态看的。
> 所以这一栏改不改只影响你读到的提示，不影响任何自动判定。

## 2. Build 正方那一份：草稿

**这是草稿，内容归你。** 我按你说的两个维度写：**编码规范** + **有没有完成
PRD/Spec 的要求**。

### 2.1 写这几条时守的三条规矩

1. **每一条都得是反方真答得出来的。** Build 的反方能读**这一轮改动涉及的文件、
   它们的直接调用方，以及已批准的上游文档**（最后这一项是 07-31 为你这个需求
   刚放开的），但**它跑不了任何东西**。所以没有一条是「跑起来对不对」——
   那类只能靠正方交运行证据。
   > 这条规矩有代价的先例：旧的第四条「自己跑过一遍，而不是只保证能编译」正是
   > 一条判它的人跑不了的标准，于是它每一轮都只能得到一个没有依据的 yes。

2. **每条只有满足 / 不满足**，不打分（你原来定的，不可推翻）。

3. **条数越多，漏答的机会越多。** 勾了阻断的条目**漏答也挡门**（fail-closed）。
   所以我压到 8 条，宁可少而每条都答得实。

### 2.2 八条

**做到要求没有（对着 PRD / Spec 看）**

1. PRD 和 Spec 里属于这一次范围的每一条要求，都能指出代码里是哪一处实现的
2. Spec 写明的边界情况和出错时的表现，代码里都有对应处理，不是只走通了主流程
3. 没有做 Spec 里没有的事 —— 多出来的行为都写清了依据

**代码本身（对着改动和调用方看）**

4. 命名和上游文档、既有代码用的是同一套词，没有为同一个概念发明第二个名字
5. 每一处不明显的决定都在代码里留下了**为什么**，而不只是写了做了什么
6. 出错路径有明确处理，没有吞掉异常，也没有把失败当成成功往下走
7. 新增或改名的每个导出都有调用方，受影响的调用点都跟着改了，没有留下死代码或半途的开关

**交代**

8. 交出了运行证据：跑了哪条命令、输出是什么，而不是只说「应该能跑」

### 2.3 阻断勾哪几条 —— 我的建议，你定

建议只勾 **第 1 条** 和 **第 8 条**：

- **第 1 条**是「这次到底做没做到」，别的都是怎么做的问题。它不满足，这一轮就该回炉。
- **第 8 条**是唯一一条能挡住「看着写完了其实没跑过」的。

其余六条判 `no` 时不挡门，但会写进你裁决前看的那张表 —— 你照样看得见，
只是由你决定要不要为它再来一轮。

**勾阻断之前要知道的一件事**：勾了阻断的条目，**模型漏答也会挡门**（这是有意的，
漏答被静默当成通过正是这套东西要防的）。07-31 之后漏答会写明白是哪一种
（没送到 / 没作答 / 答错了对象 / 被别人代答），所以卡住的时候你能看出该去改哪儿。

## 3. 改完之后

不用重启面板。rubric 是版本化的：改一次产生一个新版本，**已经记下的判定引用的还是
它们当时那一版**，所以改标准不会让任何已经盖过章的东西失效，也不会移动任何已经开
出去的阻断项。

反过来：**撤下一条正活着的阻断标准要写理由**（PRD §1.1）。上面这些改动全是不阻断
的条目，所以不会问你要理由。
